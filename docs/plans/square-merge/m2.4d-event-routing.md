# M2.4d — Маршрутизация событий и автоматизация

> Подплан [M2.4](m2.4-devices-alarms-automation.md). Ветка `square-merge/m2.4d-event-routing`
> от `master` после `m2.4c`.
>
> **Результат:** событие журнала запускает настраиваемую подписку; действия исполняются
> идемпотентно, восстанавливаются после сбоя и не зацикливаются. Реакции больше не зашиты в код.
>
> Подплан дописывает `event_subscriptions`/`subscription_actions` в baseline VmsCfg — база
> пересоздаётся ещё раз (§8 родительского плана). Baseline VmsMap тоже меняется (индекс ключа
> операции у `alarms`), поэтому `ta_map` пересоздаётся вместе с `ta_cfg`.

Маршрутизация — не обработчик сообщений с `switch` по типу действия, а небольшой движок
автоматизации: ему нужны гарантии исполнения, журнал запусков и диагностика. Поэтому гарантии
фиксируются здесь явно, а не выводятся из реализации.

## Шаг 2. VmsCfg: подписки ✅

Файлы: `dotnet/VmsCfg/Grpc/migrations/0000_init.sql`, новый `EventSubscriptionStorage.cs`,
`CfgServiceImpl.cs`, `VmsCfgDbContext.cs`, `VmsCfg.Tests`.

```sql
CREATE TABLE event_subscriptions (
  id uuid PRIMARY KEY,
  name text NOT NULL,
  enabled boolean NOT NULL DEFAULT true,
  event_name text NOT NULL,       -- sensor | relay | analytics | alarm_raised | alarm_returned | ...
  source_filter jsonb NOT NULL DEFAULT '{}',
  armed_condition text NOT NULL DEFAULT 'any' CHECK (armed_condition IN ('any','armed','disarmed')),
  cooldown_ms integer NOT NULL DEFAULT 0,
  version integer NOT NULL DEFAULT 1   -- растёт на каждом upsert; Router фиксирует снимок
);

CREATE TABLE subscription_actions (
  subscription_id uuid NOT NULL REFERENCES event_subscriptions(id) ON DELETE CASCADE,
  position integer NOT NULL,
  kind text NOT NULL CHECK (kind IN
    ('retain_recording','set_relay','emit_event','raise_alarm')),
  params jsonb NOT NULL,
  PRIMARY KEY (subscription_id, position)
);
```

**Селектор события** (`event_name` + `source_filter`):

```json
{
  "object_ids": [],
  "camera_ids": [],
  "kinds": ["digital_input"],
  "tokens": [],
  "props": {"contact": "closed", "min_confidence": 0.6}
}
```

Семантика фиксируется и проверяется при сохранении, а не в момент исполнения:

- **Источник полей — `extra_props` события.** У `Event` есть только `object_id`, `event_name`,
  `param0`, `param1` и `extra_props`; `device_node` Router недоступен. Поэтому `camera_id`,
  `part_kind`, `token`, `contact`/`active` пишет в props сам VmsMap (`m2.4b`), а матчер читает их
  оттуда. Без этого `demo-sensor-recording` с `props.contact` не совпадёт никогда.
- все поля объединяются через **AND**; пустой список или отсутствующее поле — «любой»;
- `object_ids` — по `object_id` события; `camera_ids`/`kinds`/`tokens` — по одноимённым props;
  `camera_ids` — UUID; `kinds` ∈ `{digital_input, relay}`; `tokens` — строки;
- `props` — равенство строк, кроме `min_confidence` (числовое «не меньше»; читается из prop
  события `confidence`, который пишет аналитика в `m2.4e` — ключ селектора называет порог, а не
  поле). Типы: значение в `props` — строка, число или boolean; `null`, массив и объект
  отвергаются при сохранении, а не приводятся неявно. При сравнении число и boolean берутся в их
  JSON-написании (`5`, `true`), строки — как есть; `min_confidence` обязан быть числом 0–1 и
  сравнивается как число;
- отсутствующее в событии поле не совпадает с заданным значением;
- **неизвестный ключ в `source_filter` или `params` — `400` при сохранении**, а не тихий игнор;
- `event_name` — только из словаря событий карты.

**Параметры действий** (тоже валидируются при сохранении, с проверкой существования через
CfgService/MapService):

| kind | params | Что делает |
|---|---|---|
| `retain_recording` | `cameras` — список UUID или `["source_camera"]`; `timeout_seconds` 1–3600; `event_id` — шаблон, по умолчанию `subscription:{subscription_id}:{source_object_id}`; `raise_alarm` (по умолчанию `false`) | `VmsFs.RetainEvent` на N камер; VmsFs создаёт свой `event_uuid` на пару `(event_id, camera_id)`; повтор в пределах эпизода продлевает его |
| `set_relay` | `camera_id` — UUID; `token`; `active` | `VmsOnvif.SetRelayOutputState` — **устанавливает требуемое состояние**, а не переключает; повтор с тем же значением ничего не меняет у выхода с фиксированным состоянием (см. оговорку в разделе идемпотентности) |
| `emit_event` | `object_id` (UUID или `"source"`), `event_name`, `param0`, `param1`, `props` | `VmsMap.UpdateEvents`; id детерминирован от `(subscription_id, trigger_event_id, position)`, вставка `ON CONFLICT (id) DO NOTHING`, строка outbox — **только при фактической вставке** |
| `raise_alarm` | `object_id` (UUID или `"source"`), `definition` ∈ `{sensor, subscription}`, `dedup_key` — шаблон, по умолчанию `subscription:{subscription_id}:{source_object_id}` | `VmsMap.RaiseAlarm`; `(source_event_id, object_id, dedup_key)` среди строк любого статуса и `(object_id, dedup_key)` среди незакрытых возвращают существующую тревогу без второго события |

**Шаблоны.** В `event_id` и `dedup_key` допустимы ровно три подстановки — `{subscription_id}`,
`{source_object_id}` (узел события-источника) и `{camera_id}` (камера каждой итерации
`retain_recording`); неизвестная подстановка — `400` при сохранении. Служебные поля причинной
цепочки (`causation_id`, `origin`, `depth`, `causation_chain`) Router пишет **после** пользовательских
`props` и перезаписывает их: подписка не может подделать путь, который её же останавливает.

**Идемпотентность каждого действия — проверяемое требование, а не пожелание.** `next_position`
сужает окно повтора, но не закрывает его: процесс может упасть после действия и до записи
позиции, поэтому каждое действие обязано пережить повтор. Проверяется отдельным тестом на каждое
действие:
- `set_relay` — повтор не меняет результат и не дёргает реле. Оговорка: это верно для выходов с
  фиксированным состоянием (`Bistable`); у моностабильного выхода повторная установка `active`
  может повторить импульс. Защиты от этого в M2.4 нет — окно сужает запись запуска, но не
  закрывает; ограничение записано в `event-routing-followups.md`;
- `raise_alarm` — повтор не создаёт вторую тревогу и не пишет второе `alarm_raised`.
  **Ключ операции** `(source_event_id, object_id, dedup_key)` среди строк любого статуса: повтор
  того же действия возвращает ту же тревогу, даже если оператор успел её закрыть. Это отдельная
  задача от `dedup_key` «одно условие — одна открытая тревога»: `dedup_key` не даёт двум
  одновременным условиям стать двумя тревогами, `source_event_id` не даёт одному запуску создать
  вторую тревогу после закрытия первой. Оба ключа — индексы в `ta_map.alarms`, не проверки в коде;
- `retain_recording` — повтор в пределах `MaxEpisodeDuration` продлевает тот же эпизод; окно
  повтора ограничено пятью попытками и таймаутом обработчика (секунды-минуты), что заведомо
  меньше 3 минут. Повтор после долгого простоя (рестарт через часы) откроет новый эпизод — это
  осознанно: опоздавшая реакция всё равно опоздала;
- `emit_event` — повтор даёт тот же id события, и Router пропускает уже завершённый запуск.
  **Строка outbox пишется только при фактической вставке события**: иначе повторная публикация
  старого события запустила бы подписку, созданную уже после него.

**Повторы: точная семантика.** Счётчик попыток живёт в записи запуска (`attempts`), а не в памяти
обработчика и не в политике брокера: рестарт процесса его не сбрасывает. Попытка считается на
весь запуск, а не на действие. Первая ошибка любого действия останавливает цепочку и возвращает
`Retry`; после пятой попытки запись получает `status=failed` с `error` **до** подтверждения
сообщения, публикуется в `debug-entity-state`, и сообщение подтверждается. Ошибки не делятся на
временные и постоянные: у Router нет надёжного способа их различить, а пять попыток — достаточный
барьер, чтобы постоянная ошибка не крутила очередь. Таймаут политики сообщения (60 с) — не число
попыток: он покрывает цепочку из нескольких RPC, а решение о повторе принимает Router.

**Окно повтора и TTL.** Запись запуска хранится 24 ч. Это заведомо больше любого окна повторной
доставки брокера (Dapr/RabbitMQ повторяет минуты, не сутки) и любого рестарта процесса; за
пределами окна действует то же правило, что и для retention: «опоздавшая реакция всё равно
опоздала» — повтор спустя часы законно откроет новый эпизод и новую тревогу. Отдельного вечного
реестра идемпотентности нет: его цена — вторая база, растущая без границы, а выигрыш — только для
replay, которого в системе нет.

**Параллельная обработка.** Даже один экземпляр не гарантирует, что обработчик не будет вызван для
двух доставок одновременно, поэтому подписчик в VmsSingleton сериализует обработку семафором, а
запись запуска пишется в общий state store. Тест «два одинаковых сообщения» проверяет
последовательную пару доставок; настоящую межпроцессную гонку закрывает не память, а ключ операции
у действия.

`Upsert`/`Remove` публикуют `event-subscriptions-changed` после коммита; `version` растёт.
`ListEventSubscriptions` отдаёт подписки с действиями.

**Проверка:** `dotnet test dotnet/VmsCfg.Tests`; неизвестный ключ, несуществующая камера,
недопустимый `event_name` и недопустимый `kind` отвергаются; повторный upsert увеличивает
`version`.

## Шаг 3. VmsSingleton: `EventRouting` ✅

Файлы: `dotnet/VmsSingleton/Program.cs`, `VmsSingleton.csproj`, новые
`EventRouting/EventRouter.cs`, `SubscriptionCache.cs`, `SubscriptionMatcher.cs`, `ActionExecutor.cs`,
`EventRunStore.cs`, `CausationChain.cs`, `MediaServerRegistry.cs`; новый проект
`dotnet/VmsSingleton.Tests`.

Почему здесь, а не в VmsMap: VmsMap реплицируем, а запуск подписки должен произойти ровно в одном
месте. `VmsSingleton` уже имеет Dapr pub/sub и клиент `CfgService`. Он ничего не хранит, кроме
ключей запуска и cooldown в state store, и командует сервисами через их RPC.

Единственность `VmsSingleton` — инвариант развёртывания (`CLAUDE.md`; в compose одна реплика).
Отдельная распределённая координация не нужна: ключи запуска и cooldown лежат в state store, и даже
ошибочно запущенная вторая реплика не задвоит запуск — она лишь поделит поток событий (consumer
group), что деградирует, но не дублирует. Поэтому в `m2.4d` проверяется, что в обоих compose у
`VmsSingleton` `replicas: 1`/единственный экземпляр, а не добавляется блокировка.

**Предел масштаба (инварианты 17, 21).** Router — один экземпляр, и это осознанно: он обрабатывает
события журнала, а при 100 000 камер поток переходов датчиков — единицы-десятки в секунду, что один
процесс держит. Опасен только нефильтрованный `analytics`: гейт в `m2.4e` обязателен. Всё состояние
запусков, cooldown и дедупликации — в общем state store, а не в памяти, поэтому Router можно вынести
в отдельный шардируемый сервис без переделки логики; это записано в
`event-routing-followups.md`.

**Поток:**

```
map-event-created {event_id}
  → Router читает событие (MapService) и подписки (кэш из VmsCfg)
  → SubscriptionMatcher: event_name + source_filter + armed_condition
  → CausationChain: depth и повтор подписки в цепочке
  → EventRunStore.Get:
       running    → продолжить с next_position (cooldown не спрашивается)
       completed/failed → подтвердить и ничего не делать
       нет записи → Cooldown (только здесь) → записать запуск → стартовать cooldown
  → ActionExecutor: действия по порядку, next_position после каждого
```

Порядок здесь — часть гарантии, а не оформление. **Существующий запуск отвечает раньше cooldown'а**:
cooldown, взятый самим запуском, иначе выглядел бы штормом и проглатывал бы повтор, который должен
продолжить этот же запуск. По той же причине запись запуска пишется **до** cooldown'а: падение
между ними оставляет запуск, повтор его находит и продолжает; обратный порядок оставил бы cooldown
без запуска и потерял бы реакцию.

**Гарантии (инвариант 8):**

- Доставка — **at-least-once**; exactly-once для цепочки из нескольких сервисов не обещается.
  Consumer group (один app id — одна очередь) исключает *параллельную* доставку одного сообщения
  двум репликам, но не повтор: обработчик упал до подтверждения, подтверждение потерялось,
  подписчик перезапустился, брокер повторил доставку. Все четыре случая — норма, а не сбой, и
  покрываются записью запуска вместе с идемпотентностью действий.
- Запуск идемпотентен, и каждое действие идемпотентно: `retain_recording` — стабильный `event_id`
  (продление эпизода), `emit_event` — детерминированный id события, `raise_alarm` — ключ операции
  `(source_event_id, object_id, dedup_key)` поверх дедупликации незакрытых, `set_relay` — по
  значению.
- **Запись запуска** в state store: ключ `event-run:{subscription_id}:{trigger_event_id}`,
  TTL 24 ч, значение:

  ```json
  {"subscription_id":"...","trigger_event_id":"...","version":3,
   "snapshot":{...},"next_position":2,"status":"running",
   "attempts":1,"error":null,"updated_at":"..."}
  ```

  `snapshot` — подписка с действиями на момент старта (инвариант 12): изменение конфигурации не
  меняет уже начатый запуск. После успешного действия `next_position` увеличивается; статус
  `completed` — когда пройдены все. Повторная доставка продолжает с `next_position`, а не с нуля
  и не «всё сначала». Повтор уже выполненного действия безопасен благодаря идемпотентности, но
  лишней работы не делаем. Запись пишется **до** старта cooldown (см. поток) и до первого
  действия: падение между ними не теряет запуск.
- **Ошибка действия:** действия выполняются последовательно; первая ошибка останавливает цепочку
  и возвращает `Retry`. Счётчик `attempts` — в записи запуска, не в памяти; после пяти
  доставок — `status=failed`, `error` сохраняется, запись публикуется в `debug-entity-state`
  (`service=vmsingleton`, `entity_type=event_run`), сообщение подтверждается. Так оператор видит
  невыполненную реакцию, а очередь не крутит её вечно. Таймаут обработчика (60 с) — не число
  попыток; политику повтора решает Router.
- **Cooldown** — на пару `(subscription_id, source_object_id)`, в state store
  `event-cooldown:{subscription_id}:{source_object_id}`, чтобы пережить рестарт. Проверяется
  **только для нового запуска**; существующий running-запуск продолжается независимо от него,
  иначе cooldown, взятый самим запуском, проглатывал бы его собственный повтор.
- **Причинная цепочка:** каждое событие подписки несёт props `causation_id`, `origin=subscription`,
  `depth` и список пройденных подписок (`causation_chain`, через запятую). Router не запускает
  подписку, если `depth > 8` или `subscription_id` уже есть в цепочке; отказ пишется в лог и в
  `debug-entity-state` (`event_routing_suppressed`). Это сознательное ограничение модели, а не
  универсальный детектор циклов: повторное применение той же подписки в одной цепочке запрещено
  всегда. Служебные props пишет Router последними — подписка не может их подменить.
- Router не доверяет телу `map-event-created`: конфигурацию перечитывает из VmsCfg, событие — из
  VmsMap, охрану — из VmsMap (`GetNodeArming`).

**`SubscriptionCache`** — кэш подписок, инвалидируется по `event-subscriptions-changed`. VmsSingleton —
ровно один экземпляр, поэтому pub/sub здесь достаточен (в отличие от реплицируемого VmsMap,
инвариант 14). TTL кэша — 60 с: если сигнал потерян (VmsCfg упал между коммитом и публикацией),
устаревшая конфигурация живёт не дольше минуты, а не «пока не перезапустят». Outbox для
конфигурации не нужен: это редкие администраторские изменения, и минута задержки дешевле, чем
второй механизм доставки. Определения тревог Router не кэширует — он их не резолвит: VmsMap
превращает имя источника в определение и сам пишет предупреждение, если его нет.

**`MediaServerRegistry`** — двухуровневый кэш: `ListMediaServers` (сервер → fs/onvif) и
**камера → сервер** через `CfgService.GetCamera`, оба на 30 с. Без второго уровня
`retain_recording`/`set_relay` по `camera_id` нельзя адресовать: `ListMediaServers` не знает, к
какому серверу относится камера. Клиенты VmsMap/VmsFs/VmsOnvif — через
`DaprClient.CreateInvocationInvoker`, таймауты 5–10 с.

**Программная обвязка.** `Program.cs` читает новый `DAPR_MAP_APP_ID` (он уже есть в `.env:129`,
но не используется) и регистрирует `AddVmsDebugState()` из `VmsLog` — иначе обещанная диагностика
`event_runs`/`event_routing_suppressed` некуда публикуется. Переменная добавляется в конфигурацию
запуска VmsSingleton в `.vscode/launch.json` (сейчас её там нет, F5 упадёт), в `../ta_install/.env`
она уже есть.

**Семантика `event_id` у `retain_recording`** — по умолчанию это ключ эпизода, а не случайный
идентификатор: `event_id` = `subscription:{subscription_id}:{source_object_id}`. Параметр `event_id`
— шаблон с теми же тремя подстановками, что и `dedup_key`; пустой параметр берёт это значение.
События одного источника в пределах `MaxEpisodeDuration` (3 мин) продлевают один эпизод; после
истечения VmsFs открывает новый `event_uuid` под тем же `event_id`. Cooldown подписки работает до
этого механизма и не заменяет его: он гасит шторм, а ключ эпизода группирует запись.

## Шаг 4. Отложенное ✅

Создать `docs/future_plans/event-routing-followups.md`: окна времени и выдержки (`for_seconds`),
условия по пространству, уведомления и вебхуки, пользовательские выражения, PTZ-пресет как
действие, полный редактор подписок, диагностический экран запусков. Дописать туда же оговорку про
моностабильный выход в `set_relay`: повторная установка `active` для него повторяет импульс, и
защиты в M2.4 нет.

### Integration

- **Повторная доставка `map-event-created`** (четыре случая): обработчик упал до подтверждения —
  запуск продолжается с `next_position`; подтверждение потерялось — дубль видит `status=completed`

  повторил доставку после успеха — эффектов нет. Две доставки подряд обрабатываются
  сериализованно и дают один запуск.
- Каждое действие отдельно переживает повтор (см. таблицу идемпотентности): второе `RetainEvent`

  второй `emit_event` не публикует событие заново.
- Изменение подписки во время исполнения не влияет на начатый запуск.
- Ошибка действия после 5 попыток оставляет `status=failed` и запись в реестре диагностики.
- Потерянный `event-subscriptions-changed` (VmsCfg упал между коммитом и публикацией) — кэш

## Ход работы

Реализовано 2026-11-06 на ветке `square-merge/m2.4d-event-routing` (от `square-merge/m2.4c-alarms`).
Решения, принятые по ходу и не выводимые из кода:

- **Порядок «запуск → cooldown» исправлен по ревью плана.** Существующий запуск отвечает раньше
  cooldown'а, запись запуска пишется до старта cooldown'а. Без этого повтор, обязанный продолжить
  запуск, проглатывался бы cooldown'ом, который этот же запуск и взял.
- **Ключ операции `raise_alarm` — `(source_event_id, object_id, dedup_key)`** в `ta_map.alarms`,
  частичный уникальный индекс `ux_alarms_subscription_event` (только `source = 'subscription'`).
  Retention исключён: он переиспользует id эпизода на каждом продлении, и тому нужно двигать
  проектируемый конец.
- **Существование `object_id` при сохранении подписки не проверяется.** Дерево узлов — VmsMap, а
  VmsCfg намеренно не читает его базу (CLAUDE.md: ядро не пишет ничего ради карты); узел, которого
  нет, отвергнет сам VmsMap при исполнении. Камеры проверяются — они в таблице VmsCfg.
- **Определения тревог в `SubscriptionCache` не кэшируются**: Router их не резолвит, это делает
  VmsMap при raise. Кэш держит только подписки.
- **UI в этом подплане нет** — контракт `CfgService` готов, панель `Admin → Event routing`
  собирается в `m2.4e` по нему.
- `DAPR_STATE_STORE_NAME` добавлен в конфигурацию запуска VmsSingleton (`.vscode/launch.json`):
  запись запусков и cooldown живут в общем state store, без переменной сервис не стартует.
