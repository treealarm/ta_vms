# M2.6 — Диаграмма устройства: модель, части в регионах, автопривязка

> Часть плана Square → ta_vms (`docs/plans/square-merge/README.md`).
> **Низкоприоритетный концепт**, не обязательство: выполняется после M2.4 (части устройства,
> `device_node`) и M2.5 (демо-пары). Ветка `square-merge/m2.6-device-diagrams` от `master`
> после M2.5.
>
> Идея пользователя 2026-11-05: «разрисовать камеру как свитч» — диаграмма, похожая на реальный
> девайс (вид сзади, входы и реле), где регионы реально привязаны к железным собратьям в плане
> состояний; тип диаграммы «дружит» с моделью устройства, а реплики частей появляются
> автоматически.
>
> **Правило сопоставления уточняется на реальных камерах.** Автопривязку делаем; когда дойдём до
> выбора признака (`token`/`name`/`index`), нужно попросить пользователя включить реальные камеры и
> посмотреть, как у них идентифицируются реле и сенсоры. До этого — разумный дефолт (точный
> `token`) и настраиваемый `match_by`.

## 1. Идея и место в модели

У нас уже есть две оси:

- **Space** — реальное географическое место (карта, план, этаж): координаты, геометрия, картинка.
- **Node** — логическая сущность в `objects`: контейнер, камера, часть устройства, мнемосхема.
  Узел можно поставить на Space, а можно не ставить; узел может быть холстом для детей.

M2.4 добавляет третью ось — **часть реального устройства**: цифровой вход и реле камеры — это
логические узлы под камерой (`device_node`), у них есть состояния и события. M2.6 добавляет
**четвёртую** — представление устройства на уровне детализации:

> Диаграмма устройства — это узел-холст, который изображает физический девайс (вид сзади,
> передняя панель, клеммник). В её регионах стоят **реплики** логических частей устройства; реплика
> показывает состояние владельца, поэтому регион «реле lamp» горит ровно тогда, когда горит
> реальное реле.

Тип диаграммы может описывать **полное устройство** — все возможные входы и реле модели, включая
те, которых у конкретного экземпляра нет. Конкретная камера показывает только те части, которые
реально есть у неё и заведены в конфигурации. Нет части — нет реплики и нет состояния: регион
остаётся нарисованным, но пустым. Тип не выдумывает сущности, которых нет у устройства.

Это не новая ветка дерева и не новый вид устройства: диаграмма — обычный узел с `diagrams`-строкой,
её дети — обычные реплики (`objects.owner_id`) с `region_id`. Всё, что нужно, уже есть в модели
Square; не хватает **шаблона типа** и **автоматической привязки к модели устройства**. Правило
сопоставления сущностей уточним на реальных камерах.

### Зачем

- **Документирование инфраструктуры.** Администратор видит камеру не как точку на карте, а как
  устройство: сколько у неё входов, какие реле, что к ним подключено.
- **Оператору — панель.** Открыл камеру → «вид сзади» → видит, что реле `lamp` включено, вход
  `input` замкнут; кликает по региону — попадает в узел части, её события и состояния.
- **Один механизм для всех устройств.** Камера сегодня, пожарная панель/свитч/контроллер — завтра:
  шаблон описывает модель, а не конкретный тип кода.

## 2. Что уже есть

| Механизм | Где | Что даёт |
|---|---|---|
| `diagram_types`, `diagram_type_regions` | `dotnet/VmsMap/Grpc/migrations/0001_square_schema.sql` | Тип мнемосхемы: картинка и именованные регионы |
| `diagrams` (`dgr_type`, `region_id`, `geometry`) | там же | Узел-диаграмма и место ребёнка в регионе |
| Реплики (`objects.owner_id`) | `MapServiceImpl.CreateReplica` | Копия узла, показывающая состояния/значения владельца |
| `region_id` | `DiagramViewer.tsx`, `diagramGeometry.ts` | Ребёнок без своей геометрии стоит в регионе; перетаскивание меняет регион |
| Части устройства | M2.4: `device_node`, `device-parts-known` | Логические узлы `digital_input`/`relay` под камерой |
| Модель устройства | `VmsOnvif.OnvifSettingsService.GetDeviceInfoAsync` | `manufacturer`, `model`, `firmware` по ONVIF |

Чего нет:

- у `diagram_types` нет признака «это шаблон устройства» и модели, которой он соответствует;
- нет отображения «регион → часть устройства»;
- нет автоматического создания диаграммы и реплик частей при появлении камеры;
- `CreateReplica` не умеет ставить реплику в регион одной транзакцией (сегодня это делает
  `saveDiagramPlacement` отдельным вызовом).

## 3. Предложение

### 3.1. Модель устройства в манифесте

`device-parts-known` (M2.4) расширяется полями уровня устройства:

```json
{
  "source_kind": "camera",
  "source_id": "…",
  "manufacturer": "OnvifSim",
  "model": "Simulated fixed camera",
  "firmware": "0.1.0",
  "parts": [ { "kind": "digital_input", "token": "input", "name": "…", "idle_state": "open", "present": true } ]
}
```

- VmsOnvif заполняет `manufacturer`/`model`/`firmware` из `GetDeviceInformation` при discovery
  (раз в 60 с, M2.4); если камера не ответила — пустые строки, автопривязка не срабатывает.
- VmsMap хранит снимок в новой таблице `device_info` (`source_kind`, `source_id`,
  `manufacturer`, `model`, `firmware`), чтобы автопривязка не зависела от тела события и
  переживала рестарт. Это **снимок железа**, а не конфигурация: владелец — интеграция.
- Поля необязательные: старый VmsOnvif без них просто не даёт автопривязки; ручная привязка
  работает.

```sql
CREATE TABLE device_info (
  source_kind varchar NOT NULL,
  source_id   uuid    NOT NULL,
  manufacturer text   NOT NULL DEFAULT '',
  model        text   NOT NULL DEFAULT '',
  firmware     text   NOT NULL DEFAULT '',
  PRIMARY KEY (source_kind, source_id)
);
```

### 3.2. Тип диаграммы как шаблон устройства

`diagram_types` получает признаки шаблона. M2.4 уже сворачивает схему в один `0000_init.sql`,
поэтому это колонки в `CREATE TABLE`, а не отдельная миграция; `ALTER` ниже — только для
наглядности:

```sql
ALTER TABLE diagram_types
  ADD COLUMN source_kind          varchar,               -- 'camera' сегодня; null = обычная мнемосхема
  ADD COLUMN device_manufacturer  text NOT NULL DEFAULT '', -- '' = любой
  ADD COLUMN device_model         text NOT NULL DEFAULT '', -- '' = любая
  ADD COLUMN auto_attach          boolean NOT NULL DEFAULT false;
```

Сопоставление — точное, без регулярных выражений: `source_kind` совпадает, `device_manufacturer`
и `device_model` равны (регистронезависимо) или пусты. Если подходят несколько типов, выигрывает
тип с непустыми `manufacturer`/`model`; при равенстве — ничего не создаём и пишем предупреждение
(лучше явная ошибка конфигурации, чем случайная диаграмма).

Связь «регион → часть» — отдельная таблица. Регион может указывать часть не только точным
токеном, но и именем или порядковым номером; признак и значение — две колонки:

```sql
CREATE TABLE diagram_type_parts (
  diagram_type_id uuid NOT NULL REFERENCES diagram_types (id) ON DELETE CASCADE,
  region_key      text NOT NULL,
  part_kind       text NOT NULL,   -- 'digital_input' | 'relay'
  match_by        text NOT NULL CHECK (match_by IN ('token','name','index')),
  match_value     text NOT NULL,   -- token, имя или 1-based индекс как текст
  PRIMARY KEY (diagram_type_id, region_key),
  FOREIGN KEY (diagram_type_id, region_key)
    REFERENCES diagram_type_regions (diagram_type_id, region_key) ON DELETE CASCADE
);
```

Правила сопоставления:

- **token** — точное совпадение `part_kind` + `token`; самый надёжный, его и стоит использовать по
  умолчанию.
- **name** — регистронезависимое совпадение с именем части: `device_settings.name`, если оно
  задано, иначе `name` из `device-parts-known`. Имена не обязаны быть уникальными; совпадение
  двух частей с одним именем — предупреждение, регион не привязывается.
- **index** — 1-based порядок части внутри `kind` в манифесте (`1` — первый вход, `2` — второе реле
  и т.д.). Порядок должен быть стабильным между публикациями манифеста: либо `ordinal` в
  `device-parts-known`/`device_node`, либо сортировка по `token`. Что именно — открытый вопрос;
  до решения индекс считается по порядку в манифесте.
- Приоритет: `token` > `name` > `index`. Если одну часть выбрали два региона, это конфликт
  конфигурации: пишем предупреждение, реплика не создаётся (либо создаётся в первом регионе —
  открытый вопрос).
- Регион без строки в `diagram_type_parts` — просто рисунок/подпись, не привязан.

**Что считается настроенной частью.** Связка возможна только с частью, которая одновременно:

1. есть у устройства — пришла в `device-parts-known` и получила `device_node` (M2.4);
2. заведена в конфигурации — у неё есть строка `device_settings` (M2.4: `arm_mode`,
   `trigger_on`, `alarm_enabled`).

Если части нет в конфигурации, связки нет: реплика не создаётся, состояние в регион не приходит,
регион остаётся нарисованным, но пустым. Тип диаграммы при этом валиден — он описывает полное
устройство, а не конкретную его комплектацию. Если у устройства не настроена ни одна часть из
шаблона, автоматическая диаграмма не создаётся.

**Решение пользователя 2026-11-05:** тип диаграммы может описывать полное устройство и связывать
свои сущности с частями по признакам (имя, индекс, токен); но если часть не заведена в
конфигурации, связки нет и состояние не приходит. Тип не выдумывает части, которых у устройства
нет.

**Автопривязка — часть фичи.** `auto_attach` — обычный флаг типа (по умолчанию `false`,
включается для тех типов, где автоматика уместна). Признак сопоставления по умолчанию — точный
`token`; когда дойдём до реальных камер, нужно попросить пользователя их включить и посмотреть, как
у них идентифицируются реле и сенсоры, чтобы выбрать правило (`token`/`name`/`index`) и, если
надо, поправить дефолт. Ручная привязка работает независимо.

### 3.3. Автоматическая диаграмма и реплики частей

Новая таблица — обратное соответствие «устройство → его диаграмма», как `device_node`:

```sql
CREATE TABLE device_diagram (
  object_id       uuid PRIMARY KEY REFERENCES objects (id) ON DELETE CASCADE,
  source_kind     varchar NOT NULL,
  source_id       uuid    NOT NULL,
  diagram_type_id uuid    NOT NULL REFERENCES diagram_types (id) ON DELETE CASCADE,
  auto_created    boolean NOT NULL DEFAULT false,
  UNIQUE (source_kind, source_id)
);
```

Одна диаграмма на устройство (front/rear — открытый вопрос). `object_id` детерминирован от
`(source_kind, source_id, diagram_type_id)`, как `CameraObjectId`/`device_node`, чтобы повторная
привязка не плодила дубликаты. `auto_created=true` ставит только автоматика; ручная привязка
пишет `false`, и `EnsureAsync` такую диаграмму не трогает (уважает выбор администратора).

`DeviceDiagramService` (VmsMap, рядом с `DeviceNodeService` M2.4) делает одну операцию
`EnsureAsync(sourceKind, sourceId)`:

1. Берёт `device_info`, `device_node` и `device_settings` устройства; если модели нет или не
   настроена ни одна часть — выходит.
2. Если у типа включён `auto_attach`, находит подходящий `diagram_types`; иначе выходит и ждёт
   ручного `AttachAsync`.
3. Создаёт (или обновляет) узел-диаграмму:
   - `objects.parent_id` = канонический узел устройства (камера);
   - `objects.owner_id` = null — это не реплика, а собственный узел;
   - `diagrams.dgr_type` = тип; `diagrams.geometry` = размер бумаги типа;
   - `diagrams.region_id` = null: диаграмма не обязана стоять на карте;
   - имя: `"{device name} / {type name}"`.
4. Для каждой строки `diagram_type_parts` находит часть по правилу `match_by`/`match_value`
   (token > name > index) среди **настроенных** частей (`device_node` + `device_settings`) и
   создаёт/обновляет **реплику**:
   - `objects.parent_id` = узел-диаграмма;
   - `objects.owner_id` = узел части;
   - `diagrams.region_id` = `region_key`;
   - `diagrams.geometry` = null (место задаёт регион);
   - имя = имя части.
   Если правило не нашло настроенную часть — регион остаётся без реплики; это не ошибка.
5. Удаляет реплики, чьих частей больше нет в `device_node`, `device_settings` или
   `diagram_type_parts`.
6. Ничего не делает, если всё уже совпадает (сравнение по owner + region).

Почему это работает без нового кода состояний:

- `DiagramViewer` уже грузит состояния/значения для всех детей диаграммы;
- реплика отвечает состоянием владельца (`StatesUpdateService` резолвит `owner_id`);
- регион показывает цвет/состояние реплики; клик по ребёнку выбирает узел части.

Триггеры: `device-parts-known` (после `DeviceNodeService.EnsureAsync`) и `server-config-changed`
(камера появилась/переименована). Оба идемпотентны; `device-parts-known` приходит раз в 60 с, но
`EnsureAsync` пишет только различия. При выключенном `auto_attach` триггеры ничего не создают:
работает ручной `AttachAsync`.

### 3.4. Ручная привязка и редактор

- **Ручной путь** — для модели, которой нет шаблона, или когда автоматика не сработала: в
  `Admin → Maps` у узла-устройства действие «Add device diagram» → выбор типа (список
  фильтруется по `source_kind`, если тип — шаблон). Создаёт ту же структуру через
  `DeviceDiagramService.AttachAsync` и пишет `auto_created=false`; автоматика такую диаграмму
  не пересоздаёт и не перезаписывает.
- **Редактор типа** (`MapDiagramTypesDialog.tsx` + `DiagramTypeRegionEditor.tsx`):
  - поля `source_kind`, `manufacturer`, `model`, `auto_attach`;
  - для каждого региона — `part_kind`, `match_by` (token/name/index) и `match_value`
    (токен, имя или номер; список токенов подсвечивается, если у выбранной модели есть манифест);
  - предупреждение, если регион не привязан или пара частей дублируется.
- **Редактор диаграммы** (`DiagramViewer.tsx`): автопривязанная диаграмма показывает реплики
  read-only; двигать их между регионами вручную нельзя — источник истины тип. Ручная диаграмма
  (без `device_diagram`) ведёт себя как обычная мнемосхема.

### 3.5. Что автоматика не перезаписывает

- Положение самой диаграммы на карте/плане (если администратор её разместил) — не трогаем.
- Имя диаграммы, заданное вручную, — не перезаписываем после первого создания.
- Реплики, созданные вручную в той же диаграмме, — не удаляем; автоматика управляет только
  репликами, которые сама создала (по `owner_id` из `diagram_type_parts`).
- В регион без настроенной части автоматика не ставит заглушку и не создаёт узел: регион
  остаётся таким, каким его нарисовал тип; состояния в нём нет.
- Тип, удалённый из справочника: `diagrams.dgr_type` становится null по существующему FK
  `ON DELETE SET NULL`; диаграмма остаётся холстом, реплики — как были. Автоматика перестаёт её
  обслуживать; администратор может удалить узел.

## 4. Пример: камера как свитч

Демо-мир M2.4/M2.5 даёт `sim-master` с тремя реле (`lamp`, `peer`, `loop`) и входом `input`.
Тип диаграммы «Camera rear panel»:

- картинка — вид сзади камеры (SVG/PNG), на ней клеммник;
- регионы: `input`, `lamp`, `peer`, `loop` (+ подписи);
- `diagram_type_parts` (по умолчанию точный токен):
  `input → digital_input/input`, `lamp → relay/lamp`, `peer → relay/peer`,
  `loop → relay/loop`; для другой модели те же регионы можно связать по имени или индексу;
- `source_kind='camera'`, `manufacturer='OnvifSim'`, `model='Simulated fixed camera'`,
  `auto_attach=true` — демо проверяет в том числе автопривязку; если автоматика мешает, тип можно
  перевести на ручную (`auto_attach=false` + `AttachAsync`).

Для демо `sim-master` диаграмма создаётся автоматически; в регионах — реплики четырёх частей.
Для этого демо-провижининг M2.4 должен завести `device_settings` для всех четырёх частей: часть
без строки в конфигурации остаётся несвязанной, и её регион пуст — состояния нет.
Переключение реле `peer` в карточке камеры меняет состояние `RELAY_ACTIVE/INACTIVE`, и регион
`peer` на диаграмме загорается. `sim-ptz` (модель `Simulated PTZ camera`) получает свой тип с
одним регионом `input`, если часть настроена. `sim-vehicle` — та же модель, что у `sim-master`, но
у неё нет настроенных частей, поэтому автопривязка её пропускает: ни одна строка
`diagram_type_parts` не находится среди `device_node` + `device_settings`.

Это же работает для свитча/пожарной панели, когда у них появятся `source_kind` и манифест частей:
шаблон не знает, что такое «камера», он знает только `kind`/`token`.

## 5. Этапы (когда дойдём)

1. **Манифест и `device_info`.** VmsOnvif discovery добавляет `manufacturer`/`model`/`firmware`;
   VmsMap пишет `device_info`. Проверка: unit-тест разбора; пустые поля не ломают M2.4.
2. **Схема шаблона.** `diagram_types` (4 колонки), `diagram_type_parts`
   (`match_by`/`match_value`), `device_diagram` в baseline `0000_init.sql` VmsMap; DTO/proto
   (`DiagramType`, `DiagramTypeRegion`); валидация региона/части в `DiagramTypeService`.
   Проверка: миграция на чистой БД, CRUD типа.
3. **`DeviceDiagramService`.** `AttachAsync` и `EnsureAsync` с сопоставлением token/name/index;
   только настроенные части (`device_node` + `device_settings`); реплики с `region_id`;
   идемпотентность, удаление лишних реплик. Дефолт сопоставления — точный `token`; `auto_attach`
   включается у типа. Проверка: unit + Postgres; два вызова не создают дублей;
   добавление/удаление части и настройки отражается.
4. **Редактор.** Поля шаблона и привязка регионов в `MapDiagramTypesDialog`/
   `DiagramTypeRegionEditor`; действие «Add device diagram» у устройства. Проверка: `npm run
   build`, `npm run lint`, ручной сценарий.
5. **Демо.** Тип «Camera rear panel» для `OnvifSim`/`Simulated fixed camera`, `auto_attach=true`;
   `sim-master` создаётся автоматически; проверка состояний реле/входа; при желании — тип для
   `sim-ptz`. Проверка: `check_demo.py` (или ручной сценарий) — диаграмма под камерой, регион
   меняет цвет при переключении реле.
6. **Документация.** `docs/maps-and-plans.md` (диаграмма устройства как узел-холст с репликами),
   README милстоуна, «Ход работы».
7. **Проверка на реальных камерах (перед финальным выбором правила).** Попросить пользователя
   включить реальные камеры; посмотреть, как у них идентифицируются реле и сенсоры
   (`manufacturer`/`model`, токены/имена/индексы), и уточнить дефолт/приоритет сопоставления.
   До этого работает дефолт — точный `token`.

## 6. Проверка

### Unit

- `DeviceModelMatchTests`: точное совпадение, регистронезависимость, пустые поля, несколько
  кандидатов.
- `DiagramTemplateTests`: регион без части, часть без региона, дубликат пары, регион удалён;
  привязка по `token`, `name`, `index`; приоритет token > name > index; конфликт двух регионов на
  одну часть; несуществующая часть.
- `DeviceDiagramServiceTests`: идемпотентный `EnsureAsync`; один `device_diagram` на устройство;
  добавление/удаление части; реплика в нужном регионе; состояния реплики резолвятся владельцем;
  часть без строки `device_settings` не связывается и не даёт состояния; удаление устройства
  каскадом.
- `MapDiagramTypesDialog` — ручной сценарий; отдельных frontend-тестов на компонент нет.

### Integration (Postgres)

- `device_diagram` unique `(source_kind, source_id)`; `diagram_type_parts` FK на регион.
- Автопривязка двух камер одной модели даёт две диаграммы с независимыми репликами.
- Часть есть в `device-parts-known`, но не в `device_settings`: реплики нет, состояние в регион
  не приходит; после добавления строки реплика появляется при следующем `EnsureAsync`.
- `GetDiagramContent` отдаёт диаграмму и её детей; `GetVisualStates` по детям возвращает
  состояния владельцев.

### Demo / ручная проверка

- `sim-master` → «Camera rear panel»: четыре региона, состояния `RELAY_*`/`SENSOR_*` совпадают с
  карточкой устройства.
- Переключение `peer`/`lamp` в UI меняет регион без перезагрузки страницы (SSE `api/map/live`).
- Клик по региону выбирает узел части; открываются её события.

## 7. Открытые вопросы

- **Одна диаграмма на устройство или несколько?** Сейчас `UNIQUE (source_kind, source_id)`;
  front/rear — это два типа или два экземпляра? Если несколько, убрать уникальность и добавить
  `slot`/`name`.
- **Где живёт диаграмма по умолчанию?** Предложение: под узлом устройства, не на карте; при
  желании администратор ставит её на Space. Стоит ли показывать её в `Nodes` всегда или только
  при раскрытии устройства?
- **Какие признаки реально отдают камеры?** Это главный открытый вопрос для правила
  сопоставления: `manufacturer`/`model` у реальных камер, токены/имена/индексы частей,
  стабильность строк между прошивками. Проверяем на реальных камерах — попросить пользователя их
  включить; до этого дефолт — точный `token`.
- **Точное совпадение модели или шаблоны?** Прошивки и ревизии меняют строку; возможно,
  `device_model` должен поддерживать `*` или префикс. Тоже ждёт реальных камер.
- **Токены частей у разных ревизий.** `input`/`relay1` могут отличаться; нужен ли per-device
  override или отдельный тип на ревизию.
- **Признак связи: token, имя или индекс.** Токен надёжен, но нестабилен между ревизиями; имя
  задаёт администратор и оно может быть пустым/неуникальным; индекс зависит от порядка в
  манифесте. Нужно решить: какой признак считать основным, как хранить стабильный `ordinal`
  (в `device-parts-known`/`device_node` или сортировать по токену) и что делать при конфликте.
- **Имя для сопоставления.** `device_settings.name` (администратор) или `name` из
  `device-parts-known` (интеграция)? Если администратор переименовал часть, должна ли связка
  по имени сломаться? Предложение: `device_settings.name`, если задано, иначе манифест.
- **Части, которых нет в манифесте или конфигурации.** Пропускать (как предложено) или
  показывать пустой слот с подписью «нет устройства»? Предложение: регион остаётся пустым,
  без выдуманной сущности и без состояния; подпись — только если её нарисовал тип.
- **Значения, а не только состояния.** Регион может показывать температуру/напряжение; в M2.6
  только состояния, значения — later.
- **Автопривязка для всех камер модели.** Если у модели есть тип, но у конкретной камеры нет
  ни одной части из шаблона — создавать пустую диаграмму или пропускать? Предложение:
  пропускать, если не совпала ни одна часть.
- **Ручные правки автодиаграммы.** Разрешать переименование/перемещение реплик или считать тип
  единственным источником истины? Предложение: read-only дети, двигать можно только саму
  диаграмму.
- **Мультиустройство.** Диаграмма свитча, на которой камеры — это отдельный уровень; в M2.6 не
  решаем.

## 8. Что не входит

- **DSL описания устройств.** Пользовательский язык «вот камера, вот её части» — future; сейчас
  типизированный манифест M2.4 + шаблон типа.
- **Автогенерация картинки** панели по манифесту — рисует человек; M2.6 только привязывает
  регионы.
- **Пожарная панель и другие классы устройств** — `fire-alarm-integration.md`; механизм шаблона
  к ним применим, но их части/состояния появятся позже.
- **Части, кроме `digital_input`/`relay`** (потоки, питание, вентиляторы) — по мере появления в
  `device_node`.
- **Значения/телеметрия в регионах** — состояниями M2.6 ограничивается.
- **Полный визуальный редактор шаблонов** — M2.6 даёт поля и привязку регионов, не «рисовалку»
  устройств.

## 9. Ход работы

Записано 2026-11-05 как низкоприоритетный концепт. Не начато. Зависит от M2.4 (части и
`device_node`) и M2.5 (демо-пары). Уточнение 2026-11-05: тип может описывать полное устройство,
связка — по токену/имени/индексу, но только с частями, заведёнными в конфигурации; иначе региона
без состояния. **Правило сопоставления проверим на реальных камерах:** когда дойдём до выбора
признака, попросить пользователя включить реальные камеры и посмотреть, как у них идентифицируются
реле и сенсоры; до этого работает дефолт — точный `token`. Автопривязка при этом делается и
тестируется на демо. При старте — отдельная сессия планирования: уточнить открытые вопросы выше,
затем детализировать шаги.
