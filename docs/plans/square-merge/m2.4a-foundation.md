# M2.4a — Фундамент: baseline БД, UUID и `device_node`

> Подплан [M2.4](m2.4-devices-alarms-automation.md). Ветка `square-merge/m2.4a-foundation`
> от `master`. Предыдущий подплан не требуется.
>
> **Результат:** камера и её части корректно представлены в дереве под узлом сервера; карта и план
> показывают реплики; у порта в демо нет тревоги; у каждого сервиса ровно один baseline-файл схемы,
> БД пересоздаётся с нуля.

Это инфраструктурный подплан, а не функциональный: он не добавляет ни датчиков, ни тревог. Его
смысл — закончить смену идентификаторов, реестра узлов и места канонического узла в дереве
отдельно, чтобы следующие подпланы не смешивали механическую правку с бизнес-логикой. Шаг 0 —
простая уборка, которая не должна ждать фундамента.

## Шаг 2. ✅ `device_node` вместо `camera_node`

Схема (в `dotnet/VmsMap/Grpc/migrations/0000_init.sql`):

```sql
CREATE TABLE device_node (
  object_id   uuid PRIMARY KEY REFERENCES objects(id) ON DELETE CASCADE,
  source_kind varchar NOT NULL,   -- 'camera' сегодня
  source_id   uuid NOT NULL,      -- camera_id
  part_kind   varchar NOT NULL,   -- 'device' — камера целиком; 'digital_input'/'relay' — часть
  part_token  varchar NOT NULL,   -- token части; '' для устройства целиком
  UNIQUE (source_kind, source_id, part_kind, part_token)
);
```

- `object_id` детерминирован:
  `ObjectIdGenerator.GenerateObjectId($"{sourceKind}|{sourceId}|{partKind}|{partToken}", "device_node")`.
  Обратно id не читается — реестр и есть обратный поиск.
- **Один вывод id на всё.** Сегодня `CameraObjectId.For(cameraId)` считает id версией `"camera"`;
  если камера в `device_node` будет считаться новой формулой, у неё окажется два разных узла.
  Поэтому вводится `DeviceObjectId.For(sourceKind, sourceId, partKind, partToken)`, а
  `CameraObjectId.For(cameraId)` делегирует в него как `("camera", cameraId, "device", "")`.
  Старая версия `"camera"` удаляется целиком. БД пересоздаётся, так что смена id безопасна.
  Проверка: `grep -rn 'GenerateObjectId(.*"camera"'` пуст, и тест доказывает, что
  `CameraObjectId.For(x) == DeviceObjectId.For("camera", x, "device", "")`.
- Камера — строка `part_kind='device'`; части — `digital_input`/`relay`. Общий ключ нужен, чтобы
  будущий адаптер пожарной панели не заводил второй реестр.
- Код VmsMap переводится с `CameraNode` на `DeviceNode` с условием
  `source_kind='camera' AND part_kind='device'`. Полный список файлов — результат
  `grep -rn 'camera_node\|CameraNodes\|DBCameraNode' dotnet`; основные: `Db/PgDbContext.cs`,
  `Db/Models/Spatial/DBCameraNode.cs` → `DBDeviceNode.cs`, `Clients/ICameraNodeService.cs`,
  `Db/Services/CameraIdLookup.cs`, `NodeKindLookup.cs`, `RightsService.cs`, `SpatialDb.cs`,
  `Adapter/CameraNodeService.cs`, `Adapter/AlarmService.cs`, `Demo/DemoSeeder.cs`,
  `Demo/DemoValueFeeder.cs`, `Grpc/MapServiceImpl.Reads.cs`, `Grpc/MapServiceImpl.Rights.cs`, тесты.
  Это механическая правка в одном сервисе; внешние контракты не меняются.
- `NodeKind.Part` добавляется в `dotnet/VmsMap/Domain/Rights/RightActions.cs`; `NodeKindLookup`
  отвечает `Part` по строке `device_node` (камера — `Camera`).
- Удаление камеры удаляет поддерево частей; `device_node` — каскадом по `object_id`.
- **`StartupResyncService`** сейчас берёт все камеры одним `ListAsync(null)` и обрабатывает по
  одной; при 100 000 камер это один огромный ответ и 100 000 последовательных
  `EnsureCameraAsync`. Перевести на пакеты (например, по 500) и разумный параллелизм; сбой одной
  камеры не отменяет обход (инвариант 21).

**Проверка:**
- `dotnet test dotnet/VmsMap.Tests`: узлы и реплики камер читаются, права, `GetByIds` и
  `GetVisualStates` не меняются.
- Тест «нет второго допущения»: grep по `camera_node`/`CameraNode` пуст, и тест доказывает, что
  узел части (`part_kind='digital_input'`) не считается узлом камеры ни в `CameraIdLookup`, ни в
  `NodeKindLookup`, ни в `RightsService`.
- Тест удаления: камера с двумя узлами частей удаляется — не остаётся ни `objects`, ни
  `device_node`, ни состояний, ни событий, ни тревог этих узлов.
- Тест неразмещённой части: узел `device_node` создан без `geo_objects`/`camera_placement`,
  `GetVisualStates` отдаёт его состояния, `GetEventsByFilter` — его события, геометрии нет.

## Шаг 3. ✅ Канонический узел — всегда под сервером, размещение — реплика

Сейчас размещённая камера переезжает под пространство своего опорного размещения: канонический
узел **и есть** то, что нарисовано на карте (`SpatialDb.UpsertPlacementAsync`, ветка `isReference`). Для
M2.4 это не годится: узлы датчиков оказались бы разбросаны по ветвям карт, а каноническое дерево
устройства должно быть одним.

Новая модель (решение пользователя, 2026-11-06):

```
server                          карты и планы — отдельная ветвь
  └── camera  (канонический)      map
       ├── digital_input            └── camera (реплика, owner_id → канонический)
       └── relay                         └── camera (реплика) …
```

Файлы: `dotnet/VmsMap/Adapter/CameraNodeService.cs`, `dotnet/VmsMap/Db/Services/SpatialDb.cs`,
`dotnet/VmsMap/Grpc/MapServiceImpl.Rights.cs`, `dotnet/VmsMap.Tests/*`, `CLAUDE.md`,
`docs/future_plans/devices-and-nodes.md`.

- **`CameraNodeService.EnsureCameraAsync`** — родитель всегда узел сервера
  (`EnsureServerAsync(camera.ServerId)`); поиск опорного размещения для выбора родителя убирается.
  `ReconcileParentAsync` становится тем же вызовом: возвращать узел «на место» больше не нужно.
- **`SpatialDb.UpsertPlacementAsync`, ветка `isReference`** — не двигает канонический узел и не
  вешает на него `camera_placement`/`geo_objects`. Вместо этого:
  - на пространстве создаётся (или переиспользуется) реплика камеры, и её строка
    `camera_placement` получает `is_reference = true`;
  - прежняя опорная реплика на другом холсте остаётся обычной картинкой (`is_reference = false`),
    её рисунок не трогается;
  - если на целевом пространстве уже есть картинка этой камеры, опорной становится она, а не
    новая реплика.
  Логика `canonicalCanvas` («куда вернуть камеру, когда она уедет») удаляется: канонический узел
  никуда не уезжает.
- **Вид принадлежит реплике.** `visual` и `geo_objects` создаются на реплике; у канонического
  узла их нет вовсе. Одна и та же камера может выглядеть по-разному на карте, плане и диаграмме —
  состояние у них общее (от владельца), вид свой. Строка `camera_placement` есть только у
  географических холстов: у реплики на диаграмме её нет, поэтому калибровки и наведение на неё
  не опираются. Камера, размещённая только на диаграмме, опорного размещения не имеет —
  наведение недоступно, пока её не поставят на карту или план.
- **`SpatialDb.RemoveSpaceAsync`** — опорные строки теперь принадлежат репликам внутри поддерева и
  удаляются вместе с ним; цикл, который снимал родителя и рисунок у канонического узла, убирается.
  Камера без опорной реплики остаётся в дереве под сервером, просто без позиции (наведение
  недоступно) — как и сегодня после снятия с карты.
- **`SpatialDb.RemovePlacementAsync`** — ветка, возвращавшая канонический узел на место после
  снятия размещения (`:546`), становится мёртвой и удаляется: снимается реплика, узел не двигается.
- **Права якорятся на пространство.** `RightsService.AllowedAsync` идёт **вверх** по `parent_id` и
  `owner_id`; канонический узел под сервером до пространства не доходит, поэтому пользователь с
  `view` на `space/umd` перестал бы видеть тревоги устройств (а в enforced-режиме — и сами узлы).
  Правило: для узла устройства (камеры или части — часть разрешается через камеру) проверка прав
  начинается от **опорной реплики** и её пространства; опорной нет — от узла сервера. Разрешение
  кэшируется по узлу. Демо выдаёт `view` на `space/umd`, поэтому тест «тревога части видна с
  правами пространства» обязателен.
- **`GetCameraNode` — удалить.** Вызовов нет ни в одном сервисе и ни во фронтенде; его контракт
  («канонический узел камеры для редактора прав») держится на том, что id камеры ≠ id узла, а это
  теперь выражается через `device_node`, не через RPC. После переноса эталона на реплику он к тому
  же отдаёт узел без геометрии — не то, что нужно карте. Удаляются RPC и `GetCameraNodeResponse`
  из `vms_map.proto` (без `reserved`), реализация в `MapServiceImpl.Rights.cs` и строка про его
  контракт в `docs/plans/square-merge/m4-frontend.md`. Если редактору прав понадобится
  «камера → канонический узел», это будет отдельный узкий запрос по `device_node`.
- **Удаление** — `RemoveCameraAsync` уже сносит канонический узел, все реплики по `owner_id`,
  строки `camera_placement`, `ptz_geo_observations` и `ground_observations`; поведение
  сохраняется и покрывается тестом. Вопросов пользователю не задаём: пересоздание камеры даёт
  новый GUID, старое дерево удаляется целиком.
- **`docs/future_plans/devices-and-nodes.md`** — инвариант «привязки живут только на каноническом
  узле, реплика не может нести эталон» отменяется: эталон теперь несёт реплика. Файл сокращается
  до того, что осталось открытым.
- **`CLAUDE.md`** — фраза «the adapter creates the canonical node … under the space of its
  reference placement» заменяется новой моделью.
- **Что это не ломает.** Вся привязка железа идёт по `camera_id`, id узла в ней не участвует:
  `PlacedReferenceAsync`/`GetCameraSpatialModelAsync`, `MoveReferencePointAsync`,
  `ptz_geo_observation`/`ground_observation` (ключ `(camera_id, landmark_id)`), уникальность
  эталона держит `idx_camera_placement_reference`. Поэтому наведение и калибровки продолжают
  работать, когда эталон принадлежит реплике.
- **Клиент.** `MapsOperatorPanel.nodeForPlacement` и `SpaceEditor` сейчас выводят «эталон = маркер
  без `owner_id`» (`p.isReference ? !m.ownerId : !!m.ownerId`). После переноса эталона на реплику
  это неверно: и эталон, и картинка — реплики, различает их только `isReference`. Те же формулы
  проверить по всему `web_srv.client`.
- **Размещение частей** в M2.4 не появляется: палитра `Devices` ставит на карту камеры, реплики
  частей — M2.6 и `generic-device-placement.md`. Модель их допускает, UI — нет.

**Проверка:**
- `CameraNodeServiceTests`: размещённая камера остаётся под узлом сервера; неразмещённая — тоже;
  переименование обновляет канонический узел.
- `SpatialDbTests`/`SpatialPostgresTests`: первое размещение создаёт реплику с `is_reference=true`,
  у канонического узла нет ни `geo_objects`, ни строки размещения; размещение на втором холсте
  оставляет прежнюю опорную реплику картинкой; удаление карты убирает реплики, а камера остаётся
  под сервером; удаление камеры не оставляет ни узлов, ни реплик, ни размещений, ни наблюдений.
- Живая проверка: демо-камера на карте — это реплика; в дереве она под сервером, а не под
  пространством.
- Тест вида: у канонического узла нет `visual`/`geo_objects`; у двух реплик одной камеры (карта и
  диаграмма) вид разный, а состояния, события и права читаются одни и те же.
- Тест прав: `view` на пространстве опорной реплики даёт доступ к узлу камеры и её части; без
  опорной реплики действуют права узла сервера; admin обходит и то и другое.
- Тест снятия размещения: `RemovePlacementAsync` убирает реплику, канонический узел остаётся под
  сервером и не меняет родителя.

## Ход работы

**2026-11-06, база ветки.** `master` не содержит закрытый M2.3 (39 коммитов: `DemoTelemetry`,
`DemoValueFeeder`, живой `check_demo.py`). Резать буквально от `master` значило бы переписывать шаг 0
под код до M2.3, поэтому ветка `square-merge/m2.4a-foundation` отрезана от тип-а
`square-merge/m2.3-onvif-live-parameters` (решение пользователя). Ветку M2.3 при выпуске нужно
влить в `master` раньше M2.4a.

**Шаг 0.** Порт — `CONNECTED`: строка остаётся, потому что `DemoSeeder` не чистит старые состояния,
и `CONNECTED` перезаписывает набор, оставленный миром версии 5. `DemoWorldTests` переименован в
`ThePortIsCalmAndTheLevelsArePartOfTheWorld`. `check_demo.py`: `check_alarm` заменён на
`check_port_not_alarmed` — состояние порта читается через `POST /api/map/states`, список тревожных
узлов (`POST /api/map/states/alarmed`) не должен содержать порт. Камеры могут быть
`DISCONNECTED` законно, поэтому проверяется именно порт. `demo-gui-parity.md` больше не называет
порт синтетической тревогой.

**Шаг 1, baseline.** Девять миграций VmsCfg, одна VmsFs, семь VmsMap и две VmsAnalyticsSingleton
свёрнуты в `0000_init.sql` каждого сервиса; старые файлы удалены. Свёртка проверена не на глаз:
каждый baseline и старый набор применены к разным БД одного Postgres, и сравнены
`information_schema.columns`, индексы и `pg_constraint` — различия только в типах id и одном
добавленном индексе (`idx_camera_setup_name`, для `ORDER BY name` при 100 000 камер). В VmsFs и
VmsAnalytics удалённые в старых миграциях `ALTER` слиты в `CREATE TABLE` (например,
`detection_embeddings.model`), в VmsMap `diagrams.dgr_type` сразу объявлен `ON DELETE SET NULL`.

**Шаг 1, защита мигратора.** `VmsDbMigrator` видит `0000_init.sql` в каталоге миграций, не находит
его в `schema_migrations` и, если в `public` есть хоть одна таблица кроме `schema_migrations`,
падает с `InvalidOperationException`: «database '<name>' has tables but no '0000_init.sql' baseline
— its schema predates the baseline … Recreate the database». Проверено на двух БД: со старой
таблицей — отказ, на пустой — миграция и запись `0000_init.sql` в `schema_migrations`.

**Шаг 1, UUID.** В `ta_cfg` — `camera_setup.camera_id` и `storage.storage_id` плюс все FK на них
(`camera_stream`, `camera_storage`, `camera_schedule`, `monitor_camera`, `monitor_slot`,
`onvif_*`, `camera_states`, `ptz_*`, `analytics_watch`); в `ta_fs` — `camera_id` в `clips`,
`retention_events`, `source_outages`, `edge_import_jobs`, `clip_metadata_chunks` и
`clips.storage_id`; в `ta_map` — `camera_placement`, `camera_node`, `ptz_geo_observation`,
`ground_observation`; в `ta_analytics` — `detections.camera_id`/`storage_id`. Деньги на проводе не
менялись: proto, DTO и JSON по-прежнему несут id строкой. Преобразование живёт на границе БД —
EF-конвертер `string ↔ uuid` в `VmsCfgDbContext`, `ClipsDbContext`, `VmsMapDbContext`,
`AnalyticsDbContext` (одно место вместо правки сотен вызовов), а в сыром SQL — `$n::uuid` в
параметрах и `::text`/`cast` в выборках. `clips.storage_id` и `detections.storage_id` стали
`uuid NULL`: пустая строка означала «без хранилища», теперь это NULL (на проводе у `Recording`
остался `''`). Демо и стенд получают id своим путём: `DemoIds.Camera(name)` в VmsMap и такой же
`DemoCameraIds.For(name)` в VmsCfg (два процесса, общего проекта нет — namespace и версия UUIDv5
закреплены тестами с обеих сторон одним и тем же значением), а `check_demo.py` и
`onvifsim_lab.py` считают тот же UUIDv5 в Python. Видеостена в VmsCfg ищет камеры по этим id, а не
по именам. Идентификатор default-хранилища — фиксированный UUID
`00000000-0000-0000-0000-0000000000d1`; в редакторе хранилищ поле id убрано, новый id сервер
выдаёт сам, а подпись строки — `root_path`.

**Шаг 1, что проверено живьём.** Базы `ta_cfg`, `ta_fs`, `ta_map`, `ta_analytics`, `ta_state`
удалены и созданы заново `db-init`; dev-стек поднят с нуля, все 13 процессов слушают, в
`schema_migrations` каждых четырёх — ровно `0000_init.sql`. `check_demo.py --provision-cameras`
проходит полностью (установка, повторная установка без изменений, удаление, реле, лампа,
телеметрия, порт без тревоги). Стенд: `onvifsim_lab.py --world maryland provision` и `calibrate`
проходят — значит, наведение и калибровки читают по `camera_id` и после переноса FK в uuid. Через
gRPC VmsFs отдельно проверены `IngestClip` (со storage и без), `RetainEvent`, `ListRetentionEvents`,
`GetRecordings`, `GetClipsForEvent`, `ReportSourceLiveness`/`ListSourceOutages`, а также запись
`clip_metadata_chunks`; через API — расписания камер, analytics-watch, PTZ-политика и `armed`.
Найдено и исправлено по ходу: `DbClip.StorageId` был ненулевым `string`, EF звал `GetGuid` на
NULL-колонке — свойство стало `string?` с `NULL ↔ ""` на границе. Удаление демо передавало имя
камеры вместо её id — исправлено в `DemoSeeder.DeleteAsync`.

**Шаг 1, находка.** На первой установке демо после пересоздания БД VmsMap один раз залогировал
`duplicate key … objects_pkey`: узел сервера/камеры создавали одновременно подписчик
`server-config-changed` и сидер демо, а `MapDb.UpdateHierarchyAsync` вставляет без upsert. Dapr
повторил сообщение, установка продолжилась; на повторных установках не воспроизводится. Записано
будущим планом, чинить вместе с пакетным resync шага 2; исправлено там же (см. «Шаг 2»).

**Шаг 2, реестр.** `camera_node` заменён на `device_node` (`object_id`, `source_kind`, `source_id`,
`part_kind`, `part_token`, уникальный ключ на четыре последних); `source_id` — `uuid`, как и
камера в VmsCfg. `DBCameraNode` стал `DBDeviceNode`, `CameraNodeService`/`ICameraNodeService` —
`DeviceNodeService`/`IDeviceNodeService`, `DbSet.CameraNodes` — `DeviceNodes`. Все чтения, которым
нужна камера, фильтруют `source_kind='camera' AND part_kind='device'` (`CameraIdLookup`,
`NodeKindLookup`, `RightsService.GetEffectiveAsync`, `AlarmService`, `DemoSeeder`,
`DemoValueFeeder`, `MapServiceImpl.GetCameraNode`, `RemoveUnknownAsync`). `grep` по
`camera_node`/`CameraNode`/`DBCameraNode` в коде пуст; единственное, что ещё носит это имя, —
RPC `GetCameraNode` и его сообщения, которые по плану удаляются на шаге 3. Заодно переименована
приватная константа VmsCfg `CameraNodeVersionKey` → `CamNodeVersionKey`: ключ в state store
`cam-node-version` не менялся, но имя метода больше не путается с удалённой таблицей.

**Шаг 2, один вывод id.** `DeviceObjectId.For(sourceKind, sourceId, partKind, partToken)` —
`GenerateObjectId($"{sourceKind}|{sourceId}|{partKind}|{partToken}", "device_node")`;
`CameraObjectId.For(cameraId)` делегирует в него как `("camera", id, "device", "")`. Тест
`ACameraHasOneDerivationWhateverTheSpelling` доказывает равенство и то, что у части id другой.
Старая версия `"camera"` удалена; узлы после пересоздания БД новые, как и предполагалось.

**Шаг 2, вид узла.** `NodeKind.Part` добавлен; `NodeKindLookup` отвечает `Camera` только на строку
`part_kind='device'` и `Part` — на остальные строки реестра (и на строки размещения у снимков), так
что часть не считается камерой ни в `CameraIdLookup`, ни в правах (`camera_id` у такой строки
`null`), ни в тревожном обходе. Набор действий части — `[View, Edit, ViewLive, Control]`;
`Acknowledge` придёт с сущностью тревоги в M2.4c, а не заводится заранее. Клиент знает вид
`part`: порядок в `KIND_ORDER` и подписи в en/es.

**Шаг 2, удаление и чтение части.** `RemoveCameraAsync` сносит строки реестра всей камеры
(`source_kind='camera' AND source_id=camera_id`, части включены) и через `MapUpdateService.Delete`
— поддерево объектов; в Postgres это каскадом уносит `device_node`, состояния, события и тревоги.
Тест на Postgres `DeletingACameraTakesItsPartsTheirStatesEventsAndAlarms` это проверяет; тест на
in-memory — что не остаётся ни узлов, ни строк реестра. Второй тест
(`APartWithoutGeometryIsReadLikeAnyNode`) доказывает, что у части без `geo_objects` и
`camera_placement` `GetVisualStates` отдаёт её состояния, а `GetEventsByFilter` — её события.

**Шаг 2, resync.** `StartupResyncService` идёт по камерам волнами по 500 с параллелизмом 4;
каждая камера берёт свой scope и `DbContext`, сбой одной логируется и не отменяет обход — её id
остаётся в `known`, поэтому удалённой она не считается. Каталог по-прежнему отдаёт весь список
одним RPC `ListCameras`: страницы в этом контракте нет, а его потребители — все сервисы, поэтому
это отдельная задача, а не правка шага 2.

**Шаг 2, гонка вставки узла — исправлена, а не отложена.** Параллельный resync сделал
найденную на шаге 1 гонку систематической: пять камер одновременно заводили один узел сервера.
`MapDb.UpdateHierarchyAsync` теперь вставляет новый узел одним `INSERT … ON CONFLICT (id) DO
UPDATE` (для реляционных провайдеров; in-memory остаётся прежним путём), поэтому «прочитал —
вставил» больше не оставляет окна. Заведённый на шаге 1 future-план по этой гонке удалён. Проверено:
на пересозданной `ta_map` после старта — 0 ошибок в логе, 5 строк `device_node`, 6 объектов.

**Шаг 3, канонический узел.** `DeviceNodeService.EnsureCameraAsync` больше не ищет опорное
размещение: родитель всегда узел сервера (`ServerNodeId.For`, вынесен в `Domain/ServerNodeId.cs`
и общий с `SpatialDb`). `ReconcileParentAsync` — тот же вызов. `SpatialDb.EnsureCanonicalNodeAsync`
создаёт канонический узел под сервером, если размещение пришло раньше адаптера.

**Шаг 3, размещение — реплика.** `SpatialDb.UpsertPlacementAsync` переписан: канонический узел не
двигается, `camera_placement` и `geo_objects` вешаются только на реплику. Первое размещение
создаёт реплику и делает её опорной; если на целевом холсте уже есть картинка камеры, опорной
становится она, а не новая реплика. Старая опорная реплика остаётся картинкой с прежним рисунком;
флаг снимается отдельным `SaveChanges` до назначения нового, иначе частичный уникальный индекс
`idx_camera_placement_reference` может увидеть две опорные строки одной камеры. Логика
`canonicalCanvas` и `CreatePictureAsync` удалены. `RemovePlacementAsync` теперь только снимает
реплику (удаляет её узел, строку и точку) — мёртвая ветка «вернуть канонический узел на место»
ушла. `RemoveSpaceAsync` снимает строки размещения и рисунки поддерева, не трогая родителя
канонического узла: камера без опорной реплики остаётся под сервером. Комментарий
`MoveReferencePointAsync` поправлен: точка двигается у опорной реплики.

**Шаг 3, права.** `RightsService.AllowedAsync` разложен на `WalkAsync` (прежний обход по
`parent_id` и `owner_id`) и якорь: для узла устройства (`device_node`, часть — через тот же
`source_id`) добавляется обход от его **опорной реплики**, её пространства и предков. Своего
обхода узла это не отменяет — право, выданное прямо на каноническом узле, по-прежнему
действует; при отсутствии опорной реплики остаётся только путь камеры к серверу, что и есть
«якорь — узел сервера». `GetEffectiveAsync` распространяет права ещё и от реплики к её владельцу:
право, выданное на пространство, доходит до реплики, от неё — до канонического узла и его частей.
Тесты: `ADeviceIsAllowedWhatItsReferenceReplicaIsAllowed` (view на пространстве даёт доступ к
камере и её входу; без опорной реплики — нет; право на узле сервера работает; admin обходит) и
`TheViewBelongsToTheReplicaAndTheMeaningDoesNot` (у канонического узла нет `visual` и
`geo_objects`; у двух реплик разный вид; состояния и события у них общие).

**Шаг 3, `GetCameraNode`.** RPC и `GetCameraNodeResponse` удалены из `vms_map.proto` (без
`reserved`), реализация — из `MapServiceImpl.Rights.cs`, строка о его контракте — из
`m4-frontend.md`. Ни один сервис и ни один клиент его не вызывал.

**Шаг 3, клиент.** Формулы `p.isReference ? !m.ownerId : !!m.ownerId` действительно неверны, но
различать эталон и картинку по узлу не нужно вовсе: на одном холсте у камеры не больше одного
размещения, и узел размещения — всегда реплика. В `MapsOperatorPanel`, `SpaceEditor`,
`mapEditsSlice.movePlacedCamera` и `objectsSlice.resolveCameraNode` теперь выбирается маркер с
`ownerId` (реплика), с прежним запасным вариантом «любой узел этой камеры»; неиспользуемый
параметр `isReference` у `movePlacedCamera` убран. `tsc --noEmit` чист.

**Шаг 3, проверено.** `dotnet test dotnet/VmsMap.Tests` — 137 тестов, включая Postgres. Живьём:
`ta_map` пересоздана, dev-стек поднят; `check_demo.py` проходит полностью; `onvifsim_lab.py
--world maryland provision` и `calibrate` проходят — наведение и калибровки читают опорную
реплику по `camera_id`. SQL-проверка на живой базе: все пять камер — под узлом `vms`; у
канонических узлов 0 строк `geo_objects` и 0 строк `camera_placement`; все размещения
принадлежат узлам с `owner_id`.
