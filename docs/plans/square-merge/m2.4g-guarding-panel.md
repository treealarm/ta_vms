# M2.4g — Операторская панель «Охрана»

> Подплан [M2.4](m2.4-devices-alarms-automation.md), после [M2.4f](m2.4f-operator-arming.md).
> Ветка `m2.4g-guarding-panel` от `master`.
>
> **Результат:** у оператора есть отдельная вкладка «Охрана»: список датчиков выбранного
> пространства (и всего, что под ним) с тумблерами постановки/снятия, с подписью **фактического**
> источника охраны и с фильтром по правам. Список серверный и постраничный — при 100 000 камер в
> браузер уходит одна страница, а не весь парк. Тумблер пишет через уже существующий
> `PUT .../digital-inputs/{token}/arm-mode` (`SetDeviceArmMode`), поэтому новых путей записи не
> появляется. Попутно исправляется вторая половина картины: тревога датчика поднимается до
> **помещения**, в котором стоит камера, а не только по каноническому дереву под сервером.

## Решения (2026-11-12)

- **Панель — отдельная вкладка оператора**, а не ещё один ряд в оверлее Device I/O. Решение
  пользователя записано в [20-zone-arming.md](../../future_plans/20-zone-arming.md): охрана
  датчика была спрятана среди реле, а это операторская работа, а не настройка.
- **Список серверный.** Браузер не перечисляет камеры и не опрашивает их по одной: VmsMap отдаёт
  страницу датчиков уже отфильтрованной по пространству и правам.
- **Строка списка — обнаруженный цифровой вход** (`device_node`: `source_kind='camera'`,
  `part_kind='digital_input'`), а не строка настроек VmsCfg: физический датчик существует и до
  того, как администратор его настроил. Настройки (имя, режим, флаг тревоги) приходят из VmsCfg
  пачкой на страницу; у ненастроенного входа `configured=false`, тумблер неактивен.
- **Пространство — поддерево.** Фильтр `space_id` включает само пространство и все вложенные
  планы/диаграммы: это ровно те датчики, на которые может подействовать свойство `armed`
  этого пространства (`EffectiveArmingResolver` идёт вверх по предкам опорной реплики). Так же
  ведут себя права: право на пространство наследуется вниз.
- **Контракт сразу не камерный.** Адресация строки — `source_kind`/`source_id`/`part_kind`/
  `part_token`, как у `GetDevicePartArming`. Камера сегодня — частный случай
  `source_kind='camera'`; пожарная панель и её шлейфы придут тем же RPC. Запрос уже принимает
  `space_id`, а зона позже добавится полигоном в том же сообщении (как `Box.zone` у `GetByBox`),
  вторым RPC она не станет.
- **Пагинация — keyset по `(имя, id)` с `has_more`**, без `total`: права режут строки после
  выборки, поэтому честного общего числа нет, а смещение по страницам «прыгало» бы при каждой
  смене охраны. Догрузка идёт кусками, пока страница не наберётся или не кончится выборка.
- **Запись — существующая команда.** Панель вызывает тот же `SetDeviceArmMode`; `inherit` —
  админская настройка, оператор её не пишет. Без права `control` тумблер неактивен, но граница —
  серверный `[RequiresRight(Control)]`, а не флаг UI.
- **Права чтения — `view_live`**, как у списка digital inputs камеры. VmsMap применяет их сам, на
  том же дереве, и отдаёт `can_control` для UI.

## Часть A. Список датчиков

### 1. VmsCfg — пачечные чтения

Список не может ходить в VmsCfg по камере: страница из 50 датчиков — это 50+ gRPC-вызовов.

`proto/vms_cfg.proto`:

```proto
rpc ListDeviceSettingsForCameras(ListDeviceSettingsForCamerasRequest)
    returns (ListDeviceSettingsResponse);
rpc GetCamStates(GetCamStatesRequest) returns (GetCamStatesResponse);

message ListDeviceSettingsForCamerasRequest {
  repeated string camera_ids = 1;
}

message GetCamStatesRequest  { repeated string camera_ids = 1; }
message GetCamStatesResponse { repeated CameraArmState states = 1; }
message CameraArmState {
  string camera_id = 1;
  bool   armed     = 2;
}
```

- `DeviceStorage.ListManyAsync(cameraIds)` — один `WHERE camera_id = ANY(...)`, те же поля, что у
  `ListAsync`; пустой список и не-UUID отсекаются до запроса.
- `CameraStorage.GetCamStatesAsync(cameraIds)` — `SELECT camera_id, armed FROM camera_states
  WHERE camera_id = ANY(...)`. Отсутствие строки — это `armed=false`, как у `GetCameraArmedAsync`.
- Обработчики — тонкие, как `ListDeviceSettings`/`GetCamState`; права у VmsCfg не проверяются
  (их проверяет вызывающий, сегодня это только VmsMap).

### 2. VmsMap — RPC списка

`proto/vms_map.proto`:

```proto
rpc ListGuardSensors(ListGuardSensorsRequest) returns (ListGuardSensorsResponse);

message ListGuardSensorsRequest {
  // Пусто — всё, что вызывающий вправе видеть; иначе это пространство и всё под ним.
  string space_id  = 1;
  int32  page_size = 2;   // 0 — умолчание сервера (50), не больше 200
  GuardSensorCursor after = 3;
  Caller caller    = 4;
}

message GuardSensorCursor {
  string after_name = 1;  // имя узла датчика
  string after_id   = 2;  // id узла — разрешает одноимённые
}

message GuardSensor {
  string source_kind = 1;  // "camera" сегодня
  string source_id   = 2;  // id камеры в VmsCfg
  string part_kind   = 3;  // "digital_input"
  string part_token  = 4;
  string object_id   = 5;  // узел части в дереве
  string name        = 6;  // имя узла части (из настроек либо "камера / token")
  string camera_name = 7;  // имя канонического узла камеры
  string space_id    = 8;  // ближайший холст опорной реплики
  string space_name  = 9;
  string arm_mode    = 10; // "inherit"|"armed"|"disarmed"; "" — вход не настроен
  bool   alarm_enabled = 11;
  bool   configured  = 12; // есть строка настроек — иначе тумблер нечем записать
  bool   armed       = 13; // фактическая охрана
  string arming_source = 14; // "explicit"|"space"|"camera"
  bool   can_control = 15;
}

message ListGuardSensorsResponse {
  repeated GuardSensor sensors = 1;
  bool has_more = 2;
  GuardSensorCursor next = 3;
}
```

**Фильтр пространства.** Поддерево только по `parent_id` (без `owner_id`): камера, чья опорная
реплика нарисована в другом пространстве, не должна попадать в это через владельца. В реляционном
пути — один запрос с `WITH RECURSIVE sub AS (...)` от `space_id` вниз, соединённый с
`camera_placement p ON p.object_id IN (sub) AND p.is_reference`, затем
`device_node dn ON dn.source_id = p.camera_id AND dn.source_kind='camera'
AND dn.part_kind='digital_input'`. Для in-memory провайдера тестов — тот же отбор в LINQ через
`MapDb.GetSubtreeIdsAsync` (у него уже есть построчный запасной путь). Порядок — `(part.name,
dn.object_id)`, страница `page_size+1` строк, `has_more` — по лишней строке.

**Права и догрузка.** VmsMap зовёт `IRightsService.AllowedAsync(ids, ViewLive, caller)` на
выбранный кусок и отбрасывает невидимое; если после отбрасывания страница не полна, а `has_more`
есть — берёт следующий кусок. `can_control` считается одним пачечным
`AllowedAsync(ids, Control, caller)` для итоговой страницы. Это та же схема, что у `GetAlarms`
(выборка → права → страница), и она не материализует 100 000 узлов.

**Пачечная охрана.** `EffectiveArmingResolver` получает
`ResolveManyAsync(IReadOnlyCollection<DevicePartRef> parts, ct)`: та же схема (явный `arm_mode` →
свойство `armed` ближайшего контейнера опорной реплики → флаг камеры), но:
- настройки — один `IDeviceSettingsSource.ListManyAsync(cameraIds)`;
- флаги камер — один `ICameraStateSource.GetArmedManyAsync(cameraIds)`;
- предки опорных реплик — по одному запросу на уровень дерева для всех камер сразу (как
  `RightsService.WalkAsync`), первое явное свойство `armed` побеждает.

`DeviceSettingsCache` реализует `ListManyAsync`: спрашивает версию, берёт из кэша что есть,
недостающие камеры — одним `ListDeviceSettingsForCameras`, кладёт по камере. Существующий
`ListAsync(cameraId)`/`FindAsync` не меняются.

Новый код — `Grpc/MapServiceImpl.Guarding.cs` (RPC) и `Domain/Arming/GuardSensorQuery.cs`
(запрос+сборка строк), чтобы `Reads` не пух. Внедрение — как у остальных сервисов в
`Program.cs`.

### 3. web_srv — эндпоинт

`Controllers/GuardingController.cs`, маршрут `api/guarding`:

- `GET api/guarding/sensors?spaceId=&pageSize=&afterName=&afterId=` —
  `[RequiresRight(RightActions.ViewLive, Source = RightSource.Action)]`: фильтрует VmsMap, как у
  `MapReadControllers`; фильтр прав только фиксирует решение. `Caller = User.ToMapCaller()`.
- Ответ — camelCase DTO `{ sensors, hasMore, next }`, поля строки как в proto; `armed` не
  делается nullable: фактическая охрана для узла датчика всегда разрешается (запасной вариант —
  флаг камеры).
- Ошибки VmsMap (`InvalidArgument` на не-UUID `space_id`) проходят через `RpcExceptionFilter` →
  400.
- Записи нет: тумблер ходит в существующий `PUT api/DeviceIo/cameras/{id}/digital-inputs/{token}/arm-mode`.

7. `finally`: мастер возвращён в `inherit`, реле выключены (как в `check_operator_arming`).

## Часть B. Тревога помещения

**Наблюдение пользователя (2026-11-12):** датчик в тревоге, а помещение над камерой тревоги не
показывает.

**Причина.** Агрегация `alarm_states` идёт по `objects.parent_id` канонического дерева:
датчик → канонический узел камеры → узел сервера. Опорная реплика камеры, нарисованная в
помещении, — отдельный узел с `owner_id`; своих состояний она не хранит («только владелец держит
строку», `StatesUpdateService`), поэтому её родители (пространство и выше) не считают её
тревожной и `children_alarms` помещения остаётся нулём. Это не акторы Square, а их замена —
пересчёт по каноническому дереву.

**Решение — зеркало на опорной реплике.** Ровно одна реплика камеры (опорная) получает строку
`alarm_states`, равную строке канонического узла камеры: `alarm` и `children_alarms` владельца.
Дальше обычная агрегация поднимает счётчик по пространствам. Остальные реплики по-прежнему
отвечают через владельца (`OwnerView`) и своих строк не получают — дублей нет.

- `StatesUpdateService.RecomputeAsync`: после пересчёта канонического пути — для каждой камеры из
  замыкания, у которой есть опорная реплика, записать/обновить её строку значениями канонического
  узла и пересчитать **родителей** реплики (`RecomputeAsync(replica.ParentIds)`), чтобы счётчик
  помещения и его предков сошёлся в той же транзакции. Реплика в агрегацию как собственный узел не
  попадает: её состояние производное.
- `GetAlarmedStates` без `ids`: не отдавать строки реплик (`objects.owner_id IS NOT NULL`) — иначе
  операторский список тревог покажет ту же камеру дважды; счётчик пространства при этом остаётся.
- Смена опорной реплики (перенос, удаление, назначение новой): `SpatialDb`/`MapUpdateService`
  после записи чистят зеркало старой реплики и обновляют счётчики родителей обеих.
- Тесты: `AlarmAggregationTests` (производная строка реплики не считается собственной),
  Postgres-тест (`VMS_MAP_TEST_DSN`) на «тревога датчика → `children_alarms` пространства и его
  предков → снятие тревоги возвращает ноль», и живой шаг приёмки: в `check_sensor_alarm` после
  подъёма тревоги `alarm_reaches(vms, <space id>)` истинно, после возврата в норму — ложно.

## Что сделано

### Часть A

- **VmsCfg.** `proto/vms_cfg.proto` — `ListDeviceSettingsForCameras` (пачка настроек) и
  `GetCamStates` (пачка флагов `armed`); `DeviceStorage.ListManyAsync`,
  `CameraStorage.GetCameraArmedAsync(IReadOnlyCollection<string>)`; обработчики в
  `CfgServiceImpl`. Настройки читаются с явным перечнем камер, поэтому страница панели стоит два
  gRPC-вызова, а не два на камеру.
- **VmsMap.** `proto/vms_map.proto` — `ListGuardSensors`/`GuardSensor`/`GuardSensorCursor`.
  `GuardSensorQuery` (`Domain/Arming/GuardSensorQuery.cs`) выбирает страницу: поддерево
  пространства (рекурсивный CTE только по `parent_id`, чтобы не втянуть камеру через владельца
  чужой картинки), опорные реплики, узлы `digital_input`; порядок `(имя, id)`, keyset-курсор,
  `has_more`. Права — пачечный `AllowedAsync(ViewLive)` на кусок, с догрузкой, пока страница не
  наберётся (не больше 2000 строк за запрос); `can_control` — пачечный `AllowedAsync(Control)`.
  `EffectiveArmingResolver.ResolveManyAsync` повторяет ту же схему explicit → space → camera в
  один проход: настройки и флаги камер пачками, обход предков опорных реплик — по уровню на все
  камеры сразу. `DeviceSettingsCache.ListManyAsync` и `ICameraStateSource.GetArmedManyAsync`
  питают его. RPC — `Grpc/MapServiceImpl.Guarding.cs`.
- **web_srv.** `Controllers/GuardingController.cs` — `GET api/guarding/sensors` с
  `[RequiresRight(ViewLive, Source = Action)]` и `Caller = User.ToMapCaller()`; ответ — camelCase
  DTO с `hasMore`/`next`. Записи нет: тумблер ходит в существующий `PUT …/arm-mode`.

  пользователя при браузерной проверке.

### Часть B

- `StatesUpdateService.RecomputeAsync` после пересчёта канонического пути зеркалит строку
  изменившейся камеры на её опорную реплику и пересчитывает родителей реплики;
  `WriteMirrorsAsync` снимает строку со всех нереферентных картинок камеры (устаревшая опора
  после переноса) и ставит её только опорной.
- `SpatialDb.UpsertPlacementAsync` после коммита зовёт
  `IMapUpdateService.RefreshPlacementMirrorsAsync` → `StatesUpdateService.RefreshPlacementMirrorsAsync`:
  перенос опоры меняет, какое помещение считает тревогу, хотя ни одно состояние не изменилось.
- `GetAlarmedStates` без `ids` не отдаёт строки реплик (`objects.owner_id IS NOT NULL`) — иначе
  общий список тревог показывал бы камеру дважды; счётчик помещения при этом остаётся.
- Тест `AlarmStorePostgresTests.TheRoomCountsTheCameraThatStandsInIt` (Postgres, при
  `VMS_MAP_TEST_DSN`): тревога датчика → `children_alarms` у опорной реплики, помещения и здания;
  список тревог без реплики; возврат в норму обнуляет всё.
