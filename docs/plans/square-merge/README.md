## 1. Контекст

Square (`../Square`) — платформа мониторинга объектов: дерево объектов, карта (Leaflet), состояния
с тревогами и подсветкой родителя, журнал событий, живые значения, треки, мнемосхемы, интеграции по
gRPC с самоописываемыми командами. ta_vms встраивается в него как видеоподсистема
(`docs/square-integration-plan.md`), но интеграция полуготова: экспорт пространств «не проверен на
живом Square», команды из Square не подключены, dev-compose ta_vms не поднимается без чужой
docker-сети, а у оператора две карты и два интерфейса.

Решение пользователя (2026-10-28): Square как самостоятельный проект исчерпан; его платформа
(серверная модель и протокол) ценна как **слой карты и событий внутри ta_vms**. Фронтенд Square
(17 тыс. строк, писался вручную, без тестов) модульно не берётся — только как образец.

## 2. Вердикт

**Объединять — да.** Серверное ядро Square берётся **модульно** (проекты как есть, с рефакторингом
под правила ta_vms), а не переписывается: это работающие годами 7,5 тыс. строк, переписывать их ради
стиля — против DRY/KISS. Кусками переносится только то, что в ta_vms устроено иначе:
`LeafletAlarms` (контроллеры ходят в БД напрямую, а в ta_vms базой владеет один сервис, web_srv
говорит с ним по gRPC), `StateWebSocket` (становится gRPC-стримом из сервиса карты и SSE в web_srv)
и `BlinkService` (логика берётся, акторы заменяются на обновление в той же транзакции).

**PostGIS остаётся.** Для слоёв масштаба, треков и запросов «что в области/зоне» нужен
пространственный индекс. Цена — образ `postgis/postgis` вместо `postgres` в трёх compose-файлах и
ещё один пинованный артефакт в `../ta_install/windows/versions.json`.

**Одно дерево.** Таблица `objects(id, parent_id, owner_id, name)` Square — единственное дерево.
Пространство ta_vms (space) — вид узла с боковой таблицей, как `diagrams` у Square. Камера после
размещения — объект дерева с геометрией и свойствами; что это камера, знает боковая таблица
размещения (`camera_placement` с `camera_id`).

**Две модели картинки, у каждой свой смысл.** План ta_vms — всегда «вид сверху» в WGS84: у
геометрии есть физический смысл (калибровки, наведение PTZ, детекции на карте). Мнемосхема Square —
холст в пикселях без привязки к местности: вид сбоку, изометрия, SCADA-подобная схема с регионами,
куда выводятся живые значения. Переносятся обе; это не дублирование, а разная семантика.

**Старая интеграция сносится в самом начале**, Square-репозиторий архивируется после переноса.

**Обратной совместимости нет и не нужно** (пользователь, 2026-10-28): ни тем, ни другим
продуктом пока никто не пользуется. Отсюда три следствия:
- Всё, что в Square посвящено **универсальной интеграции чужих систем** — реестр типов
  интеграций (`integro_types`, «Add new typed child»), самоописываемые команды (`actions.proto`,
  `action_*`), `IntegrationHost`/`IntegrationUtilsLib`/`SquareIntegrationClient`, топики
  `OnUpdateIntegros_*` — в объединённой системе не нужно и **не переносится**. Внешние продьюсеры,
  если понадобятся, подключатся позже к обычному gRPC `VmsMap` (`docs/future_plans`).
- Модули **сливаются**: ядро Square (`Domain`, `DbLayer`, `DataChangeLayer`) становится одним
  проектом `VmsMap`; тестовые/демонстрационные сервисы (`GrpcTracksClient`, `AASubService`,
  `BlinkService` как процесс) не переносятся.
- При переносе каждое решение оценивается и, если неудачно, **рефакторится сразу** (§3.1), а не
  копируется «как есть ради скорости».

**`VmsMap` — это «VmsCfg для карты».** Единственный владелец базы `ta_map` и источник истины о
дереве, геометрии, состояниях и событиях; web_srv и остальные сервисы ходят к нему по gRPC и
никогда в его базу. У Square контроллеры `LeafletAlarms` читали и писали БД напрямую — это одно из
решений, которое не переезжает.

### 3.1. Что рефакторится при переносе

Принцип: модуль берётся, но каждое решение в нём проверяется на пригодность для объединённой
системы; копировать известную ошибку — нельзя. Список кандидатов (пополняется по ходу):

- Дефекты из §1: `UpdateHierarchyAsync`, `RemoveAsync`, ключ `integro_types` (сама таблица
  уходит), PK у `events`, проверка права Control, права только в `GetByBox`.
- Статические кэши (`StatesUpdateService` — множество тревожных состояний, не инвалидируется)
  → чтение справочника / кэш с инвалидацией по записи.
- Обход дерева по одному запросу на узел (`MapService.GetAllChildren`) и по запросу на уровень
  (`GetByChildIdAsync`) → рекурсивный CTE.
- События: `Skip/Take` со смещением и сортировка по всем ключам **в памяти после** пагинации,
  объявленные и игнорируемые поля фильтра (`objects`, `property_filter`, `search_id`), `start_id`
  как «contains по имени», печать SQL в консоль → сортировка и keyset-пагинация в БД, фильтр по
  поддереву вместо таблицы `groups` (в едином дереве группа — это узел).
- Удаление объекта не чистит `object_states`, `alarm_states`, `events`, `tracks`, `rights` →
  каскад по FK или в одной транзакции.
- `GetOwnersAndViewsAsync` теряет обычные объекты, если во входе есть реплика → переписать.
- Реплики создаются фронтендом копированием свойств (`createDiagramReplica.ts`) → rpc
  `CreateReplica` в `VmsMap`.
- Магические свойства `__color`, `__image*`, `__image_rotate`, `__text` в универсальной
  `properties` → типизированная таблица `visual` (§4.2); `properties` только для абстрактных
  свойств объекта. Миграция `0001` сразу создаёт `visual`, переносить данные неоткуда.
- Размещение по региону — правило модели: узел с `region_id` не имеет собственной геометрии,
  сервис это проверяет при записи, а не только фронтенд при отрисовке.
- Неаутентифицированный WebSocket `/state` → SSE за аутентификацией web_srv.
- `diagrams.dgr_type` — имя типа строкой вместо id → FK на `diagram_types.id`;
  `DiagramCoordProto` без `rotation` (терялся при пуше) → в новом контракте поворот есть.
- `action_*`, `integro`, `integro_types`, `integro_type_children`, `groups` — не создаются.
- Файлы на томе `leaflet_data` → таблица в БД (§4.6).
- `KMeans.cs:77` TODO — посмотреть при переносе.

## 4. Целевая архитектура

### 4.1. Сервис `VmsMap`

- `dotnet/VmsMap`, Dapr app-id `vmsmap`, env `DAPR_MAP_APP_ID`; своя БД `POSTGRES_MAP_DB=ta_map` с
  расширением PostGIS; слушает loopback; gRPC (`--app-protocol grpc`).
- **Класс масштабирования — реплицируемый**, без суффикса Singleton: вся состояние в БД; агрегат
  тревог считается в транзакции записи; подписчик-адаптер (§4.4) переводит события в записи —
  для этого семантика рабочей очереди (одно событие одной реплике) верна; поллер изменений в каждом
  процессе читает БД, поэтому стрим с любой реплики видит записи любой другой.
- Системный сервис: живёт на core (`roles: standalone, core` в
  `../ta_install/windows/config/services.json`).
- Один проект `dotnet/VmsMap` с папками `Domain/`, `Db/`, `Grpc/`, `Adapter/`; отдельные
  сборки Square (`Domain`, `DbLayer`, `DataChangeLayer`) нужны были для общей БД трёх процессов,
  здесь процесс один.
- Схема: миграция `0001` = SQL из `multitenant_admin` минус таблицы интеграций и `groups`, плюс
  `CREATE EXTENSION IF NOT EXISTS postgis`, PK у `events`, FK `diagrams → diagram_types`; дальше —
  свои миграции через `DbMigrator`.
  `DbMigrator` сейчас скопирован в трёх сервисах (копии VmsFs и VmsAnalyticsSingleton идентичны,
  у VmsCfg другой advisory lock и три сида после миграций); четвёртая копия — повод вынести ядро
  (подключение с ретраями, lock, `schema_migrations`, прогон `Grpc/migrations/*.sql`) в новый
  общий проект `dotnet/VmsDb` с хуком для сидов. Не в `VmsLog`: он подключён к сервисам без БД и
  не должен тянуть Npgsql.
- Подключение — тот же контракт, что у VmsCfg/VmsFs (`Program.cs`): `VMS_MAP_POSTGRES_DSN` или
  `POSTGRES_DSN` как явный override, иначе `POSTGRES_HOST/PORT/USER/PASSWORD` + `POSTGRES_MAP_DB`,
  каждое через `Require`.
- `objects.id` остаётся `uuid`; id объекта камеры выводится детерминированно из `camera_id`
  (`ObjectIdGenerator`, как делал `ToObjectId`), сам `camera_id` хранится в `camera_placement`.
- Агрегация тревог — рекурсивный CTE по `parent_id`, изолированный в одном методе репозитория
  (допустимое исключение из правила «EF для запросов»).

### 4.2. Единое дерево

`objects` — единственное дерево; вид узла задаётся боковыми таблицами по тому же `id`:

| Боковая таблица | Узел | Откуда |
|---|---|---|
| `spaces` (`kind` map/plan, `real_coordinates`, `elevation_m`, `ordinal`, `view_*`) | пространство | VmsCfg `space` без `parent_id`/`footprint`/`name` (они теперь в `objects`/`geo_objects`) |
| `space_plan` (три угла, картинка `bytea`, `mime`, `etag`) | план пространства | VmsCfg как есть |
| `geo_objects` (`figure`, `radius`, `zoom_level`) + новая колонка `canvas_id` | всё, что нарисовано своей геометрией | Square + денормализованный id ближайшего предка-холста для запросов по области внутри одного холста (условные координаты разных планов пересекаются около (0,0); пиксели мнемосхем — тем более) |
| `camera_placement` (`camera_id`, `is_reference`, `height_m`, `heading_deg`, `hfov_deg`, `range_m`) | опорное размещение камеры | VmsCfg; ключ — `object_id`, частичный уникальный индекс по `camera_id where is_reference` |
| `landmark` (`height_m`) | ориентир | VmsCfg |
| `ptz_geo_observation`, `ground_observation` | калибровки | VmsCfg как есть (`camera_id` + id ориентира) |
| `diagrams`, `diagram_types`, `diagram_type_regions` | мнемосхема | Square как есть |
| `visual` (`color`, `image`, `image_width`, `image_height`, `rotation_deg`, `text`) | как объект нарисован | **новая, типизированная** — вместо магических свойств Square `__color`, `__image`, `__image_width/height`, `__image_rotate`, `__text` в `properties`. Это общие для карты вещи, а не абстрактные свойства объекта; в `properties` они оказались из экономии. `rotation_deg` для камеры = её азимут из `camera_placement` (одно поле, не два) |
| `properties`, `rights`, `levels`, `object_states`, `alarm_states`, `events`, `track_points`, `db_values` | | Square, с правками §3.1; `properties` — только абстрактные свойства объекта (`visual_type` остаётся для редактора) |
| — (`integro*`, `action_*`, `groups`) | | не создаются: «что это камера» говорит `camera_placement`, вид узла — наличие боковой строки, группа — узел дерева |

Правила:
- **Холсты.** Узел — холст, если он пространство (координаты WGS84) или мнемосхема (пиксели своего
  прямоугольника, регионы своего типа). **Геометрия узла — в координатах ближайшего предка-холста.**
  Футпринт вложенного плана — его собственная фигура (полигон) в родителе; то, что сегодня
  `space.footprint` jsonb. Узел может **и стоять на холсте родителя, и быть холстом для детей**:
  стойка нарисована на плане этажа точкой или прямоугольником и при этом сама — мнемосхема с
  посадочными местами; прибор в ней — мнемосхема с портами. Так уровни детализации вкладываются
  сколь угодно глубоко (план → стойка → прибор → порт).
- **Авторазмещение по региону.** Ребёнок с `region_id` (регион в типе мнемосхемы родителя)
  собственной геометрии не имеет: его место — регион. Это и есть «автоматика сказала, что прибор
  стоит в посадочном месте N»: источник (адаптер, rpc) задаёт только `parent_id` и `region_id`, и
  объект появляется в стойке на предназначенном месте. У Square это уже так (`DiagramElement`
  рисует по региону и запрещает перетаскивать); здесь это правило модели, а не только отрисовки.
- **Рисуется один уровень за раз.** На холсте видны его прямые дети (и реплики); то, что внутри
  них, — после входа в них (хлебные крошки/футпринты, у Square — Dive/Resurface). Глубина
  предпросмотра 0–3 у мнемосхем — настройка просмотра, не модели. На карте к этому добавляются
  слои масштаба (§4.3).
- **Камера после размещения — объект.** Опорное размещение: узел под холстом, точка в
  `geo_objects`, числа для наведения и `camera_id` — в `camera_placement` (она же говорит «этот
  узел — камера»); азимут хранится один раз (`camera_placement.heading_deg`) и отдаётся как
  поворот иконки. Картинки камеры на других планах — реплики (`owner_id`) со
  своей геометрией; состояния и значения реплика показывает владельца — это ровно то, что сегодня
  вычисляет `SquareSpaceExport`, теперь без пересчёта в пиксели.
- **Неразмещённая камера тоже узел**: под автоматическим узлом своего сервера (запись реестра
  узлов), пока администратор не перенесёт её в пространство. Иначе у неё нет места для
  состояний, событий и прав. (Допущение; см. §8.)
- **Тревога поднимается по одному `parent_id`** сквозь объекты, пространства и мнемосхемы без
  особых случаев; то, что сегодня браузер считает из списка тревог («горит здание, если горит этаж»),
  становится `alarm_states.children_alarms`.
- Инварианты `docs/maps-and-plans.md` сохраняются: WGS84 + высота над полом, условные координаты
  около (0,0), «две пространства делят геометрию, если это одно пространство или оба настоящие»,
  одно опорное размещение, фиты не хранятся, азимут 0 = север по часовой.
- Мнемосхема — узел с `diagrams`; её дети размещаются в пикселях её прямоугольника или в регионе
  её типа (как у Square). Камера попадает на мнемосхему репликой. Плану регионы не добавляются:
  если на плане нужна «стойка с местами», это узел-мнемосхема, стоящий на плане.

### 4.3. Слои масштаба

`levels` + `zoom_level` объекта — как у Square: объект без слоя виден всегда; на масштабе города —
районы, на детальном — камеры. Фильтр в `GeoService.GetGeoAsync` уже есть; редактор уровней —
в админке карт.

### 4.4. Как состояния попадают на карту: адаптер

Карта — слой; ядро ta_vms о ней не знает (как не знало о Square). Вход один — адаптер внутри
`VmsMap`, который переводит события ta_vms в записи дерева, состояний и журнала. Отдельного
«протокола продьюсеров» нет: если когда-нибудь понадобится внешний источник, он будет звать те же
rpc `MapService` (`UpdateStates`, `AddEvents`, …), что зовёт web_srv (`docs/future_plans`).

**Адаптер** `VmsMap/Adapter/` — это сегодняшний `VmsSquareSingleton`, перенесённый внутрь и
зовущий сервисы `Db/` напрямую вместо gRPC в Square:
   - `server-config-changed` → камеры ↔ объекты (имя, профиль, `armed`, узел сервера для
     неразмещённых), как `CameraChangeSubscriber`; **и удаление**: `GetCamera.Found=false` →
     удалить объект камеры, её реплики, `camera_placement` и наблюдения. Сегодня это делал FK
     `camera_placement.camera_id → camera_setup ON DELETE CASCADE`, между базами его не будет.
     По той же причине `UpsertCameraPlacement` проверяет существование камеры вызовом `GetCamera`
     в VmsCfg (осознанная межсервисная проверка вместо FK);
   - `camera-state-changed` → свойство `armed`;
   - `retention-event-created` (payload: `camera_id`, `stream_name`, `alarm_start_ts`) →
     адаптер дочитывает эпизод через `FsService.ListRetentionEvents` (`from_alarm_start_ts`; там
     `trigger` и `alarm_end_ts`) → состояние `ALARM` на объекте камеры + запись в `events`
     (`event_name=alarm`, `param0=stream`, `param1=trigger`) с `alarm_end_ts` в свойствах события —
     одной транзакцией. `NORM` ставит периодическая сверка (раз в 3 с, как сегодня `useAlarms`):
     выбрать из БД объекты в `ALARM`, чей конец в прошлом, перепроверить `ListRetentionEvents`
     (конец мог отодвинуться продлением) и снять. Список идущих тревог живёт **в БД, не в памяти
     реплики** — иначе событие, пришедшее одной реплике, после её рестарта никогда не снялось бы;
     сверка идемпотентна, её могут гонять все реплики. Отдельного топика «тревога кончилась» нет
     и не нужно;
   - `CONNECTED`/`DISCONNECTED`: топика «камера в сети» нет (`video_srv` публикует только
     `debug-entity-state`, `GetCamState` знает только `armed`). Источник — готовность пути MediaMTX:
     `VmsUtils.GetMediaMtxPathsInfo` возвращает все пути сервера одним вызовом; адаптер опрашивает
     его раз в 5 с на каждый MediaMTX и выставляет состояние при смене. Опрос, не событие — но
     один вызов на сервер, а не на камеру.
   Событие — только адресация: адаптер перечитывает состояние у владельца (`GetCamera`,
   `GetCamState`, `ListRetentionEvents`), как требует CLAUDE.md. Стартовая сверка (цикл
   `SquareResyncService` «повторять до первого успеха») выполняется в каждой реплике — она
   идемпотентна. Из кода `VmsSquareSingleton` не нужны: `Fingerprint`, `KnownToSquareAsync`
   и обход «Square не создаёт объект без геометрии», `PositionFor` (условные координаты теперь
   законны), `DefaultLat/Lon`, две параллельные RPC вместо одной транзакции.

**Команды с карты для камер** (PTZ, охрана, запись): клиент по `camera_placement` знает
`camera_id` и открывает родные элементы — те же компоненты, что сегодня в карточке камеры.
Самоописываемые действия Square не переносятся; команды для не-камерных объектов появятся вместе
с их источником (`docs/future_plans`).

### 4.5. Живые обновления

`VmsMap`: один поллер на процесс раздаёт серверный стрим `MapService.Watch(box | ids | values)` с
теми же сообщениями, что у Square (`set_ids2update`, `set_ids2delete`, `set_visual_states`,
`on_values_changed`). Честно про стоимость: `StateWebSocket` Square не читает `xmin` (в
`BaseEntity` он закомментирован), а раз в секунду **перечитывает весь наблюдаемый набор**
(`GetGeoAsync(box)`, `GetStatesAsync(ids)`) и сравнивает поле `Version` DTO. Перенос: поллер
объединяет наблюдаемые наборы всех стримов процесса в один запрос в секунду и диффует по
`Version`; для деревьев в тысячи узлов этого достаточно, при росте — таблица изменений вместо
перечитывания (`docs/future_plans`). Каждое сообщение несёт `object_id` и, для узла-камеры,
`camera_id`. web_srv: `GET api/map/live` — SSE поверх этого стрима (`AnalyticsLiveController`
как образец: один gRPC-стрим на одно SSE-соединение, права перечитываются на каждое событие);
фильтр — по §4.7. Клиент добирает данные REST-ом, как и у Square. Поллинг `api/fs/alarms` уходит
— тревоги приходят состояниями.

### 4.6. Файлы

Картинки планов, фоны мнемосхем и типов, картинки событий (`base64image_fs`) — в БД `ta_map`
(таблица `files`: id, mime, bytes, etag), раздаёт web_srv `api/map/files/{id}` (чанками по gRPC,
как `GetSpacePlanImage`; лимит 20 MiB). События от внутреннего адаптера картинок не копируют —
ссылаются на уже существующие (кроп аналитики, кадр клипа).

### 4.7. Права: одна модель на систему

Сегодня две системы прав: в VmsCfg — ACL камер (`user_camera_permission` с флагами
`view_live/view_archive/ptz/control/export`, `user_all_cameras_permission`, режим
`camera_acl_setting` open/enforced; проверяет `CameraAccessFilter` в web_srv, кэш сбрасывается по
ключу `cam-perm-version`), у Square — `rights` на объект (`{role|user, View|Control}`, без
наследования, объект без строк виден всем). Пользователь хочет **единые права на систему, разные
по набору действий для разных сущностей и расширяемые** (2026-10-28). Единое дерево это даёт:

- **Право = строка на узле дерева**: `rights(object_id, subject, action)`, где `subject` — роль
  Keycloak или имя пользователя, `action` — строка из открытого набора. Наследуется **вниз по
  дереву**: право на здание действует на все его этажи и камеры; на узле сервера — на все его
  неразмещённые камеры; на корне — на всё. `admin` имеет всё без строк.
- **Действия — по виду узла, набор расширяем без миграций**: общие для любого узла — `view`,
  `edit`; камера — `view_live`, `view_archive`, `ptz`, `control`, `export` (ровно нынешние флаги);
  карта добавит `ack_alarm`, когда появится приём тревог (сейчас не добавляется — YAGNI, но
  модель его ждёт). Какие действия к какому виду применимы — таблица в коде (`RightActions`),
  одна на систему, её же читает UI прав.
- **Режим** open/enforced один на систему (`AclModeSwitch` уже есть): в open узел без строк виден
  всем, в enforced — только по строкам. Это обобщение сегодняшнего `camera_acl_setting`.
- **Владелец — `VmsMap`** (права лежат на узлах, узлы его). VmsCfg теряет три таблицы прав и
  rpc `Set/GetUserCameraPermissions`, `SetCameraAclMode`; `BumpCameraPermissionsVersionAsync`
  переезжает в `VmsMap` под тем же механизмом — ключ `rights-version` в state store, потому что
  web_srv реплицируем и инвалидируется версией, а не событием (правило CLAUDE.md).
- **Проверка — одна, в web_srv**: `CameraAccessFilter` обобщается в `RightsFilter` с атрибутом
  `[RequiresRight("view_live", Source=…)]`; `CameraAccessService` становится `RightsService`, читает
  из `VmsMap` `GetEffectiveRights(username, roles)` — развёрнутый по дереву список «узел →
  действия» для этого пользователя, кэш 60 с + версия. Для чтений, возвращающих много узлов
  (`GetByBox`, `GetByParent`, события, состояния, `Watch`), фильтрует `VmsMap` сам по тому же
  контексту (`username`, `roles` в запросе), чтобы не гонять лишнее; правило одно, реализаций две
  — вычисление эффективных прав живёт в одном месте (`VmsMap`), web_srv только спрашивает.
- **Следствие для §4.2**: каждая камера обязана быть узлом с момента создания (иначе ей негде
  иметь права) — допущение 1 в §8 становится требованием. Узел камеры создаёт адаптер по
  `server-config-changed` под узлом её сервера.
- Переезд данных прав не нужен (установки тестовые), но форма старых флагов сохранена один к
  одному, так что при желании это одна SQL-вставка.

### 4.8. Карта для оператора: симбиоз

Сегодняшняя операторская карта ta_vms остаётся основой (пространства, этажи, хлебные крошки,
детекции на земле, список тревог, карточка камеры); из Square приходит главный экран как раскладка
«дерево — холст — объект»:

- **Слева, вкладки:** *Дерево* — одно дерево узлов (пространства, объекты, камеры, мнемосхемы) с
  точками тревог, которые поднимаются вверх, и чекбоксами для таблицы состояний; *Тревоги* —
  нынешний список, но из состояний; *Поиск* — по имени и «свойство = значение», период для треков.
- **В центре:** `SpaceCanvas` как сейчас (карта с тайлами или план), плюс произвольные фигуры
  (точка/круг, полилиния, полигон) с `visual` (цвет, иконка, поворот, подпись) и слоями масштаба;
  красная — если тревога у объекта или потомка, иначе цвет первого состояния, иначе `visual.color`
  (правило Square). Если выбран узел-мнемосхема — её холст с детьми по регионам и вложением на
  глубину 0–3; «Dive/Resurface» Square — это наши хлебные крошки и футпринты, одно и то же
  движение для плана и для стойки на нём.
- **Справа:** панель выбранного узла. Камера → существующий `CameraUnifiedCard` (live, архив, PTZ,
  охрана, запись). Прочий объект → свойства (оператору только чтение), чипы состояний, последние
  события.
- **Журнал событий** — отдельная вкладка оператора, обобщение `RetentionEventsTab`: период,
  поддерево (выбранный узел и всё под ним — вместо групп Square), Param 0/1, текст по имени,
  галерея картинок, автообновление.
- **Таблица состояний** (`/_states` Square) — вкладка или режим слева: отмеченные в дереве объекты с
  чипами состояний в реальном времени.
- **Редактирование остаётся в Admin → Maps** (разделение оператора и администратора в ta_vms не
  меняем): туда добавляются произвольные фигуры с редактированием вершин, редактор свойств с
  `visual_type`, реплики перетаскиванием, слой масштаба объекта, справочник состояний, редактор
  мнемосхем и их типов (регионы в долях), уровни масштаба. **Права** — на вкладке выбранного узла
  (строки «субъект → действия», действия по виду узла); нынешняя админская страница прав по
  камерам становится её частным случаем и уходит.

## 8. Допущения, которые стоит подтвердить по ходу

1. ~~Неразмещённая камера — узел под узлом своего сервера~~ — после решения о единых правах
   (§4.7) это требование, не допущение: у камеры без узла негде лежать правам.
2. **Без миграции данных пространств** из VmsCfg в VmsMap (установки v0.1.x тестовые). Альтернатива:
   одноразовый импорт при первом старте `VmsMap` через gRPC VmsCfg — две релизных итерации.
3. **Агрегация тревог в SQL-транзакции** вместо акторов. Альтернатива — перенести `BlinkService` с
   акторами и починить известные рассинхроны; выбор в M1 по результату теста агрегации.
4. **Файлы в БД** (планы, фоны, картинки событий). Альтернатива — общий том, но сервис
   реплицируемый и правило «никаких локальных файлов» у web_srv.
5. **Редактирование только в Admin → Maps**, не на операторском экране (у Square — на главном
   экране по роли).
6. Порядок M2 и M3 можно поменять местами, если состояния/события нужны раньше переезда
   спатиального модуля: M3 не зависит от M2 (адаптер вешает камеры под узел сервера, пока
   пространств в `VmsMap` нет).

## 9. Сквозная проверка после M4

1. Dev-стек поднимается без multitenant_admin (`docker compose up`), `VmsMap` мигрирует `ta_map` с PostGIS.
2. Стенд `tests/onvifsim`: калибровки и наведение через `VmsMap` — как в `docs/maps-and-plans.md`.
3. Тревога камеры → красная камера, этаж, здание, строка дерева; SSE без поллинга `api/fs/alarms`;
   по окончании — бледное кольцо и `NORM`.
4. Журнал событий: фильтры, галерея, автообновление; событие ведёт к архиву камеры.
5. Мнемосхема «вид сбоку» с репликой камеры и регионом со значением (значение — через
   `UpdateValues` по `grpcurl`).
6. Права: пользователь без доступа к камере не видит её ни в дереве, ни в событиях; объект с
   `rights` для роли виден только ей; право, выданное на здание, наследуется его камерами;
   live/архив/PTZ/экспорт ведут себя как до объединения.
7. Windows: инсталлятор ставит PostgreSQL + PostGIS, `vmsmap` в манифесте, `Build-Stage.ps1`
   находит exe.
