# M2.4f — Постановка датчика камеры на охрану из операторского режима

> Подплан [M2.4](m2.4-devices-alarms-automation.md), после [M2.4e](m2.4e-analytics-admin-demo.md).
> Ветка `m2.4f-operator-arming` от `master`.
>
> **Результат:** оператор ставит на охрану и снимает с неё датчик камеры прямо с карточки, видит
> **фактическую** охрану (а не только собственный режим) и не может нажать то, на что у него нет
> права. Демо делает это на «Main room master»: его вход «Master sensor» включён в реле `loop`,
> так что вся цепочка — переключатель → настройка → тревога → квитирование — проверяется живьём.

## Решения (2026-11-12)

- **Объём — только датчик камеры.** Охрана пространств/зон свойством `armed` остаётся отдельной
  задачей ([20-zone-arming.md](../../future_plans/20-zone-arming.md)).
- **Демо — «Main room master»** (`sim-master/input`, «Master sensor»), включённый в собственное
  реле `loop`. Сценарий `sim-ptz/input` (реле `peer`, тревога, маршрутизация, ack) сохраняется
  целиком. OnvifSim не менялся: провод `master/loop → master/input` в мире `maryland` уже был.
- **Команда, а не событие.** Переключатель вызывает VmsCfg синхронно; `device-settings-changed`
  остаётся уведомлением после коммита. Событие-команда через pub/sub не годится: у реплик общая
  очередь (событие получит одна), нет ответа и контекста прав, а потерянная команда молча
  оставила бы датчик снятым. Это же правило CLAUDE.md: события — сигналы, данные потребитель
  перечитывает сам.
- **Одна схема охраны.** Ядро — `EffectiveArmingResolver` (явный `arm_mode` → свойство `armed`
  ближайшего контейнера → флаг камеры). Хранимого флага «меня можно поставить на охрану» нет:
  способность вычисляется из вида узла/`part_kind`, а будущий `device_class` добавит политику
  (пожарная зона — `always armed`).
- **Права — существующее `control`.** Нового действия нет: постановка/снятие датчика и реле — это
  `control`; чтение списков — `view_live`. Отдельной роли «оператор» не нужно: право выдаётся
  роли или пользователю на пространство, где стоит камера.

## Что сделано

### 1. VmsCfg — точечная запись режима

`proto/vms_cfg.proto`:

```proto
rpc SetDeviceArmMode(SetDeviceArmModeRequest) returns (OperationStatus);

message SetDeviceArmModeRequest {
  string camera_id = 1;
  string token     = 2;
  string arm_mode  = 3;  // "armed" | "disarmed"
}
```

- `DeviceStorage.SetArmModeAsync` — один `UPDATE` одной колонки. Не read-modify-write: операторская
  карточка с чуть устаревшей копией не может затереть `name`, `trigger_on` или `alarm_enabled`,
  которые правил администратор. `WHERE kind = 'digital_input'` отсекает реле, поэтому 0 строк —
  это и «нет такого входа», и «это реле».
- `DeviceSettingsRules.ValidateArmCommand` — пустая/не-UUID камера, пустой token, режим не
  `armed`/`disarmed` (в том числе `inherit`: это админская настройка, а не команда оператора).
- `CfgServiceImpl.SetDeviceArmMode` отвечает gRPC-статусами: `InvalidArgument` для валидации,
  `NotFound` когда у камеры нет настроенного входа с таким token. web_srv превращает их в
  400/404 через `RpcExceptionFilter`; 403 даёт фильтр прав до вызова.
- После коммита — тот же `DeviceSettingsNotifier.NotifyAsync`, что у `SetDeviceSettings`:
  `device-settings-version` в state store и `device-settings-changed` в pub/sub.

**Надёжность уведомления.** Публикация best-effort: запись уже закоммичена, а VmsMap читает
`device-settings-version` не чаще раза в 30 с и держит TTL записи 5 мин, поэтому потеря сигнала
**задерживает** пересчёт тревоги, но не теряет изменение. Пересчёт идемпотентен: ключ
дедупликации тревоги не даёт повторной постановке поднять вторую. Transactional outbox в этот шаг
не вводился.

### 2. VmsMap — эффективная охрана части

`proto/vms_map.proto`:

```proto
rpc GetDevicePartArming(GetDevicePartArmingRequest) returns (GetDevicePartArmingResponse);

message GetDevicePartArmingRequest {
  string source_kind = 1;  // "camera" today
  string source_id   = 2;
  string part_kind   = 3;  // "digital_input"
  string part_token  = 4;
}
```

- Адресация — по источнику, не по камере: `device_node` уже общий реестр, и план по пожарной
  сигнализации предусматривает `source_kind='fire_panel'` для панели, её зон и шлейфов
  ([13-fire-alarm-integration.md](../../future_plans/13-fire-alarm-integration.md)). web_srv
  передаёт `source_kind="camera"`; «камера» остаётся частным случаем вызова, не формой контракта.
- `MapServiceImpl.Reads.GetDevicePartArming` находит `device_node` по четырём полям и отдаёт
  `EffectiveArmingResolver.ResolveAsync`. Нет узла части (устройство ещё не присылало снимок) или
  нет id узла — `found=false`, а не «снят с охраны». Незаполненный адрес — `InvalidArgument`.
- Резолвер пока камеро-центричен (`source_id` — id камеры, пространство через
  `camera_placement`, запасной вариант — флаг камеры). Для не-камерных источников это заменится
  политикой класса устройства (`device_class`, `arm_policy='always'`); `NodeArming.source` —
  строка, поэтому новый источник добавится без смены контракта. Сейчас такого не реализуем:
  пожарных устройств ещё нет.

### 3. web_srv — операторский вход и выдача режима

`DeviceIoController` (в конструкторе — `IRightsService` и `MapService.MapServiceClient`):

- `GET cameras/{id}/digital-inputs` (`ViewLive`) отдаёт по каждому входу `armMode` (собственный
  режим из VmsCfg), `armed` и `armingSource` (**фактическая** охрана из VmsMap), `alarmEnabled`,
  `canControl`. Настройки и охрана читаются терпимо: если сервис не ответил, поле `null`, живые
  состояния списка сохраняются.
- `GET cameras/{id}/relay-outputs` получает `canControl` — теперь панель не даёт кликать реле без
  права, вместо 403 после клика.
- `PUT cameras/{id}/digital-inputs/{token}/arm-mode` (`Control`), тело `{ "armMode": "armed" |
  "disarmed" }`. Ошибки VmsCfg идут статусами, не одним 400.
- `canControl` — флаг для UI, а не замена серверной проверке: `[RequiresRight(Control)]` на
  действии остаётся границей.
- Админский `GET/PUT .../settings` не менялся: там по-прежнему все три режима, триггер и флаг
  тревоги.

### 4. Фронтенд

- `DigitalInputDto` получил `armMode`, `alarmEnabled`, `armed`, `armingSource`, `canControl`;
  `RelayOutputDto` — `canControl`. Новый `api/deviceIoApi.ts` с `setDigitalInputArmMode`.
- `DeviceIoPanel.DigitalInputRow`: переключатель охраны показывается только при
  `alarmEnabled === true` и **checked = `armed === true`** — то есть по фактическому состоянию, а
  не по `armMode`. Подпись говорит источник: `On guard` / `On guard (camera)` / `On guard (zone)`;
  при `armed === null` — «Guard state unknown», а не выключено.
- Клик оптимистичен и откатывается: при ошибке переключатель возвращается к серверному состоянию
  (`live.reload()`), чтобы не показывать принятую охрану, которую сервер не принял; успешный
  ответ тоже перечитывает список.
- Без `canControl` неактивны и охрана, и реле, с подсказкой «No control right on this camera».
  Подсказка у охраны: снятие не квитирует и не закрывает активную тревогу.
- i18n: `deviceIoGuard*`, `deviceIoNoControl` (en/es). Админский `DeviceIoSection` не менялся.

### 5. Демо и проверка

- `DemoDevices.MasterSensorSettings()` — `sim-master/input` называется «Master sensor»,
  `arm_mode=inherit`, `trigger_on=closed`, `alarm_enabled=true`. Камера в демо снята, поэтому
  датчик тоже; тревога поднимается только после постановки с карточки.
- `DemoInstallerTests` — настройки проходят `DeviceSettingsRules.Validate`, режим `inherit`,
  триггер `closed`, тревога включена, и они входят в `MasterSettings()`.
- `check_demo.py`, `check_operator_arming` (после `check_provisioning`, только при живом
  симуляторе), целиком в `try/finally`:
  1. вход показывает `inherit`, `armed=false`, `armingSource="camera"`, `alarmEnabled`, `canControl`;
  2. `PUT arm-mode armed` → режим `armed`, `armed=true`, источник `explicit`;
  3. закрыть `loop` → событие `sensor` c `contact=closed`, одна активная тревога, `ALARM` на части
     и предках;
  4. повторная постановка → тревога по-прежнему одна (идемпотентность);
  5. ack при активном условии и охране → 409;
  6. снять с охраны → ack проходит, но `ALARM` остаётся (инвариант M2.4c);
  7. открыть `loop` → контакт `open`, тревога закрыта, `ALARM` снят;
  8. `finally`: `loop` выключен, режим возвращён в `inherit`.
- `check_cleanup` дополнен мастер-входом и реле `loop`: падение раньше не оставит демо на охране.

### 6. Тесты

- `VmsCfg.Tests`: правила `ValidateArmCommand`; Postgres-часть — `SetArmModeAsync` меняет только
  режим, сохраняет имя/триггер/флаг; неизвестный вход и реле не трогаются (`false`).
- `VmsMap.Tests.DeviceNodeTests`: часть находится по `source_kind`/`source_id`/`part_kind`/
  `part_token`; неизвестная часть — `found=false`; неполный адрес — `RpcException`.
- Новый `web_srv.Tests`: `SetDigitalInputArmMode` объявляет `[RequiresRight(Control)]`, оба
  списочных чтения — `[RequiresRight(ViewLive)]`, каждое действие контроллера что-то объявляет;
  `RightsFilter` отказывает действию без аннотации и без права и пропускает с правом, а без
  `cameraId` отвечает 400.

## Проверка

1. `dotnet test dotnet/VmsCfg.Tests` — правила и (при `VMS_CFG_TEST_DSN`) Postgres-часть.
2. `dotnet test dotnet/VmsMap.Tests` — `DeviceNodeTests`, `EffectiveArmingTests`,
   `SensorAlarmTests`, `RightsServiceTests`.
3. `dotnet test dotnet/web_srv.Tests` — права DeviceIo и fail-closed фильтр.
4. `dotnet build dotnet/ta_vms.sln`; `npm run build` и `npm run lint`.
5. Живой прогон: стек и OnvifSim, `python3 tests/demo/check_demo.py --provision-cameras` — шаг
   `Operator arming` проходит, включая восстановление в `finally`.
6. Браузер: Operator → Map → «Main room master» → Sensors: «Master sensor» в `inherit` подписан
   «Off guard (camera)», а не просто выключен; поставить на охрану, включить `Loop` → тревога,
   ack отклонён; снять с охраны → ack проходит, тревога остаётся; выключить `Loop` → норма.
7. Права (при Keycloak): пользователь без `control` на пространство камеры видит переключатели
   неактивными, а прямой `PUT .../arm-mode` отвечает 403; после выдачи роли `control` (сброс по
   `rights-version`, ≤1 с) переключатели оживают.

Состояние: шаги 1–4 и живые 5–7 отмечены при выполнении; живой прогон и браузерная проверка —
за сессией, где поднят стек.
