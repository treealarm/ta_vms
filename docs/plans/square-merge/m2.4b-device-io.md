## Шаг 2. ✅ VmsCfg: `device_settings`

Файлы: `dotnet/VmsCfg/Grpc/migrations/0000_init.sql`, `DeviceStorage.cs`, `CfgServiceImpl.cs`,
`VmsCfgDbContext.cs`, `VmsCfg.Tests`.

```sql
CREATE TABLE device_settings (
  camera_id     uuid NOT NULL REFERENCES camera_setup(camera_id) ON DELETE CASCADE,
  kind          text NOT NULL CHECK (kind IN ('digital_input','relay')),
  token         text NOT NULL,
  name          text NOT NULL DEFAULT '',
  arm_mode      text NOT NULL DEFAULT 'inherit' CHECK (arm_mode IN ('inherit','armed','disarmed')),
  trigger_on    text CHECK (trigger_on IN ('open','closed')),
  alarm_enabled boolean NOT NULL DEFAULT false,
  PRIMARY KEY (camera_id, kind, token),
  CHECK (kind = 'digital_input' OR (arm_mode = 'inherit' AND trigger_on IS NULL AND NOT alarm_enabled)),
  CHECK (NOT alarm_enabled OR trigger_on IS NOT NULL)
);
```

- Охранные поля (`arm_mode`, `trigger_on`, `alarm_enabled`) осмысленны только у входа; у реле
  таблица их запрещает, чтобы не хранить конфигурацию, которую приложение не умеет применить.
- **Отсутствие строки — это значения по умолчанию**, а не ошибка: `arm_mode='inherit'`,
  `alarm_enabled=false`, `trigger_on=NULL`, имя — из token. Строку создаёт администратор,
  когда настраивает часть; автообнаружение строк не пишет.
- RPC `ListDeviceSettings`/`SetDeviceSettings`; запись публикует `device-settings-changed`
  (`{camera_id}`, snake_case) после коммита.
- Валидация: `kind`, `arm_mode`, `trigger_on`; `alarm_enabled` только для `digital_input` и только
  вместе с `trigger_on`.

**Проверка:** `dotnet test dotnet/VmsCfg.Tests`; миграция на чистой `ta_cfg`; повторный upsert
идемпотентен; недопустимая комбинация (реле с `alarm_enabled`) отвергается.

## Шаг 3. ✅ VmsOnvif: манифест и поток событий устройства

Файлы: `dotnet/VmsOnvif/DeviceIoStateService.cs`, новые `DeviceEventPublisher.cs`,
`DeviceIoDiscoveryService.cs`, правки `Grpc/DeviceIoServiceImpl.cs` (вызывает
`ReportDevicesAsync` в двух местах), `OnvifEventSubscriptionService.cs`, `Program.cs`,
`VmsOnvif.Tests/DeviceIoStateServiceTests.cs`.

1. `DeviceIoStateService`:
   - **`ReportDevicesAsync(cameraId, kind, IReadOnlyList<DeviceDescriptor>)` заменяет
     `ReportDevicePresenceAsync(cameraId, kind, count)`**, а не расширяет её:
     `DeviceDescriptor = (Token, IdleState)`, отдельный счётчик больше не передаётся. **Имени в
     дескрипторе нет**: OnvifLib (`OnvifRelayOutput`, `OnvifDigitalInput`) его не отдаёт, и
     отдельный релиз пакета ради подписи не нужен — подпись берётся из `device_settings.name`
     (пусто → token).
     Учёт «что уже прочитано» сохраняется, но живёт в тех же дескрипторах: `Presence(int Relays,
     int Inputs)` заменяется на `DevicePresence` с двумя списками (`null` — ещё не читали),
     `HasDevices`/`IsEmpty` считаются по ним. Watcher закрывается ровно при `IsEmpty`, то есть
     когда **оба** списка прочитаны и пусты, — частичное чтение его не закрывает. Существующие
     тесты `TheRelayListGoingEmptyLeavesTheInputsWatched` и `TheSubscriptionClosesOnceBothListsAreEmpty`
     переезжают на новую сигнатуру и продолжают это доказывать.
   - `Watch` хранит последнее `DeviceIoState`; `idle_state` берёт из `DevicePresence` и по нему
     считает `contact`. Добавляет событие `DeviceEventRaised` и
     `TryGetSnapshot(cameraId, kind, token)`.
   - **Смена `idle_state`** (UI переключает полярность) пересчитывает `contact` для токена с
     известным логическим состоянием и порождает `DeviceEventRaised` сразу, не дожидаясь
     heartbeat: иначе тревога осталась бы посчитанной по старой полярности до следующего снимка.
   - **Debounce** per `(kind, token)` — константа 200 мс; `Initialized` публикуется один раз на
     открытие подписки.
   - Ошибка чтения `GetRelayOutputs`/`GetDigitalInputs` не вызывает `ReportDevicesAsync` вовсе:
     отсутствие ответа не должно выглядеть как «часть исчезла».
2. `DeviceEventPublisher` (hosted): подписан на `DeviceEventRaised`, пишет в bounded `Channel`,
   публикует `device-event`. Присваивает `epoch` — GUID, создаваемый при старте процесса, — и
   `seq`: монотонный счётчик на каждую пару `(camera, kind, token)`, растущий на каждом
   отправленном `device-event`, включая повтор значения. Снимок `device-snapshot` несёт тот же
   `epoch`, но счётчик не двигает.
3. `DeviceIoDiscoveryService` (hosted): обход `ListCameras(server_id=OWN_SERVER_ID)` — для каждой
   ONVIF-камеры `GetRelayOutputs`/`GetDigitalInputs` с таймаутом 5 с и параллелизмом 4. Это
   открывает pull-point без открытой панели — иначе тревога датчика работала бы, только пока
   оператор смотрит вкладку.
   - **Интервал — настройка**, а не константа 60 с: `DEVICE_DISCOVERY_INTERVAL_SECONDS`
     (необязательная, умолчание 300 с — в `.env` её можно не заводить). При 100 000 камер минутный
     обход — это тысячи запросов в секунду на установку; VmsOnvif шардируется по нодам, но и
     внутри ноды обход идёт пакетами, а не по всем камерам сразу.
   - Обход и снимок (п. 4–5) — один интервал: снимок и есть результат обхода.
4. **Снимок устройства — он же манифест.** Обход публикует `device-snapshot` — одно сообщение на
   **камеру** со всеми её частями, а не по сообщению на каждую часть. При 100 000 камер и четырёх
   частях это 333 сообщения в секунду вместо 1 333. Отдельного `device-parts-known` нет: список
   частей в снимке и есть манифест, по нему VmsMap заводит канонические узлы, не дожидаясь первого
   `Changed`. Имени в частях нет: подпись узла — `device_settings.name`, иначе token.

   ```json
   {"source_kind":"camera","source_id":"<uuid>","reachable":true,
    "observed_at":"2026-11-06T12:00:00Z","epoch":"8f14e45f-ceea-467f-a8b1-1c9c2c0f5a11",
    "parts":[{"kind":"digital_input","token":"input","idle_state":"closed",
              "contact":"open","present":true}]}
   ```

   `epoch` — тот же GUID процесса, что у `device-event`: снимок проходит тот же страж
   монотонности, что и событие, поэтому запоздавший снимок не откатывает состояние назад.
   `device-event` остаётся сообщением о переходе — одно на часть.
5. **Сверка.** Снимок нужен не только для узлов: если VmsMap потерял событие или перезапустился,
   расхождение «снимок говорит `closed`, сохранено `open`» обнаружится в пределах интервала
   обхода. Для неизменившейся части сверка проверяет тревогу (условие выполнено, а открытой тревоги
   нет — поднять).
6. **`present` и `reachable` — разные признаки:**
   - `present=false` ставится только по **успешному** ответу устройства, в котором части больше
     нет.
   - Сетевой обрыв или ошибка `GetDigitalInputs` не меняют ничего: ни `present`, ни состояния,
     ни тревоги. После 3 подряд неудачных опросов устройство помечается `reachable=false` — это
     видно в UI, но тревог не закрывает.
   - Связь камеры (`CONNECTED`/`DISCONNECTED`) остаётся делом VmsFs; VmsOnvif её не дублирует.
7. `ForgetAsync` при смене конфигурации/удалении камеры публикует `present=false` для её частей.

**Контракт `device-event`** (payload snake_case, без логических понятий):

```json
{
  "source_kind": "camera",
  "source_id": "<uuid>",
  "part_kind": "digital_input",
  "token": "input",
  "contact": "closed",
  "previous": "open",
  "initialized": false,
  "observed_at": "2026-11-06T12:00:00Z",
  "epoch": "8f14e45f-ceea-467f-a8b1-1c9c2c0f5a11",
  "seq": 42
}
```

У реле вместо `contact` — `"active": true|false`: у выхода логическое состояние, а не физический
контакт, и смешивать их формулой полярности нельзя. `observed_at` — время получения в VmsOnvif.

**`epoch` и `seq` — это и есть защита от переупорядочивания.** `epoch` — случайный GUID,
создаваемый при старте процесса VmsOnvif; `seq` — монотонный счётчик процесса на каждую пару
`(camera, kind, token)`, он растёт на каждом отправленном `device-event`, включая повтор
значения. По времени сравнивать нельзя: `object_states.timestamp` пишет VmsMap своими часами
(`DateTime.UtcNow` в `CameraStateWriter`), а `observed_at` приходит с другой машины — в
распределённом развёртывании разница часов даёт ложные отбрасывания. `observed_at` остаётся для
журнала и для сравнения между эпохами (см. шаг 4).

`contact` считает VmsOnvif: `contact_closed = (idle_state == 'open') ? active : !active`.
Если `idle_state` неизвестен, событие несёт `polarity_known=false`, а `contact` не вычисляется —
он остаётся `null`, а не угадывается (инвариант 5).

**Проверка:** «Initialized → одно сообщение; повтор того же значения → нет сообщения; Changed →
сообщение после debounce»; discovery открывает watcher без вызова UI-геттера; ошибка опроса не
меняет `present`; NC/NO дают правильный `contact`.

## Шаг 4. ✅ VmsMap: узлы, состояния, охрана, outbox

Файлы: `dotnet/VmsMap/Grpc/migrations/0000_init.sql`, `Db/PgDbContext.cs`, новые
`Adapter/DeviceNodeService.cs`, `DeviceSettingsCache.cs`, `DeviceEventSubscriber.cs`,
`DeviceEventTranslator.cs`, `DeviceEventWriter.cs`, `ObjectStateWriter.cs`, `MapLocks.cs`,
`DeviceEventReconciler.cs`, `Outbox/MapOutbox.cs`/`OutboxPublisher.cs`, `EventsWriter.cs`,
`Domain/Arming/EffectiveArmingResolver.cs`, правки `Adapter/CameraStateWriter.cs`,
`Db/Services/EventsService.cs`, `Grpc/MapServiceImpl.cs`, `Program.cs`.

Правки `0000_init.sql` в этом шаге означают ещё одно пересоздание баз (§8 родительского плана).

1. **`DeviceNodeService.EnsureAsync(sourceKind, sourceId, kind, token)`** — идемпотентно создаёт
   `objects`-узел под каноническим узлом камеры и строку `device_node` (`ON CONFLICT DO NOTHING`).
   Имя — из `device_settings.name`, иначе `"{camera.Name} / {token}"`. Геометрии не создаёт.
   По списку частей в `device-snapshot` поддерживаются флаги: в baseline дописываются
   `device_node.present boolean NOT NULL DEFAULT true` и
   `device_node.reachable boolean NOT NULL DEFAULT true`. `present=false` ставится только по
   успешному ответу устройства, в котором части больше нет; `reachable` — по последнему обходу.
   Без хранения этих флагов инварианты 3–4 и статусы палитры (`m2.4e`) не на что опереть.
2. **`DeviceSettingsCache`** — читает `device_settings` через CfgService. VmsMap реплицируем, а
   `device-settings-changed` достаётся одной реплике (общая consumer group), поэтому событие —
   только быстрый сигнал: истина в ключе версии `device-settings-version` общего state store,
   который реплика перечитывает не чаще раза в 30 с; TTL кэша — запасной путь (инвариант 14).
3. **`DeviceEventTranslator`** — переводит `device-event` в состояние и событие по словарю из
   родительского файла; `contact` у входа, `active` у реле. Событие `sensor`/`relay` пишется с
   props `camera_id`, `part_kind`, `token`, `contact`/`active`, `polarity_known`, `observed_at`:
   у Router нет `device_node`, и без этих полей селектор подписки не отфильтрует источник
   (инвариант 15).
4. **`DeviceEventWriter`**:
   - **монотонность** — по `(epoch, seq)`, а не по времени. В baseline дописываются колонки
     `device_node.last_epoch uuid`, `last_seq bigint NOT NULL DEFAULT 0`,
     `last_observed_at timestamptz`:
     - `last_epoch IS NULL` → принять;
     - `msg.epoch = last_epoch` → принять только при `msg.seq > last_seq`;
     - `msg.epoch <> last_epoch` → принять только если `msg.observed_at >= last_observed_at`
       (сообщение от прежнего процесса не должно перебить новое), затем сбросить эпоху.

     Иначе сообщение отбрасывается с записью в лог. Ограничение фиксируется явно: если часы
     машины ушли назад больше чем на интервал между событиями, новый процесс будет отклоняться,
     пока часы не догонят сохранённое `last_observed_at`; это видно в логе, а не молча.
     Событие пишется с детерминированным **UUID** id от
     `(source_kind, source_id, kind, token, epoch, seq)` — через общий хелпер `EventIds.For`
     (UUIDv5 или MD5→UUID, как `ObjectIdGenerator`), не строкой-кортежем: `EventsService`
     сегодня молча заменяет нераспознанный id случайным `NewGuid()`, что тихо убивает
     дедупликацию (инвариант 16);
   - состояние — полным набором через **`ObjectStateWriter`** (инварианты 9–10);
   - `last_epoch`/`last_seq`/`last_observed_at` обновляются в той же транзакции, что и состояние.
5. **`ObjectStateWriter` и `MapLocks`** — обобщение `CameraStateWriter`: полный набор состояний
   объекта под блокировками из `MapLocks` (`ta_map_camera_state` → `ta_map_alarm`). Все
   `pg_advisory_xact_lock` собраны в `MapLocks`; новый код не пишет их сам. Камерные хелперы
   (`SetAlarmAsync`, `SetConnectedAsync`) остаются тонкими обёртками; `AlarmStore` из `m2.4c`
   пишет через него же.
6. **`EffectiveArmingResolver`** + RPC `GetNodeArming`:

   ```
   arm_mode = 'armed'    -> true
   arm_mode = 'disarmed' -> false
   arm_mode = 'inherit'  -> пространство опорной реплики камеры и его предки:
                            ближайшее явное armed (true/false) побеждает;
                            нет опорной реплики или свойства -> camera_states.armed
   ```

   У канонического дерева нет предков-пространств: оно стоит под сервером. Поэтому «зона» — это
   не предок узла, а **место, где камера стоит**, то есть холст её опорной реплики. Для узла
   камеры — то же правило. Резолвер используется ack-проверкой (`m2.4c`) и подписками (`m2.4d`).
7. **`DeviceEventReconciler`** — по `device-snapshot` (полная сверка камеры за одну транзакцию) и
   при повторном `device-event` с тем же значением. Снимок проходит тот же страж монотонности
   `(epoch, observed_at)`, что и событие, поэтому запоздавший снимок не откатывает состояние; а
   расхождение «снимок говорит `closed`, сохранено `open`» — это и есть потерянное событие.
   Если состояние не изменилось, но условие тревоги выполнено, а открытой тревоги нет — поднять её
   (в `m2.4b` это заглушка, включается в `m2.4c`); если тревога есть, а условие ушло — `Normal`.
   Сверка идемпотентна и закрывает окно «VmsMap потерял событие / перезапустился».
8. **`map_outbox`** — транзакционный outbox для уведомлений о событиях карты:

   ```sql
   CREATE TABLE map_outbox (
     id           bigserial PRIMARY KEY,
     topic        text NOT NULL,
     payload      jsonb NOT NULL,
     created_at   timestamptz NOT NULL DEFAULT now(),
     published_at timestamptz,
     attempts     integer NOT NULL DEFAULT 0,
     last_error   text
   );
   CREATE INDEX ix_map_outbox_pending ON map_outbox (id) WHERE published_at IS NULL;
   ```

   Всякий путь, пишущий в `events`, пишет и строку outbox **в той же транзакции** (централизуется
   в одном `EventsWriter`). `Db/Services/EventsService.cs` перестаёт быть «вставь и молчи»: его
   `InsertManyAsync` вставляет `ON CONFLICT (id) DO NOTHING` и возвращает фактически вставленные
   id (EF такого не умеет — raw SQL внутри метода, разрешённое исключение из правила EF).
   `Grpc/MapServiceImpl.cs` (`UpdateEvents`) идёт через `EventsWriter`, а не зовёт `InsertManyAsync`
   напрямую: иначе `emit_event` из подписки минует outbox и публикацию `map-event-created`, и
   причинная цепочка не работает. Вставка события —
   `ON CONFLICT (id) DO NOTHING`, и строка outbox пишется **только когда строка события
   действительно вставлена**: иначе повторная публикация старого события запустила бы подписку,
   созданную уже после него. `OutboxPublisher` (hosted) раз в 250–500 мс забирает пачку
   `ORDER BY id LIMIT 100 FOR UPDATE SKIP LOCKED`, публикует `map-event-created` и отмечает
   `published_at`; при ошибке — `attempts`/`last_error` и повтор. Две реплики VmsMap не мешают
   друг другу (`SKIP LOCKED`), повторная публикация безопасна: получатель идемпотентен.
   Публикация — at-least-once (инвариант 8).
9. **`Program.cs`** — подписки на `device-event`, `device-snapshot`,
   `device-settings-changed`; регистрация hosted-сервисов.
10. **Словарь состояний.** В baseline добавляются `SENSOR_OPEN`, `SENSOR_CLOSED`, `RELAY_ACTIVE`,
   `RELAY_INACTIVE` с `alarm=false`: без строк в `object_state_descriptions` карта не знает ни
   цвета, ни alarm-флага состояния.

## Шаг 5. ✅ Настройки части: API и UI

локали.

  сохраняется, тревога по ней не поднимается до достоверного `idle_state`.

**Проверка:** `npm run build` и `npm run lint`; в браузере переключение режима меняет
`GetNodeArming`.

## Ход работы

**Шаг 1.** `DeviceSettings` (camera_id, kind, token, name, arm_mode, trigger_on, alarm_enabled),
`ListDeviceSettings`/`SetDeviceSettings` и `GetNodeArming` добавлены в proto без `reserved` и без
перенумераций. `NodeArming` несёт `object_id`, `armed` и `source` (`explicit`/`space`/`camera`), а
ответ — `found`: у пространства и сервера охраны нет. Заодно убраны два предупреждения сборки,
которые были до подплана (`FsServiceImpl` и `SpatialPostgresTests`), иначе проверка «0
предупреждений» ничего не значила бы.

**Шаг 2.** `device_settings` в baseline VmsCfg с теми же CHECK, что в плане; `DbDeviceSettings` в
`VmsCfgDbContext`; `DeviceStorage` — чтение и upsert (`ON CONFLICT ... DO UPDATE`, идемпотентный по
природному ключу). Правила валидации вынесены в `DeviceSettingsRules` и проверяются без БД. После
коммита `SetDeviceSettings` пишет `device-settings-version` в общий state store (истина для
реплицируемого VmsMap, инвариант 14) и публикует `device-settings-changed` с `{"camera_id": ...}`.
Проверено: `dotnet test dotnet/VmsCfg.Tests` — 43 теста; на чистой `ta_cfg_test` мигратор
применяет baseline, повторный upsert оставляет одну строку, CHECK отвергает тревогу без
`trigger_on`, удаление камеры каскадом убирает настройки.

**Шаг 3.** `ReportDevicePresenceAsync` заменён на `ReportDevicesAsync` с дескрипторами
`(Token, IdleState)`; `Presence` хранит два списка, частичное чтение watcher не закрывает.
`DeviceIoStateService` публикует `DeviceEventRaised` (contact у входа, active у реле, `previous`,
`polarity_known`, `initialized`) и `PartsForgotten`; contact считается по `idle_state`, при
неизвестной полярности остаётся `null`. Debounce 200 мс на `(kind, token)`, `Initialized` — без
задержки. Смена `idle_state` пересчитывает contact и публикует переход сразу. `ForgetAsync`
объявляет части отсутствующими, `ForgetAllAsync` — нет: node-wide смена на 100 000 камер не должна
порождать 100 000 сообщений, манифест восстановит discovery.

`DeviceEventPublisher` — bounded-канал (4096, `DropWrite` с записью в лог), `epoch` — GUID процесса,
`seq` — монотонный счётчик на `(camera, kind, token)`; payload собирается в `JsonElement` с
snake_case, иначе DaprClient сериализует camelCase и подписчик молча получает null. Снимок
`device-snapshot` получает тот же `epoch`, но счётчик не двигает. `DeviceIoDiscoveryService` идёт
волнами по 500 с параллелизмом 4, таймаут чтения 5 с; интервал — `DEVICE_DISCOVERY_INTERVAL_SECONDS`
(умолчание 300 с). Снимок публикуется только когда прочитаны **оба** списка; частичный ответ —
неудача обхода, потому что снимок из него объявил бы части другого списка исчезнувшими. После трёх
неудач подряд публикуется `reachable=false` с пустым `parts`.

Проверено: `dotnet test dotnet/VmsOnvif.Tests` — 25 тестов: NC/NO дают правильный contact,
неизвестная полярность `polarity_known=false`, debounce и повтор значения, смена `idle_state` без
heartbeat, частичное чтение не закрывает watcher, снимок — одно сообщение на камеру, ошибка опроса
не трогает `present` и не публикует снимок, три ошибки дают `reachable=false`.

**Шаг 4.** В baseline VmsMap добавлены `device_node.present/reachable/last_epoch/last_seq/
last_observed_at`, `map_outbox` с частичным индексом на непublished и четыре состояния
`SENSOR_OPEN`/`SENSOR_CLOSED`/`RELAY_ACTIVE`/`RELAY_INACTIVE` (alarm=false). `DeviceNodeService.
EnsureAsync` заводит узел части под камерой с именем из `device_settings.name` или
`{camera.Name} / {token}`; `device_node` пишется `ON CONFLICT DO NOTHING`, поэтому повторный снимок
ничего не меняет. `DeviceSettingsCache` — singleton: сигнал из pub/sub только сбрасывает запись,
истина — ключ `device-settings-version` (не чаще раза в 30 с), TTL 5 минут — запасной путь.

`MapLocks` собрал все `pg_advisory_xact_lock`, включая демо-установку; grep-тест проверяет, что сырых
вызовов больше нигде нет и что файл, берущий обе блокировки, берёт сначала `ta_map_camera_state`.
`ObjectStateWriter` — единственный писатель набора состояний; `CameraStateWriter` остался тонкой
обёрткой, `DeviceEventWriter` и `DeviceEventReconciler` пишут через него. Порядок событий — по
`(epoch, seq)` под `SELECT … FOR UPDATE` на строке реестра; снимок сравнивается по `epoch` и
`observed_at`. Детерминированные id событий — `EventIds`: UUID из MD5, как у узлов; нераспознанный
id в `EventsService` теперь ошибка, а не молчаливый `NewGuid()`.

`EventsWriter` пишет событие (ON CONFLICT по id) и строку `map_outbox` в одной транзакции, только
для фактически вставленного события; `OutboxPublisher` раз в 400 мс забирает пачку
`FOR UPDATE SKIP LOCKED`, публикует `map-event-created` и чистит опубликованное старше суток.
`UpdateEvents` и `AlarmService` идут через него.

`EffectiveArmingResolver` и `GetNodeArming`: собственный `arm_mode`, иначе ближайшее `armed`-свойство
пространства опорной реплики и его предков, иначе `camera_states.armed`; источник возвращается как
`explicit`/`space`/`camera`. Заодно `StatesUpdateService.RecomputeAsync` переведён с загрузки всех
детей замыкания на агрегат `objects.parent_id` (инвариант 18): на сервере со 100 000 камер это одна
строка на узел замыкания вместо 100 000 строк в памяти.

Проверено: `dotnet test dotnet/VmsMap.Tests` — 162 теста (включая 3 Postgres на `ta_map_test`):
транслятор и адресующие props, отбрасывание старого `seq`, смена эпохи и откат по `observed_at`,
повторная доставка без второго события, `EnsureAsync` идемпотентен и детерминирован, охрана
(armed/disarmed/inherit, свойство пространства, явное `false`, fallback на камеру), outbox переживает
«падение после коммита» и не дублируется при повторной вставке, grep-тест блокировок.

**Шаг 5.** `GET/PUT /api/DeviceIo/cameras/{cameraId}/settings` в `DeviceIoController` идут через
CfgService; чтение — `ViewLive`, запись — `Control`. В `DeviceIoSection` у каждого входа появились
Arming (Inherit/Armed/Disarmed) и «Alarm on contact» с выбором open/closed; у реле осталось прежнее
управление. Неизвестная полярность — предупреждение, настройка при этом сохраняется: тревога просто
не поднимется, пока камера не сообщит `idle_state`. `CameraUnifiedCard` не менялся — Guard камеры
по-прежнему управляет `camera_states.armed`, а входы с `inherit` его наследуют. Проверено:
`npm run lint` и `npm run build` чистые; `dotnet build dotnet/ta_vms.sln` — 0 предупреждений.
Живая проверка в браузере (переключение режима меняет `GetNodeArming`) остаётся за пользователем:
она требует пересозданных баз (§8) и поднятого стека.
