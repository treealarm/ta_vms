## Шаг 3. ✅ Схема `alarms` в VmsMap

`dotnet/VmsMap/Grpc/migrations/0000_init.sql`:

```sql
CREATE TABLE alarms (
  id uuid PRIMARY KEY,
  object_id uuid NOT NULL REFERENCES objects(id) ON DELETE CASCADE,
  definition_id uuid,
  subscription_id uuid,           -- event_subscriptions в VmsCfg; null у sensor/retention
  source text NOT NULL CHECK (source IN ('sensor','retention','subscription')),
  dedup_key text NOT NULL,
  condition_active boolean NOT NULL,
  status varchar NOT NULL CHECK (status IN ('active','acknowledged','returned','closed')),
  severity text NOT NULL CHECK (severity IN ('warning','critical')),
  raised_at timestamptz NOT NULL DEFAULT now(),
  cleared_at timestamptz,
  expected_end_ts timestamptz,    -- retention: прогнозируемый конец
  acknowledged_at timestamptz,
  acknowledged_by text,
  ack_comment text,
  closed_at timestamptz,
  close_reason text CHECK (close_reason IN
    ('returned_to_normal','acknowledged_after_normal','auto_returned_to_normal',
     'device_gone','false_alarm','other')),
  close_comment text,
  closed_by text,                  -- имя оператора или 'system'
  source_event_id uuid
);

CREATE UNIQUE INDEX ux_alarms_open_dedup
  ON alarms (object_id, dedup_key) WHERE status <> 'closed';
CREATE INDEX ix_alarms_open ON alarms (status, raised_at DESC) WHERE status <> 'closed';
CREATE INDEX ix_alarms_closed_at ON alarms (closed_at DESC) WHERE status = 'closed';
CREATE INDEX ix_alarms_object ON alarms (object_id, raised_at DESC);
```

`cleared_at` (условие ушло) и `closed_at` (тревога закрыта) — разные моменты; у `returned` первый
есть, второго нет. Удаление узла каскадом удаляет его тревоги вместе с историей — так же, как
события.

## Шаг 4. ✅ `AlarmStore`

Файлы: новый `dotnet/VmsMap/Adapter/AlarmStore.cs`; `ObjectStateWriter`, `AlarmService.cs`,
`AlarmSweepService.cs`, `DeviceEventReconciler.cs`, `Program.cs`.

**Транзакция и блокировки.** Каждая операция — одна транзакция: сначала `MapLocks.AcquireAllAsync`
(`ta_map_camera_state` → `ta_map_alarm`, инвариант 10), потом строка тревоги `FOR UPDATE`, потом
запись состояния через `ObjectStateWriter`:

```
MapLocks.AcquireAllAsync(tx)
SELECT ... FROM alarms WHERE ... FOR UPDATE
ObjectStateWriter.SetStatesAsync(...)   // при изменении ALARM
```

Так `ack` и `raise` не могут разойтись по порядку захвата: все пути берут один и тот же префикс,
и строка тревоги никогда не ждёт блокировку, которую держит тот, кто ждёт её. `AlarmStore` не
пишет `pg_advisory_xact_lock` сам — иначе правило порядка перестаёт быть проверяемым.

**Переходы** (единственная таблица истины; `ALARM` — состояние объекта):

| Операция | Из | Условие | В | Что пишется |
|---|---|---|---|---|
| `Raise` | нет открытой строки | — | `active` | строка, `ALARM` на объект, `alarm_raised` (кроме `source='retention'` — у него легаси-событие `alarm`) |
| `Raise` | `active`/`acknowledged` | — | без изменений | ничего (идемпотентно) |
| `Raise` | `returned` | — | `active` | `condition_active=true`, `cleared_at=null`, `alarm_raised` |
| `Normal` | `active` | `ack_policy=required` | `returned` | `condition_active=false`, `cleared_at`, `alarm_returned`, `ALARM` снять если других активных нет |
| `Normal` | `active` | `ack_policy=auto_on_normal` | `closed` | `closed_at`, `auto_returned_to_normal`, `alarm_closed` |
| `Normal` | `acknowledged` | — | `closed` | `closed_at`, `returned_to_normal`, `alarm_closed` |
| `Acknowledge` | `active` | `effective_armed=false` | `acknowledged` | `acknowledged_at/by`, `ack_comment`, `alarm_acknowledged` |
| `Acknowledge` | `active` | `effective_armed=true` | — | отказ `409` |
| `Acknowledge` | `returned` | — | `closed` | `acknowledged_at`, `closed_at`, `acknowledged_after_normal`, `alarm_acknowledged` + `alarm_closed` |
| `Acknowledge` | `acknowledged` | — | без изменений | ничего (идемпотентно) |
| `Acknowledge` | `closed` | — | — | отказ `409` |
| `Close` (оператор) | `returned` | — | `closed` | причина `false_alarm`/`other` + комментарий, `alarm_closed` |
| `Close` (оператор) | `active`/`acknowledged` | — | — | отказ `409`: условие активно |
| `Close` (система) | любая ≠ `closed` | `device_gone` | `closed` | `close_reason='device_gone'`, `condition_active=false`, `cleared_at` если пусто, `ALARM` снять, `alarm_closed` |

Правила, которые из таблицы следуют явно:

- `closed_by` пишется в каждом переходе в `closed`: имя оператора для `Acknowledge`/`Close`,
  `'system'` для `auto_on_normal` и `device_gone`.
- **Ack-условие:** `status <> 'closed' AND (condition_active = false OR effective_armed(object_id) = false)`.
  Это UX-гейт, а не блокировка: охрана живёт в двух других сервисах, и сериализовать её с ack
  нельзя. Проверка читает эффективную охрану внутри транзакции; одновременное снятие с охраны
  может отказать в одном ack — оператор повторит. Обратный порядок (ack успел до постановки на
  охрану) безвреден: ack ничего не закрывает.
- **Снятие с охраны не квитирует и не закрывает** тревогу — только разрешает ack.
- **Ручное закрытие при активном условии запрещено**; `false_alarm` — это причина закрытия уже
  вернувшейся в норму тревоги. Подавление активной тревоги — future.
- **`ALARM` снимается только когда на объекте не осталось открытых тревог с `condition_active=true`.**
  `ALARM` ставится на узел тревоги: у части он дополняет `SENSOR_*`, у камеры — `NORM`.
- `expected_end_ts` обновляется при продлении retention-эпизода.

**События жизненного цикла** (плюс `camera_id` в props, где он есть):

- `alarm_raised` — `param0=severity`, `param1=trigger`; props `alarm_id`, `source_event_id`.
- `alarm_acknowledged` — props `alarm_id`, `acknowledged_by`, `comment`.
- `alarm_returned` — props `alarm_id`.
- `alarm_closed` — props `alarm_id`, `close_reason`, `close_comment`.

Повторный `Raise` не пишет второго события. Все события проходят через `EventsWriter` из `m2.4b`,
то есть через outbox.

**Права:** `RightActions.Acknowledge = "acknowledge"` — в `All`, в `CameraActions` и в ветке
`For(NodeKind.Part)` (набор части: `View, Edit, ViewLive, Control, Acknowledge`); `GetAlarms`
фильтрует по `view`, ack/close — по `acknowledge`. `Close` — то же право, что ack: это продолжение
разбора тревоги, отдельной роли нет.

## Шаг 5. ✅ Retention на `AlarmStore`, `raise_alarm`

Файлы: `dotnet/VmsFs/Grpc/migrations/0000_init.sql`, `dotnet/VmsFs/Grpc/ClipStorage.cs`,
`FsServiceImpl.cs`, `VmsFs.Tests`; `dotnet/VmsMap/Adapter/AlarmService.cs`, `AlarmSweepService.cs`,
`Clients/IRetentionEventSource.cs`, `RetentionEventSubscriber.cs`.

- VmsFs: колонка `retention_events.raise_alarm boolean NOT NULL DEFAULT true`; при продлении
  значение **не меняется**; `retention-event-created` несёт `raise_alarm`; `RetentionEventRow`
  отдаёт его. Ручной `POST /api/fs/events` получает `raise_alarm` в DTO, по умолчанию `true`.
- VmsMap: `RetentionEpisode.RaiseAlarm`; `AlarmService.RecordAsync` вызывает
  `AlarmStore.Raise/Clear` с `dedup_key='retention:{event_uuid}'`, `source='retention'`,
  `expected_end_ts`, `source_event_id=event_uuid`. При `raise_alarm=false` — ни `ALARM`, ни строки
  `alarms`, ни события `alarm`; эпизод остаётся в VmsFs и виден в клипах.
- Легаси-событие `alarm` (id = `event_uuid`, props `alarm_end_ts`) сохраняется: по нему работает
  журнал retention. `alarm_raised` для retention не пишется — тревога видна строкой `alarms`.
- `AlarmSweepService` проверяет `alarms WHERE source='retention' AND condition_active`, а не
  состояния `ALARM`: эпизод закончился и не продлён → `Normal`; продлён → обновить
  `expected_end_ts`. Сверка идемпотентна, её выполняет каждая реплика.

## Шаг 6. ✅ Датчики: тревога по контакту

Файлы: `DeviceEventReconciler.cs`, `DeviceEventWriter.cs`, `DeviceSettingsCache.cs`.

- `alarm_enabled=true` и известная полярность: `contact == trigger_on` → `Raise` с
  `dedup_key='sensor:{source_kind}:{source_id}:{kind}:{token}'`, `source='sensor'`,
  `definition='sensor'`; `contact != trigger_on` → `Normal`.
- **Неизвестная полярность (`polarity_known=false`) тревогу не поднимает**; состояние пишется,
  UI показывает предупреждение. `alarm_enabled` без `trigger_on` в VmsCfg не сохраняется.
- Постановка на охрану уже сработавшего датчика успешна: если `contact == trigger_on` — тревога
  поднимается сразу с `param1='armed_with_active_condition'`.
- Удержание контакта новых тревог не создаёт: открытая строка по `dedup_key` делает `Raise`
  идемпотентным.
- **Сверка:** по `device-snapshot` (снимок камеры целиком) и при повторном `device-event` с тем же
  значением, если состояние не изменилось, но условие выполнено и открытой тревоги нет — `Raise`;
  если тревога есть, а условие уже нет — `Normal`. Так рестарт VmsOnvif, рестарт VmsMap или
  потерянное сообщение не оставляют систему без тревоги.
- Часть пропала (`present=false` по успешному ответу устройства) или камера удалена →
  `Close(reason='device_gone')`. Недоступность устройства тревогу не закрывает.

## Шаг 9. ✅ Масштаб: агрегация и списки на 100 000 узлов

Цель — 100 000 камер (инварианты 17–20 родительского плана). Три места этого подплана на таком
размере обязаны работать, и два из них сегодня не работают в принципе.

1. **`StatesUpdateService.RecomputeAsync` не должен грузить детей.** Сейчас
   `QueryLinksAsync("… WHERE parent_id = ANY(@ids)")` возвращает всех детей замыкания, и их id
   уходят ещё в два запроса. При сервере с 100 000 камер это 100 000 строк и массив из 100 000
   параметров на каждое изменение тревоги. Переписать:
   - `children_alarms` — один агрегат по индексу `objects.parent_id`:

     ```sql
     SELECT o.parent_id, count(*)
     FROM objects o JOIN alarm_states a ON a.id = o.id
     WHERE o.parent_id = ANY(@parents) AND (a.alarm OR a.children_alarms > 0)
     GROUP BY o.parent_id;
     ```

   - собственные тревоги замыкания — `EXISTS` по `object_state_values` (замыкание — это глубина,
     не ширина);
   - строки детей не переносятся вовсе.

   Это правка существующего кода в `master`, а не только плана: без неё первая же тревога под
   сервером на 100 000 камер кладёт запрос. `AlarmAggregation.Compute` остаётся — меняется
   способ загрузки узлов.
2. **`GetAlarms` — keyset, не offset.** Открытые — курсор `(raised_at DESC, id)`, закрытые —
   `(closed_at DESC, id)`; размер страницы — параметр с умолчанием 100. `ix_alarms_open` и
   `ix_alarms_closed_at` обслуживают обе ветки.
3. **Права — пакетно на страницу.** Для страницы тревог якоря устройств разрешаются одним запросом
   (`device_node` → камера → опорная `camera_placement`), затем один пакетный
   `AllowedAsync`; результат кэшируется по `object_id` на время запроса. Никаких запросов на
   строку списка.

**Проверка:** на 100 000 узлов и 100 открытых тревогах `EXPLAIN` показывает индексные сканы;
`RecomputeAsync` не возвращает строк детей; `GetAlarms` отдаёт страницу без полного обхода.

## Ход работы

**Шаг 1.** `Alarm`, `AlarmList`, `GetAlarmsRequest`, `AcknowledgeAlarmRequest`,
`CloseAlarmRequest`, `RaiseAlarmRequest` и четыре RPC добавлены без `reserved`; `AlarmDefinition`
и `ListAlarmDefinitions` — в VmsCfg; `raise_alarm` — в `RetainEventRequest` и
`RetentionEventRow` как `optional bool`, чтобы не сказавший ничего вызывающий сохранил прежнее
поведение.

**Шаг 2.** `alarm_definitions` в baseline VmsCfg с тремя сидами и фиксированными UUID
(`…a101` sensor — `required`, `…a102` retention — `auto_on_normal`, `…a103` subscription —
`required`): id уезжает в строку тревоги навсегда, поэтому он не может зависеть от того, что
сгенерировала миграция. Чтение — `AlarmDefinitionStorage`, RPC `ListAlarmDefinitions`; CRUD нет.

**Шаг 3.** Таблица `alarms` — как в плане. Индексы `ix_alarms_open` и `ix_alarms_closed_at`
построены под keyset-порядок каждой ветки (`(raised_at DESC, id DESC)` и `(closed_at DESC, id
DESC)`), а не по `status`: частичный индекс уже ограничен статусом, и `status` в ключе ничего бы
не нёс. `ux_alarms_open_dedup` — частичный уникальный, как в плане.

**Шаг 4.** `AlarmStore` — единственное место переходов; каждая операция берёт
`MapLocks.AcquireAllAsync` (в MapLocks появился этот метод), блокирует строку `FOR UPDATE` и
пишет состояние через `ObjectStateWriter` и событие через `EventsWriter` в той же транзакции.
Два решения по ходу:

- **Сеть не под замками.** Определения тревоги (`IAlarmDefinitionsSource`) читаются до открытия
  транзакции, а эффективная охрана для ack-гейта — до блокировки строки. План сам называет
  ack-условие UX-гейтом, а не блокировкой, поэтому гонка «сняли с охраны между чтением и
  блокировкой» допустима: строка перечитывается под замком, и переход решается по её текущему
  статусу.
- **`closed_by` для `Normal` из `acknowledged`** — имя квитировавшего, а не `system`: план
  перечисляет оператора для `Acknowledge`/`Close` и `system` для `auto_on_normal`/`device_gone`,
  а здесь закрывается именно квитирование оператора. Повторный `Close` уже закрытой тревоги —
  идемпотентен (в отличие от `Acknowledge`, который по таблице отвечает 409): двойной клик в UI не
  должен показывать ошибку.
- `ObjectStateWriter` и `AlarmStore` стали `public`: конструктор публичного `MapServiceImpl`
  принимает хранилище.

**Права.** `RightActions.Acknowledge` — в `All`, в наборе камеры и в наборе части; копия
константы — в `web_srv.Server.Authorization.RightActions`. `GetAlarms` фильтрует по `view`
батчем (`IRightsService.AllowedAsync` стал публичным), `can_ack` — по `acknowledge` батчем и
правилу состояния; сама охрана резолвится по строке и только для открытой тревоги с активным
условием — страница ограничена, а тревог с живым условием немного.

**Шаг 5.** VmsFs хранит `raise_alarm` (по умолчанию `true`), продление его **не меняет** (читает
из открытого эпизода) и отдаёт в `RetentionEventRow`; `retention-event-created` несёт его же.
`RetentionEpisode.RaiseAlarm` (по умолчанию `true` для старых строк) и `AlarmService.RecordAsync`
при `false` не пишут ничего — ни `ALARM`, ни строки, ни легаси-события `alarm`; план прямо
перечисляет все три. `AlarmSweepService` сверяет `alarms WHERE source='retention' AND
condition_active`; начало эпизода для `FindAsync` он берёт из легаси-события `alarm` по
`source_event_id`, потому что `raised_at` — время подъёма, а не начала эпизода.

**Шаг 6.** Правило «контакт = `trigger_on` на включённом и **эффективно охраняемом** входе» живёт
в одном `SensorAlarmService`, общем для события, снимка и смены настроек: любой из трёх путей
может первым увидеть живое условие без тревоги, и все три зовут идемпотентные `Raise`/`Normal`.
План не называет охрану в первом пункте шага, но правило «постановка на охрану уже сработавшего
датчика поднимает тревогу» без неё не имеет смысла, а «снятие с охраны не квитирует и не
закрывает» — соблюдено. Сверка выполняется после коммита состояния: резолвер охраны ходит в два
других сервиса. `present=false` (только по успешному ответу) закрывает тревоги части как
`device_gone`; `reachable=false` не трогает ничего.

**Шаг 7.** `MapServiceImpl.Alarms.cs`: `GetAlarms` отдаёт **две страницы с раздельными
курсорами** (`open` — `(raised_at, id)`, `closed` — `(closed_at, id)`), а не один плоский список:
у ветвей разные индексы и разный порядок, и один курсор не обслужил бы обе. `RaiseAlarm` не
проверяет права по той же причине, что и `UpdateStates`: граница — вызов через Dapr из кода
развёртывания. `AlarmsController` (`POST /api/map/alarms`, `{id}/acknowledge`, `{id}/close`) и
`RpcExceptionFilter`: `PERMISSION_DENIED` → 403, `FAILED_PRECONDITION` → 409.

**Шаг 8.** `store/alarmsSlice.ts` (две страницы, keyset, ack/close кладут изменённую строку в
свой список) и список тревог на карте — из `GetAlarms`, с кнопкой Acknowledge (disabled по
`can_ack`, подсказка объясняет отказ) и диалогом комментария/причины. «Возврат в норму и
закрытие» доступны из того же диалога для `returned`. `EventsJournal` получил фильтры и значки
`sensor`/`relay`/`analytics`/`alarm`, а событие `alarm_*` ведёт на карту с `?node=<object_id>`,
где открывается вкладка тревог. Окраска карты по-прежнему из `GetAlarmedStates`.

**Шаг 9.** `RecomputeAsync` уже переписан на агрегат `objects.parent_id` в `m2.4b` — здесь
меняется только способ загрузки узлов, и он уже O(глубины). `GetAlarms` — keyset с курсором и
умолчанием 100; права страницы — один `AllowedAsync` на ветвь.
