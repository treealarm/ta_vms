# Гонка прохода охраны при старте VmsMap

> Ветка `feature/arming-sweep-race` от `master`.
>
> Исходник — `docs/future_plans/22-arming-sweep-race.md`; future plan и его строка в индексе
> удаляются последним коммитом.
>
> **Результат:** флаг `armed` камеры сходится к зоне, в которой стоит её опорная реплика, при
> любом порядке конкурирующих записей — и на старте, когда установка демо-мира идёт параллельно
> проходу охраны, и при переносе реплики из GUI, и при событийных пересчётах. Сеятель больше не
> выводит флаг из незакоммиченного мира: упавшая установка не оставляет после себя чужой флаг.

## Контекст

При старте VmsMap `StartupResyncService` делает проход `CameraArmingReconciler.SweepAsync`, а
`DemoInstallService` в это же время переустанавливает демо-мир. Оба — `BackgroundService`, явного
порядка между ними нет.

Гонка имеет две причины, и обе надо закрыть.

1. **Пересчёт не сходится.** `ReconcileAsync` читает состояние камеры (VmsCfg), режим (карта) и
   зону (обход дерева), вычисляет `want` и пишет его в VmsCfg. Между чтением и записью любой
   другой писатель может пересчитать флаг заново — побеждает тот, кто записал последним, даже
   если его чтение было до изменения. Следующего триггера может не быть.
2. **Сеятель пересчитывает флаг внутри своей незакоммиченной транзакции.** `DemoSeeder.InstallAsync`
   держит одну транзакцию на весь мир; `SpatialDb.UpsertPlacementAsync`/`RemovePlacementAsync`,
   вызванные внутри неё, делают `ReconcileAsync` до коммита (собственного коммита у них нет —
   `BeginTransactionAsync` возвращает null при внешней транзакции). Сеятель пишет флаг по ещё не
   закоммиченному расположению реплики, а после коммита пересчёта не следует; при откате
   транзакции запись в VmsCfg не откатывается вовсе.

Наблюдалось один раз: после рестарта камера осталась `armed=true`, хотя этаж под ней был снят с
охраны; следующий рестарт исправил значение.

**Источник истины и какая гарантия нужна.** Режим камеры и зона — данные карты; `camera_states.armed`
в VmsCfg — **производное** значение, и карта — его единственный писатель
([control.md](../maps/control.md)). Флаг всегда пересчитывается
заново из текущих данных, поэтому цель — сходимость к последнему закоммиченному состоянию карты, а
не линеаризуемость записи через два сервиса.

Версия или `UpdatedAt` на строке карты этого не даст: проверка версии может сделать согласованным
**чтение** карты, но не **запись** в чужую БД — между проверкой и gRPC-записью изменение всё равно
можно закоммитить. Версия на строке `camera_states` (или `xmin`) обнаружила бы только
конкурирующего писателя **флага** — а это ровно то, что и так видит перечитывание после записи;
при этом она требует новой колонки в таблице, которую D2 как раз сокращает, и нового поля в proto,
но не защищает от `want`, посчитанного по устаревшей карте. Строгую линеаризуемость дала бы только
блокировка, удерживаемая через сетевой вызов (отвергнута ниже), или один владелец обеих строк (вне
объёма). Сходимость обеспечивают: перечитывание и пересчёт на каждом проходе (правка 1) и пересчёт
после коммита у каждого писателя (правки 2–3); восстановление — проход охраны при каждом старте
(см. правку 3).

**Почему не упорядочить хост-службы.** Порядок «проход после установки мира» не закрывает ни одну
из причин: событийный пересчёт (`CameraChangeSubscriber` на `camera-state-changed`), прочитавший
карту до коммита мира, может записать устаревшее значение уже после прохода; вторая реплика VmsMap
со своим проходом — так же. Кроме того, гонка не только стартовая: перенос опорной реплики из GUI
(`SpatialDb.UpsertPlacementAsync` → пересчёт после коммита) конкурирует с пересчётом по событию.

**Почему не блокировка.** `MapLocks` — это `pg_advisory_xact_lock`, блокировка живёт только внутри
транзакции; держать транзакцию через gRPC-вызовы в VmsCfg запрещено (решение M2.4i — «транзакцию
через сетевой вызов не держим»).

## Решение

Три правки: сходящийся пересчёт, честный момент коммита в `SpatialDb`, пересчёт после коммита в
сеятеле. Все три нужны — каждая закрывает свою причину.

### 1. Сходящийся пересчёт: `CameraArmingReconciler.ReconcileAsync`

Каждая запись флага должна быть прочитана заново; цикл ограничивается числом **записей**, и после
последней возможной записи делается ещё одно чтение.

```csharp
internal const int MaxWrites = 3;

var wrote = false;
for (var pass = 0; ; pass += 1)
{
  var (state, want) = await DeriveAsync(cameraId, ct);   // чтения: VmsCfg, режим, зона
  if (state?.Armed == want)
    return wrote;                                        // сошлось
  if (pass == MaxWrites)
  {
    _logger.LogWarning(
      "Camera '{CameraId}' arming did not settle after {Writes} write(s)", cameraId, MaxWrites);
    return wrote;                                        // следующий триггер повторит
  }
  var changed = await _cfg.SetCamArmedAsync(cameraId, want, ct);
  if (!changed)
    return wrote;                                        // VmsCfg уже держал это значение
  wrote = true;
  _logger.LogInformation(...);                           // как сегодня
}
```

- `DeriveAsync` — вынос сегодняшних строк 63–71 в приватный метод.
- **Каждый проход — полный пересчёт, а не повтор прошлого `want`.** `DeriveAsync` заново читает
  состояние из VmsCfg, режим и зону из карты; устаревший результат никогда не записывается
  повторно. Последняя возможная запись тоже перепроверяется: цикл считает проходы, а не записи.
- Нормальный путь не дорожает: сошедшийся пересчёт — одно чтение и ничего не пишет; лишнее чтение
  появляется только после записи. `ASecondLookWritesNothing` продолжает держать этот контракт.
- **Снимок карты — против рваного чтения, не против устаревшей записи.** `DeriveAsync` берёт режим
  и зону внутри короткой read-only-транзакции `RepeatableRead`, которая закрывается **до**
  gRPC-записи (правило M2.4i не нарушается: в транзакции нет сети). Сам по себе снимок не защищает
  от изменения, закоммиченного между чтением и записью, — от этого защищает проверка после каждой
  записи; снимок лишь не даёт проверке собрать `want` из наполовину старой, наполовину новой
  карты. Транзакция не открывается, если провайдер не реляционный (InMemory-тесты) или если
  транзакция уже открыта вызывающим: `BeginTransaction` в этом случае бросит.
- **Повторять внутри цикла нечего.** Снимок read-only и без блокировок, поэтому serialization
  failure и deadlock не возникают; отказ gRPC или БД пробрасывается — `ReconcileManyAsync`
  логирует камеру с причиной и продолжает с остальными, а следующий триггер повторит. Классы
  повторяемых ошибок не вводятся.
- Возвращаемое значение сохраняет прежний смысл: `true`, если хоть одна запись изменила строку.
  Ни один продакшн-вызов его не читает (`ReconcileManyAsync`, `DeviceArmingDerivation`,
  `SpatialDb`, подписчики), только тесты. Сигнатура и поведение `ReconcileManyAsync` не меняются:
  отказ по камере не отменяет остальные и не теряется — в логе есть id и причина.
- XML-комментарий класса дополняется абзацем: почему запись перепроверяется и почему чтения карты
  идут одним снимком.

### 2. `SpatialDb` не выводит флаг из незакоммиченного состояния

В `UpsertPlacementAsync` (пересчёт на строке 550) и в удалении (`AfterRemovalAsync`, строка 294,
вызывается из `RemovePlacementAsync` и `RemoveSubtreeAsync`) пересчёт выполняется, только если
владелец транзакции — сам метод. Если метод присоединился к внешней транзакции, пересчёт делает
её владелец после коммита — тот же контракт, что уже описан у `RemoveInSubtreeAsync`.

Признак — **локальный `tx`, а не `CurrentTransaction`**:

```csharp
// tx is null при внешней транзакции и всегда в InMemory; во втором случае пересчёт нужен.
private static bool IsAmbientTransaction(IDbContextTransaction? tx, VmsMapDbContext db) =>
  tx is null && db.Database.IsRelational();
```

`CurrentTransaction` для этого не годится: после `CommitAsync` он ещё указывает на закоммиченную
транзакцию до `Dispose`, то есть по нему нельзя отличить «своя, уже закоммичена» от «чужая,
открыта». `AfterRemovalAsync` получает признак `ambient` параметром от вызвавшего
(`RemovePlacementAsync`/`RemoveSubtreeAsync` знают свой `tx`).

Следствие: у сеятеля исчезают пересчёты до коммита, а вместе с ними и запись флага по миру,
который затем откатился. Остальные вызывающие (gRPC-путь переноса реплики, удаление из GUI)
работают как сегодня — они владеют транзакцией и пересчитывают сразу после своего коммита.

### 3. Сеятель пересчитывает после коммита: `DemoSeeder`

`DemoSeeder` не получает новых зависимостей — он уже держит `SpatialDb`, а тот владеет
`CameraArmingReconciler`. В `SpatialDb` добавляются два публичных помощника рядом с существующим
`ReconcileArmingAsync`:

- `ReconcileCamerasAsync(IReadOnlyCollection<string> cameraIds)` → `_arming.ReconcileManyAsync`;
- `CamerasUnderAsync(IReadOnlyCollection<string> objectIds)` → `GetSubtreeIdsAsync` +
  `CameraPlacements.Where(p => guids.Contains(p.object_id))` **без** фильтра `is_reference` (камера
  может стоять в удаляемом поддереве неопорной репликой). Для удаляемых поддеревьев вызывается
  **до** удаления; для оставшихся контейнеров — после коммита.

В `InstallAsync` (строка 107):

- до `DeleteAsync(stale, ct)` (строка 568) снять `removed`: камеры из поддеревьев
  `space`/`object` среди `stale` через `CamerasUnderAsync`, плюс id камер из ключей `camera/...`
  (`DemoIds.Camera(...)`);
- после `tx.CommitAsync` (строка 573) и после цикла `_deviceSettings.SetAsync` (строки 584–603),
  в `try/finally` вокруг этого цикла — один вызов `ReconcileCamerasAsync` по объединению
  `removed` и `CamerasUnderAsync(kept)`, где `kept` — id пространств и объектов, оставшихся у
  мира (`ids` ∩ `keep`, `KindOf` = `space`/`object`): это все камеры, чьи реплики стоят в
  перезаписанных контейнерах, включая камеры пользователя, перевешенные пространства и снятые
  реплики. Один `GetSubtreeIdsAsync` на все корни, а не обход по контейнеру.
  `ReconcileManyAsync` глотает отказ по отдельной камере, поэтому установка из-за пересчёта не
  падает.
- Пересчёт после цикла режимов, а не до него: `SetAsync` по части `device` пишет собственную
  строку камеры, и её `want` должен учитывать новые настройки. Сегодняшние миры пишут только
  `digital_input`, но порядок должен быть верным для любого мира.
- Сеятель передаёт только id камер; `ReconcileAsync` сам читает актуальные строки карты
  (`AsNoTracking`), поэтому между коммитом и пересчётом мир может измениться — это не страшно.
- Если процесс упадёт после коммита мира и до пересчёта, флаг не останется неверным навсегда:
  установка демо-мира выполняется при **каждом** старте с `DEMO_CONFIG`, а проход охраны
  (`SweepAsync`) при каждом старте пересчитывает все зоны независимо от демо. Для ручной
  установки/снятия мира через RPC страховка та же — старт и следующие триггеры.

В `RemoveAsync` (строка 611): до `DeleteAsync(registered, ct)` снять тем же способом камеры из
`registered` (поддеревья `space`/`object` и ключи `camera/...`), после `tx.CommitAsync`
(строка 634) — `ReconcileCamerasAsync(captured)`.

## Тесты

InMemory, `CameraArmingTests`:

1. `AFlagWrittenFromAZoneThatMovedUnderneathIsCorrected`. Реплика в охраняемой зоне; `AfterWrite`
   один раз переносит её в неохраняемую (`Markers.parent_id`) — мир переехал между чтением и
   записью. Утверждения: `ReconcileAsync` вернул `true`; итоговый флаг `false`; в журнале записей
   ровно `[(true), (false)]` — устаревшая запись была и была исправлена.
2. `AWriteOverwrittenByAConcurrentWriterIsCorrected`. `AfterWrite` один раз переключает флаг в
   `TestCameraState` обратно (чужой писатель записал после нас). Утверждения: итоговый флаг
   совпадает с зоной; записей две.
3. `AReconcileThatCannotSettleStopsAtItsBudget`. `AfterWrite` переключает флаг на каждой записи.
   Утверждение: число записей равно `CameraArmingReconciler.MaxWrites`, вызов завершается.
4. `OneCameraThatFailsDoesNotStopTheOthers`. `ReconcileManyAsync` по двум камерам; писатель
   бросает на первой. Утверждения: вторая всё равно записана; вызов не бросил. Это фиксирует
   существующий контракт, который правка не должна сломать.

`DemoSeederTests` (InMemory):

5. `TheInstallLeavesTheFlagMatchingTheCommittedZone`. Мир ставит камеру в комнату; в VmsCfg флаг
   заранее `true`, комната снята с охраны; после `InstallAsync` флаг `false` и запись была. Это
   проверка проводки сеятеля к пересчёту (порядок относительно коммита InMemory не различает).

`DemoSeederPostgresTests` (`VMS_MAP_TEST_DSN`, `[Collection("postgis")]`, мигратор, TRUNCATE):

6. `TheInstallDerivesTheFlagOnlyFromTheCommittedWorld`. Мир v1 ставит камеру в пространство A,
   ставится `object_arming(armed=true)` на A; мир v2 переносит её в B, флаг заранее `true`.
   Фейковый `ICfgArmingWriter` на каждой записи открывает **второй** контекст и запоминает, где
   лежит опорная реплика в закоммиченном мире. Утверждение: каждая наблюдённая запись видит B
   (то есть до коммита флаг не выводился), итоговый флаг соответствует зоне B.
7. `AFailedInstallWritesNoFlag`. Мир падает **после** раздела камер — например, ориентир с
   несуществующим ключом пространства (узлы пишутся раньше камер, поэтому отказ на узле не
   годится). Утверждения: `InstallAsync` бросает; фейковый писатель не вызван ни разу — откат не
   оставляет чужого флага.

Все конкурентные сценарии задаются детерминированной точкой (`AfterWrite`), а не `Task.Delay`:
тест воспроизводит ровно нужный порядок, а не надеется на планировщик. Повтор и обратный порядок
событий отдельного теста не требуют: пересчёт не берёт состояние из события, а читает текущее;
идемпотентность уже закреплена `ASecondLookWritesNothing`. Без DSN тесты 6–7 пропускаются, как
остальные Postgres-тесты. Имена — утверждения о контракте; повторяющиеся имена пространств —
константы, предел записей — `MaxWrites`, а не литерал.

## Вне объёма

- Атомарность чтения флага из VmsCfg и чтения карты: снимок делает карту согласованной, но два
  сервиса не читаются одной транзакцией. Чужую запись в VmsCfg после нашего чтения закрывает
  проверка после каждой записи (правка 1) и пересчёт писателя после коммита (правки 2–3).
- Найдено попутно: настройки частей (режим охраны входа, правило тревоги) сеятель пишет напрямую
