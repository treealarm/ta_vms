# Аудит блокировок карты

Карта берёт четыре транзитивных лока в одном порядке
(`MapLocks.cs`: `camera-state → camera-placement → alarm → device-diagram → hierarchy`). Каждый
появился под конкретную гонку, и комментарии в `MapLocks` её называют. Но набор никогда не
пересматривался целиком: неизвестно, какие из глобальных локов действительно нужны каждой
операции, а какие держатся «на всякий случай» и сериализуют весь деплой.

**Что известно**

- `camera-state` + `alarm` берёт каждая операция, меняющая состояние или агрегацию; сейчас их берут
  и сверка диаграммы устройства, и удаление камеры (с M1 «Cam Diagrams»).
- `device-diagram` с M1 — по устройству (`ta_map_device_diagram:{kind}:{id}`), без слота: сверка,
  размещение, привязка и удаление одной камеры исключают друг друга.
- `hierarchy` берёт последним `MapDb.UpdateHierarchyAsync`; вручную его не берёт никто.
- `camera-placement` — по камере, для создания картинки на канве.

**Что осталось**

1. Матрица «операция → таблицы и инварианты → защищающий лок» для всех писателей карты.
2. Конкурентные тесты на пары, которые матрица называет конфликтующими.
3. Только после этого — попытка сузить набор и замер до/после (сколько операций в секунду, сколько
   ждёт лок).

Блокировки — вопрос корректности, а не производительности: замер сам по себе не доказывает, что
лок можно убрать. Пока матрицы и тестов нет, глобальные локи остаются.
