# Порты Dapr внутри эфемерного диапазона

`scripts/dev_up.sh` поднимает девять `daprd` прямо на хосте и берёт их порты из
`.vscode/launch.json`: `-dapr-grpc-port` идут рядом 51001–51018. На этой машине
`net.ipv4.ip_local_port_range` = 32768–60999, то есть эти порты лежат внутри эфемерного диапазона
хоста. Любой исходящий сокет в том же namespace может занять такой порт как локальный, и тогда
`daprd` умирает на старте:

```
level=fatal msg="Fatal error from runtime: failed to start API gRPC server: could not listen on any endpoint"
```

Сервис при этом остаётся живым, а через Dapr недоступен: гейтвей отвечает 503. `dev_stack.py status`
этого не показывает — он говорит `listening` по порту приложения, а `daprd=` молча остаётся `-`.

**Наблюдалось 2026-11-27.** `vmsmap` не поднимался три раза подряд: `daprd` не мог занять 51018,
потому что `web-vms`-сайдкар держал соединение к Postgres ровно с этого локального порта. После его
закрытия порт ещё ~60 с висел в `TIME_WAIT` и тоже не давал сесть. Помог перезапуск `web-vms` с
последующим ожиданием, пока порт освободится.

**Почему так вышло.** Внутренние gRPC-порты (19011–19021) нарочно вынесены из эфемерного диапазона,
а app-facing — нет. В проде (`../ta_install/docker-compose.yml`) `-dapr-grpc-port` = 50001 тоже
внутри диапазона, но каждый сервис живёт в своём netns, и `daprd` слушает раньше, чем приложение
открывает свои соединения; риск меньше, но при перезапуске не нулевой.

**Что сделать:** перенести app-facing `-dapr-grpc-port` (dev и `.env`/compose прода) ниже 32768 —
рядом с существующими 19011+ — и проверить, что `dev_stack.py status` показывает `daprd=<pid>` у
всех сервисов сразу после запуска.

Связано: [distributed.md](../architecture/distributed.md), `.vscode/launch.json`.
