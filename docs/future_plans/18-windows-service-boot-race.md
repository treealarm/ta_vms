# Windows: службы ядра стартуют раньше сети

Найдено 2026-11-09 на стенде 192.168.1.82 (Windows 10, Wi-Fi), при включении машины после
выключения: `TaVms.RabbitMQ` не поднялся, в его логе

```
Failed to start Ranch listener {acceptor,{192,168,1,82},5672} ... for reason eaddrnotavail
(can't assign requested address)
```

Машина стартовала, но Wi-Fi-адаптер ещё не получил адрес, а `rabbitmq.conf` этого ядра слушает
AMQP на адресе машины (`192.168.1.82`), не на loopback. Служба с типом Automatic запустилась в
этот момент, не смогла забиндиться и осталась остановленной; повторного запуска нет. `TaVmsHost`
при этом ждёт PostgreSQL и RabbitMQ без ограничения времени, поэтому весь стек стоит, пока
администратор не запустит службу руками (`Start-Service TaVms.RabbitMQ` поднял всё за ~20 с).

Firewall и `TaVms.Postgres` (loopback) ту же проблему не показывают — у PostgreSQL адрес не нужен.

**Why:** установка на ноутбуке/машине с Wi-Fi или с DHCP — обычный случай, и там после каждого
включения стек может не встать сам. Заметить это можно только по логу RabbitMQ; web просто не
отвечает.

**How to apply:** варианты, которые надо взвесить при следующем заходе в установщик:
- `TaVmsHost` (или отдельный сторож) проверяет при старте, что каждый адрес из конфигурации
  реально присутствует на интерфейсе, и ждёт его — но он сам не может запустить RabbitMQ.
- Службам добавлены `delayed auto start` и/или recovery-действия (`failureflag`) на ошибку
  старта: RabbitMQ перезапустится через N секунд после появления адреса.
- Служба RabbitMQ получает зависимость от сетевого стека (`NDIS`/`Tcpip`) — не помогает, адрес
  появляется позже ассоциации Wi-Fi.
- `TaVmsHost` при недоступности RabbitMQ перезапускает службу, а не только ждёт.

Проверять на стенде: включить машину с Wi-Fi, не трогая службы, и убедиться, что web поднялся сам.
