# Серверный фильтр журнала событий: тип и текст

План P1/P2 ([docs/plans/ux-p1-audit.md](../plans/ux-p1-audit.md)) выносит в журнале событий тип и
поиск на первый уровень, но оба фильтра остаются клиентскими: `EventsJournal` прячет уже
загруженные строки (`visibleRows`), а страницы идут назад по keyset (`loadEvents`,
`store/eventsSlice.ts:50-62`). Серверный контракт этого не умеет.

**Что есть на сервере.** `SearchEventFilterDTO` (`dotnet/VmsMap/Domain/SearchEventFilterDTO.cs`)
принимает период, поддерево `objects`, `images_only`, `param0` и `param1`;
`EventsService.GetEventsByFilter` применяет их до keyset-курсора. Имени события и текста в
контракте нет — ни в DTO, ни в `GetEventsByFilterRequest` (`MapServiceImpl.Reads.cs`), ни в
клиентском `MapEventsFilter`.

**Почему это важно при большом журнале.** С выбранным типом клиент загружает страницы всех типов и
скрывает лишние. Пока совпадения есть в первой странице, это незаметно; когда их нет, оператор
листает «Load older» через события, которые всё равно не покажет, и «No rows» может стоять на
экране, хотя более старые подходящие события в журнале есть. Цена растёт с глубиной журнала и с
целью в 100 000 камер.

**Что сделать.** Решить набор фильтров и добавить их до нарезки страницы, как `param0`:

- `event_names: string[]` — очевидный первый шаг; тип на клиенте превращается в список имён
  (`sensor`, `relay`, `analytics`, `alarm*`, `arming`) и уходит на сервер;
- текстовый поиск — отдельное решение: по каким полям (имя события, `param0/1`, свойства), какой
  синтаксис и какой индекс. Для подстроки нужен trigram-индекс; для точного имени — обычный.

Изменение затрагивает proto (`GetEventsByFilterRequest`), `SearchEventFilterDTO`, `EventsService`,
web-контроллер/DTO и `wireFilter` в клиенте; после него заново прогнать журнал живьём на глубине,
где клиентская фильтрация перестаёт быть незаметной.
