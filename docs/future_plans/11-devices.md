# Устройства: модель, размещение и новые типы

Три темы, которые ходят вместе: что уже решено в модели устройств, как перейти от
камеро-специфичного размещения к общему и что понадобится, когда появится второй тип устройства.
Сюда сведены прежние `devices-and-nodes.md`, `generic-device-placement.md` и
`device-integrations.md`.

## 1. Модель: решено и работает

- **Камера — узел с момента создания.** `DeviceNodeService` (VmsMap/Adapter) по
  `server-config-changed` заводит канонический узел на каждую камеру, **всегда под узлом
  сервера** (`EnsureServerAsync`, имя — `server_id`). `device_node` (`source_kind`, `source_id`,
  `part_kind`, `part_token`) хранит соответствие «узел ↔ устройство/часть», потому что id узла —
  односторонний MD5; таблица `camera_node` переименована в `device_node` в M2.4a.
- **Канонический узел хранит смысл, а не рисунок.** На нём состояния, события, тревоги и права;
  `visual` и `geo_objects` у него нет вовсе.
- **Любое размещение — реплика.** Карта, план и диаграмма показывают камеру репликой
  (`objects.owner_id` → канонический узел) со своим рисунком в координатах своего холста и своим
  видом. Состояние у реплик общее — от владельца.
- **Эталон живёт на реплике.** `camera_placement` есть только у географических холстов; её строка
  с `is_reference` — это место, где камера стоит, и по ней работают наведение и калибровки. У
  реплики на диаграмме строки размещения нет: камера, размещённая только на диаграмме, опорного
  размещения не имеет, и наведение недоступно, пока её не поставят на карту или план.
- **Права устройства якорятся на пространство опорной реплики.** Канонический узел под сервером
  не наследует право, выданное на пространство карты; `RightsService` для узла устройства
  (камеры или части — часть разрешается через камеру) проверяет ещё и путь от опорной реплики.
  Нет опорной — действует путь через узел сервера.
- **Части устройства — не отдельные устройства.** Потоки, цифровые входы и реле — части одной
  камеры в VmsCfg; в дереве у части свой узел (`part_kind`), но узел устройства один. Узел части
  не обязан быть на карте: состояния, события, тревоги и права у него есть и без размещения.
- **Удаление устройства удаляет всё**: камеру с частями, реплики, размещения, наблюдения,
  события, состояния и тревоги. Пересоздание камеры даёт новый GUID и чистое дерево.
- **Что такое устройство, говорит `device_node`**, а `owner_id` отвечает только на вопрос
  «оригинал или отображение». Отдельного признака «устройство» нет — как в Square (решение
  2026-11-03).

**Admin → Nodes** — ленивое дерево с серверным поиском по имени, token и id камеры и действием
**States/Events**; **Admin → Maps → Devices** — палитра размещения с раскрываемыми частями;
вкладка **Devices** страницы камеры — настройки частей. **Place on map** из Admin → Nodes убран
(2026-11-08): он дублировал палитру Devices, но ставил камеру в центр вида без выбора точки и без
наведения конуса. Размещение живёт в редакторе карты, где его видно.

## 2. Что осталось по модели

- **Терминология.** «Устройство» (сама камера), «картинка» (реплика на плане с размещением),
  «отображение» (реплика на диаграмме без размещения) — провести эти три слова в UI и
  документации. Вкладка Cameras уже различает «Here, where it really stands» и «Picture».
- **Запрет привязки на диаграмме** получается косвенно (размещение требует пространства). Стоит
  покрыть тестом, чтобы это не «починили» случайно.
- **Свободное размещение частей устройства** на произвольном холсте — отдельная тема,
  [09-shared-device-diagrams.md](09-shared-device-diagrams.md).

Решённые вопросы, чтобы не открывать их заново:

- **План и диаграмма остаются двумя сущностями**, необязательной географической рамки у диаграммы
  не будет (решение 2026-11-03, записано в
  [`../plans/square-merge/m2.2-demo-configuration.md`](../plans/square-merge/m2.2-demo-configuration.md)).
- **Nodes показывает все логические узлы**, включая канонические узлы устройств и частей; вариант
  «скрывать» отменён (2026-11-05).
- **Картинка камеры на другом плане имеет реальные координаты** — иначе план не покажет камеру
  там, где её не видно; это осознанное поведение Square.
- **Отображение абстрактного узла на диаграмме разрешено** — это просто реплика без привязок.

## 3. Общее `device_placement` вместо `camera_placement`

Найдено 2026-11-05 при обсуждении M2.4: `camera_placement` лежит в логической части (`ta_map`) и
содержит камеро-специфичные поля. Своя таблица размещения на каждый тип устройства плохо
масштабируется.

Сейчас `camera_placement` (`VmsMap/Grpc/migrations/0000_init.sql:401`):

```sql
object_id    uuid PRIMARY KEY REFERENCES objects (id) ON DELETE CASCADE,
camera_id    uuid NOT NULL,
is_reference boolean NOT NULL DEFAULT true,
height_m     double precision NOT NULL DEFAULT 3,
heading_deg  double precision NOT NULL DEFAULT 0,   -- компасный курс, 0 = север
hfov_deg     double precision NOT NULL DEFAULT 60,
range_m      double precision NOT NULL DEFAULT 30
```

Геометрия точки — в `geo_objects`; `camera_placement` — дополнительные признаки камеры и признак
эталона. Потребители: `SpatialDb`, `VmsPtzTrackingSingleton` (наведение/калибровка),
`api/spatial/placements`, демо-сидер.

Варианты:

1. **Оставить `camera_placement`; для других типов — свои таблицы.** Просто и типизировано, но
   каждый новый тип добавляет таблицу и код размещения. Не масштабируется.
2. **Общий `device_placement` с `source_kind` + `props jsonb` (рекомендуется).**
   ```sql
   CREATE TABLE device_placement (
     object_id    uuid PRIMARY KEY REFERENCES objects (id) ON DELETE CASCADE,
     source_kind  varchar NOT NULL,   -- 'camera' | 'fire_panel' | ...
     source_id    uuid NOT NULL,      -- id устройства в его плоскости
     is_reference boolean NOT NULL DEFAULT true,
     height_m     double precision NOT NULL DEFAULT 0,
     heading_deg  double precision,   -- общий для наведения
     props        jsonb NOT NULL DEFAULT '{}' -- hfov_deg, range_m, зона, ...
   );
   ```
   Общие поля типизированы, специфические — в `props` с JSON-схемой на тип. `camera_placement`
   остаётся view/совместимым слоем на время миграции; `SpatialDb`/PTZ читают через типизированные
   аксессоры.
3. **Только `geo_objects` + properties, без боковой таблицы.** Минимум схемы, но теряются типы,
   ограничения (одна эталонная строка), индексы по `hfov/range` и быстрые запросы для наведения.

Что учесть:

- Одна эталонная строка на устройство (`UNIQUE ... WHERE is_reference`) — это ограничение должно
  остаться.
- `VmsPtzTrackingSingleton` и `SpatialDb` читают `hfov_deg`/`range_m`/`heading_deg`; переход на
  JSON требует аксессоров и валидации, иначе ошибки всплывут в наведении.
- Для частей устройства (датчик/реле) размещение вообще не нужно: `geo_objects` достаточно, если
  часть рисуется; `device_placement` — для устройств, которым нужны признаки эталона/наведения.
- `camera_placement` в `ta_map` — это логическое представление, а не запись VmsCfg; общий
  `device_placement` не должен превращаться в копию железной конфигурации.

**Рекомендация:** вариант 2, но не раньше второго типа устройства: сначала сделать второй тип
руками «по аналогии», увидеть реальные различия, затем мигрировать `camera_placement` в
`device_placement` с `props` и JSON-схемой, оставив view для совместимости.

Открытые вопросы:

- Какие поля общие для всех устройств (height, heading) и какие уходят в `props`?
- Нужна ли JSON-схема/валидация на уровне БД или достаточно кода?
- Делать `device_placement` сразу или после появления второго типа устройства?
- Как мигрировать существующие `camera_placement` и не сломать PTZ-наведение?

## 4. Второй тип устройства «по аналогии»

Замечание пользователя 2026-11-04: «камеры как бы особый вид объектов… условный радар
интегрировать должно быть просто "по аналогии"». Сейчас камера — единственный тип устройства, и
весь путь «от записи в конфигурации до точки на плане» написан под неё. Дерево, состояния,
права, реплики и рисунки от типа не зависят.

Что в камере специфично сегодня (по коду):

| Слой | Камеро-специфичное | Файл |
|---|---|---|
| Идентичность | id канонического узла = MD5 от `camera_id`; обратный справочник — `device_node` (`source_kind`, `source_id`, `part_kind`) | `VmsMap/Adapter/DeviceNodeService.cs`, `SpatialDb.EnsureCanonicalNodeAsync` |
| Конфигурация | `cameras` в VmsCfg; приходит через `server-config-changed`, узел и размещение заводятся адаптером | `VmsMap/Adapter/`, `DeviceNodeService` |
| Размещение | `camera_placement`: эталон у реплики, высота, курс, угол обзора, дальность; у канона размещения нет | `VmsMap/Db/Services/SpatialDb.cs`, `spatial`-контроллер |
| Состояния | `CONNECTED`/`DISCONNECTED` от обрывов VmsFs, `ALARM` от retention — но сама механика состояний и счётчиков по дереву тип-нейтральна | `VmsMap/Adapter/`, `StatesUpdateService` |
| Живой поток | MediaMTX/WHEP, ONVIF (PTZ-актёры), камера как источник кадров для аналитики | `VmsOnvif`, `video_srv` |
| UI | вкладка Cameras, маркер с сектором обзора, панель размещения | `SpaceEditor.tsx`, `markers.tsx`, `PlacementPanels.tsx` |

Тип-нейтрально уже всё остальное: дерево — `objects`; рисунок — `geo_objects`; состояния и
счётчики — `object_states`/`alarm_states`; права — `rights` на узлах; «оригинал или отображение» —
`objects.owner_id`.

Что понадобится радару «по аналогии»:

1. **Запись в своей плоскости.** Радар — строка в конфигурации (сегодня ближайшее место — VmsCfg,
   но его таблицы камеро-образны) и событие об изменении, как `server-config-changed`.
2. **Канонический узел** с id, выводимым из id устройства, и обратным справочником
   «узел ↔ устройство» — тем же приёмом, что `device_node`, но для своего типа.
3. **Размещение** — своя боковая таблица (высота, курс, сектор обзора — у радара он другой формы
   и смысла, чем `hfov_deg`), с тем же правилом: эталон у реплики, картинки — реплики.
4. **Состояния и события** от владельца: значения пишет тот, кто знает правду об устройстве,
   дерево только агрегирует. Менять для этого ничего не нужно.
5. **Реплика** для картинки на другом плане и отображения на диаграмме — уже общий механизм.
6. **UI**: своя вкладка выбора устройства и свой маркер на карте; список узлов не должен
   обрастать вторым набором канонических устройств.

Если делать «в лоб», получится второй `DeviceNodeService`-подобный класс с копией логики
узла/размещения/реплик. Если «по аналогии», копируется только то, что действительно разное
(таблица размещения, источник конфигурации, маркер), а общий путь переиспользуется.

**Форма, к которой это должно прийти (не сейчас):** один адаптер на тип устройства — «источник
конфигурации → канонический узел → своя боковая таблица → своя панель UI». Карта остаётся
тип-нейтральной и знает только `objects`, `geo_objects`, состояния и права. Конкретный интерфейс
адаптера пока не проектируется намеренно: пока тип один, любая абстракция будет угадыванием
(YAGNI). Второй тип сделать руками, вынести общее в интерфейс после второго примера.

Открытые вопросы:

- **Где живёт конфигурация не-камер.** Расширять VmsCfg таблицами устройств или заводить
  отдельный сервис? Реле и цифровые входы уже приходят через ONVIF-камеру, а радар — нет.
- **Одно размещение на все типы или своё у каждого.** Общие поля повторяются; специфичные
  (сектор, дальность, ориентация) — нет. Второй пример покажет, стоит ли выносить
  `device_placement` с общей частью.
- **Идентичность узла.** `CameraObjectId` — MD5; для нового типа нужен такой же детерминированный
  id и обратный справочник. Повторять MD5 или перейти на явный id вида `device/<тип>/<ключ>` —
  решить на втором типе.
- **Как тип объявляет свои состояния и действия.** Сегодня имена состояний (`ALARM`, `NORM`,
  `CONNECTED`) — соглашение адаптера, а не объявление типа; при двух типах это станет заметно.
