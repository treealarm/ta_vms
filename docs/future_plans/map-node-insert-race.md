# Узел карты вставляется без upsert: гонка на первой установке

Найдено 2026-11-06 при проверке M2.4a (шаг 1), на свежесозданной БД `ta_map`.

## Что произошло

После пересоздания БД и подъёма стека с нуля камеры провижинились пачкой, и почти одновременно
ставился демо-мир. VmsMap один раз залогировал:

```
23505: duplicate key value violates unique constraint "objects_pkey"
```

Стек: `CameraChangeSubscriber.ReconcileAsync` → `CameraNodeService.EnsureCameraAsync` →
`EnsureServerAsync` → `MapDb.UpdateHierarchyAsync` → `SaveChanges`. Тот же узел (сервер или
камера) успел создать другой путь — сидер демо зовёт `EnsureCameraAsync` до своей транзакции.

Подписчик вернул Dapr `Retry`, сообщение пришло повторно, установка продолжилась; на второй и
последующих установках ошибка не воспроизвелась. То есть данные не потерялись, но в логе остаётся
стена исключения, а полагаться на retry как на штатный путь не стоит.

## Почему

`MapDb.UpdateHierarchyAsync` решает «вставить или обновить», читая существующие строки до
`SaveChanges`. Между чтением и вставкой другой процесс (или другой `DbContext` того же процесса)
успевает вставить ту же строку. `EnsureServerAsync`/`EnsureCameraNodeRowAsync` идемпотентны по
смыслу, но не по конкурентности.

## Что сделать

- Вставку узла сделать upsert: `INSERT … ON CONFLICT (id) DO NOTHING` и повторное чтение (или
  `ON CONFLICT (id) DO UPDATE SET name/parent/owner` там, где это уместно семантике вызова).
- Либо сериализовать создание узлов карты собственным advisory lock на `objects` (по образцу
  `MapLocks`), если upsert не ложится на `UpdateHierarchyAsync` целиком.
- Делать это вместе с пакетным `StartupResyncService` из шага 2 M2.4a: там обход камер уже
  переписывается, и именно там конкурентные вызовы `EnsureCameraAsync` станут массовыми.

## Проверка

Провижининг 100–200 камер одной пачкой на пустой `ta_map` при одновременно идущей установке демо:
в логе VmsMap нет `objects_pkey`, все узлы созданы ровно по одному разу.
